## 3. 四塊大的，錢花在哪

### 3.1 TTS：固定成本 1.18 秒，其中 426ms 是每輪白做的

實測（真 CosyVoice 3 服務，n=3／點）：

| 字數 | 合成耗時 | 產出音檔長 | 即時率 |
| ---: | ---: | ---: | ---: |
| 2 | 1426ms | 1.0s | 0.70x |
| 6 | 1592ms | 1.5s | 0.95x |
| 14 | 3114ms | 4.8s | 1.55x |
| 27 | 4541ms | 7.8s | 1.73x |
| 51 | 7509ms | 14.3s | 1.91x |

→ **固定成本約 1178ms、每字約 124ms**。（7/26 報告記的是 0.9s ＋ 0.10s/字，兩個都漂了。）

固定成本裡有一塊是可以直接拿掉的，**這是實測不是推測**：

從 TTS 服務自己的日誌拆（n=60，`yield speech len L, rtf R` 與 tqdm 的每項總時間相減）：

```
model.tts 推論      = 音檔長 × rtf（rtf 中位 0.591，隨長度變）
frontend 前處理     = 中位 426ms，範圍 408–474ms —— 與文字長短無關
```

那 426ms 的出處指得出確切的行：

* `services/tts/server.py:101` 呼叫 `inference_zero_shot(text, prompt, TTS_PROMPT_WAV, stream=False)`，**沒有傳 `zero_shot_spk_id`**。
* `cosyvoice/cli/frontend.py:170` 判斷 `zero_shot_spk_id == ''` 時走 171–184：對**同一個固定參考音檔**跑 `_extract_speech_feat`＋`_extract_speech_token`＋`_extract_spk_embedding` 三次模型前向。
* 參考音檔（`asset/zero_shot_prompt.wav`）從服務啟動到關閉**一個位元組都沒變過**，所以這三次前向每輪產出完全相同的結果。
* `cosyvoice/cli/cosyvoice.py:69` 的 `add_zero_shot_spk` 就是把那份結果存進 `spk2info`，之後 `frontend.py:186` 直接取用。

### 3.2 Agent LLM：輸出的 94% 是思考 token

`llm_calls`（近 14 天，`kind='agent'`，n=390）：

| | p50 | p95 |
| :--- | ---: | ---: |
| 輸入 token | 4217 | 10313 |
| 輸出 token（**含 thinking**） | 552 | 1335 |
| 實際回覆字數 | 30 | 40 |

30 個中文字約 35 token，所以 **552 − 35 ≈ 517 個 token 是思考**，佔輸出的 94%。

⚠️ 這不代表關掉 thinking 就好：2026-07-27 實測過，`gemini-3.5-flash-lite` 不設 thinking 時工具呼叫率掉到 3/10 且會編造店名，設 MEDIUM 才 5/5。**這是正確性防線，不是可以省的脂肪**（`llm.py:36-40` 已載明）。

另兩個對照：`risk_classify` 輸入才 151 token、輸出 45 token，仍要 901ms；`moderation` 451/48 要 878ms。
→ **短輸入的判斷型呼叫，時間幾乎全是 API 往返的地板（約 850ms），不是算出來的。** 減少「呼叫次數」比減少「token 數」有效得多。

### 3.3 情境組裝：mem0 單獨跑 582ms，在管線裡變成 1510ms

| | 中位 |
| :--- | ---: |
| 地端 BGE-M3 嵌入一句話 | **7ms** |
| mem0 原生 search（嵌入＋向量查詢） | 557ms |
| `Mem0LongTermStore.search`（原話＋健康兩路並行） | **582ms** |
| 同一段，在完整管線裡 | **1510ms** |

嵌入只花 7ms（2026-08-07 切地端 BGE-M3 的成果），所以那 557ms 幾乎全是**打去 Supabase 的向量查詢往返**——約等於兩次跨海往返。

單獨 582ms、在管線裡 1510ms 的 2.6 倍差距，**成因未逐項驗證**。候選有二：管線裡同時有 5～7 個 Supabase 查詢在飛而連線池只有 5 條（`DATABASE_POOL_MAX_SIZE=5`）；以及同一時刻還有一個 Gemini 呼叫在同一個行程裡。要斷定是哪個，得在**只跑管線、不跑其他行程**的機器上重測。

## 4. 已經實測過的優化：合併分類器（現成的、關著的）

`SAFETY_COMBINED_CLASSIFIER_ENABLED` 這個旗標**程式早就寫好了，預設是 false**。開起來跑同一組五句話：

| | 對照組（分開呼叫） | 合併組 | 差 |
| :--- | ---: | ---: | :--- |
| **端到端 中位** | **9895ms** | **8324ms** | **−1571ms（−16%）** |
| 端到端 最慢 | 20852ms | 12012ms | 尾巴收斂 |
| 安全階段本身 | 1024＋902＝1926ms | 1125ms | **−801ms** |
| 情境組裝 | 1510ms | 992ms | −518ms |

**可信度分級**：安全階段那 **−801ms 是直接對照、可信**（兩次呼叫變一次，省下一次 API 往返地板）。端到端的 −1571ms 與情境組裝的 −518ms **不能全記在這項頭上**——兩組不是同時跑的，對照組還吃到一次 12 秒的停頓（見 §6）。保守估計真實收益是 **0.8～1.0 秒**。

安全屬性不變：`pipeline.py` 的註解與 `combined_classifier` 模組頂端已載明，合併後 `moderation` 結果雖然提早拿到，仍要等危急落庫／家屬通報／提醒標記走完才被查看——`test_moderation_runs_after_family_notification` 守住這條。

## 5. 還能往哪裡優化：按「已知價值 ÷ 工作量」排序

| # | 項目 | 預估收益 | 工作量 | 把握度 |
| :--- | :--- | ---: | :--- | :--- |
| 1 | **開 `SAFETY_COMBINED_CLASSIFIER_ENABLED`** | **0.8–1.0s** | 改一行 .env | **已實測** |
| 2 | **TTS 快取 speaker embedding**（`add_zero_shot_spk` ＋ 傳 `zero_shot_spk_id`） | **~0.43s／次合成** | 服務端約 5 行 | **已實測 426ms** |
| 3 | **TTS 改真串流**（`stream=True`，第一塊音訊即送） | 未測，理論可省第一段合成的大半 | 服務端＋投遞端協定 | 需實測 |
| 4 | 把 mem0 向量查詢搬離 Supabase（地端 pgvector／qdrant） | 上看 0.5s | 大 | 需實測 |
| 5 | 音檔上傳改直送 WS，不經 Supabase Storage | ~0.5s | 中 | 需實測 |

### 1 與 2 為什麼是先做的

兩項都**已經有實測數字**、都不動決策順序、都可以單獨回退。合計約 **1.2–1.4 秒**，端到端從 9.9 → 8.5 秒左右。

第 2 項的實作就是照 `add_zero_shot_spk` 的用法：啟動時（`lifespan` 已有 `TTS_PRELOAD`）註冊一次金孫的聲音，之後每次 `inference_zero_shot(..., zero_shot_spk_id="kinsun")`。
⚠️ 要驗的是**音色一模一樣**——`add_zero_shot_spk` 存的就是同一份 `model_input`，理論上位元相同，但這件事必須聽過才算數，不能只看程式碼。

### 3 為什麼值得試、但要小心

`services/tts/server.py:101` 寫死 `stream=False`，而 CosyVoice 的 `model.tts(**model_input, stream=stream)` 是支援串流的。目前 rtf 約 0.5–0.6，14 字的第一段要 3.1 秒；串流能讓第一塊音訊在整段算完前就出來。

⚠️ **7/26 已經走過一條相似的彎路**：「分段平行合成」實測更慢（GPU 互搶，固定成本付三次），結論寫在 `speech/chunking.py` 的模組說明裡——「唯一有效的路是真串流」。這一項正是那句話指的方向，但它要動 TTS 服務與投遞端的協定（目前是一次回完整 m4a ＋ `X-Duration-Ms` 標頭），不是改個參數。

### 一個測到、但**不建議**照直覺修的

需要工具的那兩句，回覆是這樣的形狀：

```
「台北今天下雨耶，氣溫大約二十四到三十一度，出門記得帶傘喔！」  29 字 → 切成 1 段
「哇，天氣好出去走走最棒了耶！阿公路上要小心，慢慢走喔。」      27 字 → 切成 2 段（第一段 14 字）
```

第一句整段都是逗號、只有句末一個驚嘆號，`split_for_speech` 切不開 → **分段串流對它完全沒作用，付了 29 字的全額 TTS**。而它恰好是「有資訊、比較長」的那一型回覆。

直覺的修法是「逗號也切」——**不要**。`speech/chunking.py:27-29` 已寫明是刻意不切：逗號處切開會讓 TTS 把半句唸成完整句、語氣塌掉。要處理的話該從提示詞下手（要求用句號斷句），而且要重新驗語氣，不是改正規表達式。

### 順帶查證：`MIN_CHUNK_CHARS = 8` 還站得住

那個 8 是從「合成時間要蓋得住播放時間」推出來的，用的是 7/26 的常數。今天兩個輸入都漂了，方向相反：

```
7/26： N/4.6 ≥ 0.9 + 0.10N   → N ≥ 7.7  → 取 8
今天： N/3.5 ≥ 1.18 + 0.124N → N ≥ 7.3  → 仍然是 8
```

（語速實測 3.5 字/秒，非 4.6。）**結論沒變，但推導過程的三個數字都要改**，見 §7。
另外：若第 2 項（speaker 快取）上線，固定成本降到約 0.75s，門檻會降到 N ≥ 4.6——那時才值得重新調這個常數。

## 6. 兩個尾巴風險（不是每輪都遇到，但遇到就很痛）

### 6.1 一次 12 秒的全面停頓

對照組第 3 輪（`台北今天天氣怎麼樣`，端到端 20375ms）出現這個形狀：

```
今日對話 recent      10230ms   （平時 178–426ms）
長期記憶 mem0.search 12243ms   （平時 985–2047ms）
事實查詢             10635ms   （平時 362–739ms，兩個提供者直接逾時放棄）
危急分級 Gemini      10776ms   （平時 852–1013ms）
```

**Supabase 與 Gemini 兩個完全不同的外部服務同時卡住十秒**，同一輪還印了兩行「事實提供者逾時（5.0 秒），略過該段」。

**根因未定，不寫在這裡當結論。** 三個候選：(a) 探針是與正式服務並存的第二個行程，兩邊搶 Supabase pooler 的 15 條連線上限（`db.py:659-662` 已載明常駐服務吃掉大部分）；(b) 機器層級的瞬間壅塞；(c) Gemini 免費層的隱式節流重試。
生產庫有同型事件（08-01 有 agent 18.4s、ASR 10.1s 各一筆），所以**不能當成純探針假象**打發掉。要定案得在乾淨機器上重現。

值得注意的副作用：事實提供者逾時是**靜默降級**——那一輪金孫的提示詞裡就少了排程或守則，長輩問「我今天要吃什麼藥」會得到不完整的答案，而且沒有人會知道。

### 6.2 Gemini 免費層 15 RPM

探針第一次跑到第四輪就撞 `429 RESOURCE_EXHAUSTED`：
`quotaValue: '15'`／`GenerateRequestsPerMinutePerProjectPerModel-FreeTier`。

一輪對話要打 3～4 次（分級、審核、工具輪 ×1–2）→ **同時最多支撐約 4 位長輩／分鐘**。畢典展示若有多人同時試玩，會直接撞牆。
（合併分類器把每輪從 3–4 次降到 2–3 次，順帶把這個天花板抬高約三成。）

| `tts_queue_wait`／`tts_synthesize` | 把「排隊等 GPU」與「GPU 在算」切開 |
| `memory_record_turn`／`memory_settle_wait` | 寫記憶本身、以及交出回覆前又多等多久 |
| `observability_write`／`reminder_mark`／`memory_write` | 一輪六筆背景落庫 |
| `tool:<工具名>` | 原本所有工具共用一格叫 `dispatch` |

另加兩個 trace 級數字：`admission_wait_ms`（metadata）與 `round_trip_ms`（feedback score，可在 Opik 上聚合 p50／p95）。

### 最重要的一項：`agent_generate` 先前是個會誤導人的數字

情境組裝與安全檢查並行，組裝較慢時 `handle` 卡在 `PreparedTurn.context()` 乾等——而這段乾等**整段被算進 `agent_generate`**。正式 trace `019fdc37` 實錄：

```
memory_assemble   513 ──────────────── 3939
agent_generate         2214 ──────────────── 5949   （Opik 顯示 3735ms）
                       └─ 前 1725ms（46%）其實是在等記憶 ─┘
```

這正是為什麼生產庫的 `llm[agent]` p50 高達 4917ms，而探針量到的單次 Gemini 工具輪只有 1222ms。**沒有這一格，看 Opik 調延遲的人會去縮 prompt、換模型，真正該修的是記憶檢索。**

## 附錄：量測方法

* **全鏈路探針**：複製 `app.build_app` 的管線接線，把每個 seam（ASR／分級／審核／`SessionMemory.assemble`／各事實提供者／`GeminiClient.generate*`／`ToolRegistry.dispatch`／TTS／上傳）換成計時版本，記下 `(label, t0, t1)` 後攤成時間軸。**並行段只算一次覆蓋，不加總**——加總會得出比端到端更大的數字。
* **探針錄音**：用 TTS 服務把五句話合成 m4a，再餵回 ASR，等同真人錄音的資料形狀。
* **節流**：兩輪間隔 22 秒（Gemini 免費層 15 RPM）。第 0 輪暖機不計（mem0 連線、Gemini TLS、TTS GPU 都是冷的；暖機輪的 mem0 檢索是 5.7 秒）。
* **探針長輩**：`probe-latency-elder`（88 則對話、2 筆排程），不碰真人記憶。
* **TTS 內部拆解**：不另外載模型（GPU 已被 ASR＋TTS＋BGE-M3 佔滿，試載會 CUDA OOM），改從服務日誌的 `yield speech len L, rtf R` 與 tqdm 每項總時間相減得出前處理成本，n=60。

## 三分鐘看懂金孫系統（先讀這段，後面每題都看得懂）

金孫＝「長輩的 AI 語音孫子」。整個系統長這樣：

- **長輩用的 App**：畫面上只有一顆大按鈕。按住講話、放開，金孫就用語音回答。不用打字、不用學任何操作——連開通都是家屬代辦的（家屬產生一組「綁定碼」輸入長輩手機就完成）。
- **金孫在背後同時做兩件事**：
  1. **陪聊**——AI 生成回覆，而且記得長輩說過的事（用藥、慢性病、生活習慣），隔天會回頭關心；
  2. **安檢**——長輩說的每句話都自動判斷危急程度，分四級：**L0**＝沒事／**L1**＝小訊號（「最近睡不好」）／**L2**＝明確警訊（「頭很暈」「跌倒」）→ **通知家屬**／**L3**＝可能有生命危險（「救命」「想不開」）→ 通知家屬＋提醒撥 119。判斷靠「11 個關鍵詞（死規則）＋AI 理解（活判斷）」兩道關卡。
- **家屬用的 App**：同一個 App 選「我是家屬」——幫長輩開通、設定用藥／回診提醒、看健康報告、收警報。
- **LINE 舊版**：產品最早做在 LINE 上（家屬在 LINE 裡開網頁操作）。現在主力轉到 App，**LINE 版凍結**——能用但不再加新功能。
- **開發者後台**：我們自己排查問題用的網頁，看得到系統運作紀錄。
- **幕後**：AI 大腦＝Google Gemini（雲端服務）；「聽懂長輩說什麼」（語音辨識）和「合成金孫的聲音」（語音合成）跑在我們的 DGX 主機上；所有資料存在雲端資料庫。
- **知情同意**：長輩開始用之前，系統會徵求同意（「金孫會記錄您的對話，必要時通知家人，同意請說是」）。**今天議程一整個都在補這個機制的洞。**

## 議程一：同意與隱私制度（四題是一組，建議連著討論）

> **為什麼有這組題**：「同意機制」是趕工做的，盤點後發現四個洞。這關係到倫理和法律，不能由一個人決定。

### 會-1｜長輩說「我不要用了」之後，金孫還是每天傳訊息給他

- **現在的情況**：系統各功能對「要不要檢查長輩同意」標準不一——用藥提醒會檢查（沒同意就不發）；回診提醒對長輩會檢查，但**發給家屬的那份不檢查**；每天的早安問候和失聯關心**完全不檢查**。結果：長輩撤回同意後，隔天早上 8 點金孫照樣傳「早安」給他。
- **要決定**：統一成什麼標準？
- **選項**：(a) 撤回＝金孫完全靜默，連給家屬的通知也停；(b) 對長輩的訊息全停，但家屬的通知照發（家屬有知的權利）。
- **建議**：(a)——撤回就該是真的撤回。
- [x] 決議：**直接忽略長輩的同意狀態**——提醒與主動訊息一律照發，不檢查長輩同不同意（既有的用藥／回診同意檢查一併移除；開通時的初次同意閘門維持）。（2026-07-09）

### 會-2｜想撤回同意，整個系統找不到地方按

- **現在的情況**：程式裡有「撤回同意」的功能，但**沒有任何按鈕、指令或畫面可以觸發它**——長輩或家屬想反悔，無路可走。另外：撤回後既有的對話紀錄會保留（這部分 Leo 已決定：預設永久保留，並在條款裡講清楚）。
- **要決定**：①撤回的入口做在哪？（家屬 App 的設定頁？長輩對金孫說「我不要用了」？兩個都做？）②撤回時要不要提供「順便刪光我所有資料」的選項？
- **建議**：家屬 App 設定頁做入口＋提供刪除選項（對外發表時「使用者資料權」是加分的故事）。
- [x] 決議：**不做撤回入口**——長輩不需要這個 App 的話會自己不用／刪掉。（2026-07-09）

### 會-3｜同意條款要改版了，以前同意過的人怎麼辦？

- **現在的情況**：我們已決定在同意條款裡補講三件事（①對話會送雲端 AI 處理 ②資料永久保留 ③開發團隊會為了排查問題看到對話內容）。問題來了：**條款改版後，之前同意過「舊版」的長輩，算不算同意過「新版」？**目前系統沒有「重新問一次」的機制。
- **要決定**：要不要對已同意的長輩重新徵求同意？怎麼問（下次對話時金孫用語音問一次？請家屬代確認？）
- **建議**：下次互動時金孫口頭問一次＋系統記下新版本號。
- [x] 決議：**先不用管**——條款改版時默認長輩也同意新版，不做重新徵求機制。（2026-07-09）

### 會-4｜家屬到底能看到長輩的什麼？

- **現在的情況**：家屬現在看得到「警報＋提醒紀錄」。但很多人不知道：系統**每天晚上都幫每位長輩寫一篇當日摘要（含心情描述）——寫好後沒有任何人看得到，純粹放著**。程式裡還埋了一個「主要家屬可以看逐字對話」的開關，從來沒啟用過。這是隱私的核心：長輩可能不想讓子女知道自己跟金孫說了什麼。
- **要決定**：家屬可見範圍劃在哪？①只有警報＋提醒（現況）②加上每日摘要 ③主要家屬可以看逐字對話。
- **建議**：②——摘要已經在生產、對家屬價值高；但要在同意條款寫明。逐字對話不開放。
- [x] 決議：**家屬可以看到每日摘要**；**管理員後台可以看到所有對話內容**（目前是方便我們調適／測試）。（2026-07-09）

## 議程二：危急守護政策（產品最核心的承諾）

### 會-5｜長輩說一次「頭暈」，全家手機同時響——這樣好嗎？

- **現在的情況**：只要判到 L2（明確警訊），系統**立刻通知所有家屬，而且每提一次就再通知一次**——沒有冷靜期、不會合併同一件事、也沒有「先通知大女兒、沒回應再通知其他人」的順序（資料庫有這個欄位但沒在用）。長輩聊天提三次「跌倒」，全家收三輪警報——很快大家就麻木了，真出事反而沒人理。
- **要決定**：①全員同時通知，還是接力升級？②要不要冷靜期（同一件事 N 分鐘內不重複轟炸）？③ L1 小訊號現在直接丟掉——要不要留下來給家屬看趨勢用？
- **建議**：全員同時＋30 分鐘冷靜期＋L1 留紀錄但不通知。
- [x] 決議：**通知所有家屬；重複提醒就重複通知，不需要冷靜期**（不是壞事）；**L1 小訊號在每日摘要裡提及就好**——不是緊急到需要立刻通知的事。（2026-07-09）

### 會-6｜判斷生死的那 11 個詞，從來沒有人審過

- **現在的情況**：觸發警報的關鍵詞目前只有 11 個（救命、想不開、頭暈、跌倒⋯⋯），寫程式的時候標註了「之後要請照護專業定稿」但一直沒做。問題：缺台語（跋倒、艱苦、袂喘氣）、缺變形講法（「活不下去」不在表裡）、而且「胸口很痛」比「胸痛」更窄——長輩講「胸痛」反而不會觸發。台語支援已確定要做，詞表必須跟上。
- **要決定**：定稿的**流程**——誰負責整理？什麼時候定稿？要不要找有照護背景的人（老師？當護理師的親友？）幫忙審一次？
- **建議**：指定一位組員當窗口，AI 先產出擴充草案（含台語），兩週內找一位照護背景的人審過，8 月初定稿。
- [x] 決議：**未來測試時滾動新增**（AI 可先推薦候選詞）；**台語詞不用加**——語音辨識輸出的就是國語漢字，不會出現台語漢字。（2026-07-09）

### 會-7｜AI 的「自信門檻」要調在哪裡？

- **現在的情況**：AI 判斷危急時會附一個「自信分數」（0 到 1）。目前規則：AI 說是 L3 但自信低於 0.7 → 降成 L2；說是 L2 但自信低於 0.4 → 降成 L1 不通知。**這兩個數字是當初 AI 寫程式時隨手填的**，直接影響「誤報多還是漏報多」。
- **要決定**：0.7／0.4 這兩個數字要不要調？（可以先不動，等會-6 詞表定稿時拿真實對話測一輪再定。）
- **建議**：先維持，跟詞表定稿一起用實測校準。
- [x] 決議：**先維持現值，未來測試時再調整**。（2026-07-09）

## 議程三：產品定位與對外敘事（8/20 發表相關）

### 會-8｜我們的目標長輩是誰？

- **現在的情況**：目前設計是「家屬包辦一切（註冊、開通、設提醒），長輩拿到手機只需要按住說話」——長輩零學習成本，但也什麼都不能自己改。另一條路是讓長輩能自己操作部分功能（要做長輩專用的設定介面，工程量大）。這決定產品故事怎麼講、以後功能往哪邊長。
- **要決定**：維持「家屬代辦＋長輩只說話」，還是投資「長輩可自主操作」？
- **建議**：維持家屬代辦，發表時把「長輩零學習成本」當賣點講。
- [x] 決議：**跳過**——團隊認為目前不需要解決，太細節；行為維持現況。（2026-07-09）

### 會-9｜對外怎麼介紹守護功能？＋三個介面的用詞要統一

- **現在的情況**：當初提案對外講「4 類風險訊號」（情緒低落／身體不適／作息失聯／用藥遺漏），但實際做出來是「L0–L3 四級制」，兩套講法對不上。更麻煩的是**三個介面各講各的**：同一個 L2 警訊，手機 App 顯示「需留意」、LINE 網頁顯示「警示」、開發者後台顯示「L2」——家屬兩邊看會以為是兩件不同的事。
- **要決定**：①發表時對外用哪套講法？（保留好懂的「4 訊號」故事＋附一頁對照表／全部改講四級制）②統一之後，每個等級的中文到底叫什麼？
- **建議**：對外講「4 訊號」（好懂），內部附對照表；用詞統一為 L2＝「警示」、L3＝「緊急」。
- [x] 決議：**跳過**——團隊認為目前不需要解決，太細節；發表講法等做發表文件時再定。（2026-07-09。另注意：會後 Leo 拍板分級改三級、刪 L3，見 00 清單 D-72）

### 會-10｜「做得好不好」的及格線數字要填多少？

- **現在的情況**：已定四類成績單，但目標數字空著：①危急偵測抓得準不準（要先準備一批標好正確答案的測試句子來考它）②語音往返速度（提案當初寫 3–4 秒內）③台語品質（微調前後比較）④找真的長輩來實測（提案當初寫 7 位）。
- **要決定**：四個數字（或範圍），以及「長輩找幾位、誰負責找」。
- **建議**：往返速度中位數 ≤4 秒；「漏報」比「誤報」嚴重，漏報率 ≤10%；台語以「微調後明顯優於微調前」為底線；長輩實測 5–7 位。
- [x] 決議：**跳過**——團隊認為目前不需要決定，太細節；量測工具照做，數字等實測後再補。（2026-07-09）

### 會-11｜金孫的早安問候，要不要用「說」的？

- **現在的情況**：金孫每天早上主動問候長輩，目前是**純文字**訊息。技術上可以讓金孫改用語音問候（長輩點開就聽到金孫講話），代價是每天每位長輩多一次語音合成的運算。
- **要決定**：要不要做語音版主動問候？
- **建議**：做——語音是這個產品的靈魂，文字問候對不識字的長輩根本無效。
- [x] 決議：**先做文字就好**。（2026-07-09）

### 會-12｜衛教回答的「小心」等級——要問當初做的人

- **背景**：金孫回答健康問題時，會去查**我們自己準備的官方衛教資料**再回答（避免 AI 亂編，這功能叫衛教問答）。回答會標一個等級，定義了四種：普通／緊急／不支援／**小心**。
- **現在的情況**：「小心」這個等級**在程式裡永遠產生不出來**——可能是當初設計留的伏筆，也可能是忘了做。Leo 想先問當初做這功能的組員再決定。
- **要決定**：「小心」等級要補上邏輯，還是刪掉？
- [x] 決議：**先跳過**——等當初做這功能的組員回覆 Leo 再定。（2026-07-09）

## 議程四：發表準備與分工（15 分鐘）

- [x] 決議：**先跳過**——等開始做發表的報告文件時再一起定。（2026-07-09）

### 會-14｜衛教資料誰負責放進去、誰把關？

- **現在的情況**：衛教問答的程式做好了，但**真正的衛教資料還沒放進去**——現在裡面只有 6 筆 AI 自己生成的測試資料（連出處日期都是假的）。需要有人執行入庫工具＋把關資料來源（只收官方可信來源，例如國健署網站）。
- **要決定**：指定一位內容負責人＋完成期限。
- [x] 決議：**先跳過入庫排程**——衛教資料目前存放在負責組員的 Supabase，之後從他的 Supabase 取得資料、搬到本專案的 Supabase。（2026-07-09）

### 會-15｜App 跟長輩要麥克風權限時說的那句話，大家看一眼

- **現在的情況**：長輩第一次用 App，iPhone 會跳出系統視窗問「允許金孫使用麥克風嗎？」——上面顯示的說明文字目前是 AI 代筆的：「**金孫需要麥克風，才能聽您說話。**」這句話會出現在所有長輩面前，全組過目確認或改掉。
- [x] 決議：**OK，照現值定稿**。（2026-07-09）

### 會-16｜分工（組織題）

## 2. 本專案特有審查重點

| 面向 | 檢查 |
| :--- | :--- |
| **決策合規（最重要）** | 改動是否觸碰 [00_決策清單](00_決策清單.md) 的 ➡ 帶會議項？**未決策的行為不可先寫死**；AI 產碼不得代填預設值（重規劃鐵律） |
| 命名 | elder_id／guardian_id 業務主鍵 vs line_user_id 外部識別碼永不混用；ID 全稱；save=upsert／record=append-only（AGENTS.md） |
| 三件套 | 新 store 必附 Protocol＋Pg＋Fake＋合約測試（D-34 教訓：Fake／Pg 語意分歧要靠合約測試抓） |
| 同意閘門 | **對話**路徑必過 ConsentGate（初次知情同意）；**出站推送不查同意**（✅ D-30 統一為不查，會-1）——新增出站訊息時不要再加同意檢查 |
| 危急路徑 | safety 相關改動不可降低「先落庫＋通知、後生成回覆」保證；fail-safe 依 D-31 |
| 隱私 | 新增 log 不得印對話原文／token；新資料表需標保留政策（D-14） |
| 組裝 | 物件建構只在三個組裝根；handler 內禁 new |

## 3. 審查流程（7 人協作）

- 每人一分支 → PR → **整合負責人合併 main**（CONTRIBUTING.md；main 受保護）。
- 「至少一位同儕審核」的分工——⚠ 建議併入今日會議「團隊分工確認」一起定（目前實務為整合負責人獨審）。
- PR 大小：>400 行 diff 或 10+ 檔考慮拆分（git-workflow.md）。

## 4. 重構紀律（適用即將展開的一次性重構）

1. **以文件為契約**：工項全部來自 16_WBS（各文件差距表彙總），不做清單外的「順手重構」。
2. **小步綠燈**：每個工項獨立 commit、可獨立 revert；跑完相關測試才進下一項。
3. **行為變更與結構變更分開 commit**（如 D-18 插座反轉是結構、D-31 L1 存底是行為——不混）。
4. 破壞性變更（API-1 信封＋v1）需三端同 PR 或緊鄰 PR，避免中間態壞掉。
5. 重構期間發現新決策點 → 先登記 00_決策清單問過再動手。

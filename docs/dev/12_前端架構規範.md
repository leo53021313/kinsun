⚠️ **`web/` 狀態層與 App 最根本的差異**（P1 地基，2026-07-30）：App 的 `SessionProvider` 是掛根節點的**單例**，一個分頁只有一份登入狀態；`web/` 的雙欄舞台要**左右兩欄同時各自登入**，這個形狀行不通，故改為工廠——`createSessionContext(role)` 每次呼叫產生一組獨立的 Provider／hook，持久化 key 分開（`kinsun_web_session_elder`／`kinsun_web_session_guardian`），互不干擾（`web/src/session/createSessionContext.tsx`）。持久化改用 `localStorage`：App 用的 `expo-secure-store` 在瀏覽器是空實作（`ExpoSecureStore.web.ts` 內容為 `export default {}`），沒有可搬的路；風險比照既有「admin 金鑰存 localStorage」例外同級（見 §8）——本前端只服務內部測試帳號。

## 4. 效能策略

- App：對講機鏈路（錄音→上傳→回覆→播放）為唯一關鍵路徑；音檔上限 env 化（D-26）；錄音採 expo-audio HIGH_QUALITY。
- 回覆音檔隨 WS binary 訊框直送（2026-07-30 延遲優化 C1）：`lib/replyAudio.ts` 把位元組寫成`Paths.cache/kinsun-reply/*.m4a` 再交給播放器，省掉「後端上傳 Supabase→App 再下載」兩趟網路。三個實作約束：①`expo-audio` 的 `AudioSource` **只吃 uri**，沒有吃記憶體位元組的路（iOS 雖認得 `data:audio/…`，但它內部就是寫進拿不到檔名、永不清理的暫存目錄，副檔名還靠 MIME 猜）；②副檔名**必須**是 `.m4a`，AVPlayer 推不出型別就載不起來；③`expo-file-system` v54 的舊 API（`writeAsStringAsync` 等）**執行期會拋**，只能用 class-based 的 `File`／`Directory`／`Paths`，而 `File.write` 吃 `Uint8Array`、是同步呼叫（回傳即已落盤，故 write→replace→play 無競態）。
  檔案自己收：cache 只在裝置儲存吃緊時才被系統回收。策略＝進畫面整個子目錄清掉重建＋環狀保留最新 3 個。⚠️ 刻意**不做「播完就刪」**——`playAndWait` 的保險逾時可能在播放器還在讀檔時就放行，留 3 個保證「正在播的那一個」永遠不在刪除範圍內。
  ⚠️ `lib/talkSocket.ts` **不可** import `expo-file-system`：它的離線可測性（`talkSocket.test.ts`不 import 任何 expo 模組）是刻意的設計，故寫檔以注入點 `writeAudio` 由 `talk.tsx` 提供，socket 只負責協定解析。落地失敗仍把訊框交出去（`audio_url` 留空）——字幕與分段資訊照樣有用。

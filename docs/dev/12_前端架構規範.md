⚠️ **`web/` 狀態層與 App 最根本的差異**（P1 地基，2026-07-30）：App 的 `SessionProvider` 是掛根節點的**單例**，一個分頁只有一份登入狀態；`web/` 的雙欄舞台要**左右兩欄同時各自登入**，這個形狀行不通，故改為工廠——`createSessionContext(role)` 每次呼叫產生一組獨立的 Provider／hook，持久化 key 分開（`kinsun_web_session_elder`／`kinsun_web_session_guardian`），互不干擾（`web/src/session/createSessionContext.tsx`）。持久化改用 `localStorage`：App 用的 `expo-secure-store` 在瀏覽器是空實作（`ExpoSecureStore.web.ts` 內容為 `export default {}`），沒有可搬的路；風險比照既有「admin 金鑰存 localStorage」例外同級（見 §8）——本前端只服務內部測試帳號。
⚠️ **`signIn` 收 `Omit<Session, "role">`**（P1 全分支審查 I3）：角色由工廠決定，呼叫端傳不進來。原本 `signIn` 收整個 `Session`，寫入用呼叫端的 `next.role`、讀取與清除卻用工廠的 `role`——在長輩 context 上傳成 `guardian`，畫面顯示長輩已登入、token 卻落在家屬鍵、長輩鍵是 null，重整之後兩欄對調。那是「兩欄互不干擾」唯一可被違反的路徑，而且看起來像永久故障，故從簽章拿掉讓它連傳錯都不可能（內部 `saveSession({ ...next, role })`，role 放展開之後）。

## 4. 效能策略

- App：對講機鏈路（錄音→上傳→回覆→播放）為唯一關鍵路徑；音檔上限 env 化（D-26）；錄音採 expo-audio HIGH_QUALITY。
- 回覆音檔隨 WS binary 訊框直送（2026-07-30 延遲優化 C1）：`lib/replyAudio.ts` 把位元組寫成`Paths.cache/kinsun-reply/*.m4a` 再交給播放器，省掉「後端上傳 Supabase→App 再下載」兩趟網路。三個實作約束：①`expo-audio` 的 `AudioSource` **只吃 uri**，沒有吃記憶體位元組的路（iOS 雖認得 `data:audio/…`，但它內部就是寫進拿不到檔名、永不清理的暫存目錄，副檔名還靠 MIME 猜）；②副檔名**必須**是 `.m4a`，AVPlayer 推不出型別就載不起來；③`expo-file-system` v54 的舊 API（`writeAsStringAsync` 等）**執行期會拋**，只能用 class-based 的 `File`／`Directory`／`Paths`，而 `File.write` 吃 `Uint8Array`、是同步呼叫（回傳即已落盤，故 write→replace→play 無競態）。
  檔案自己收：cache 只在裝置儲存吃緊時才被系統回收。策略＝進畫面整個子目錄清掉重建＋環狀保留最新 3 個。⚠️ 刻意**不做「播完就刪」**——`playAndWait` 的保險逾時可能在播放器還在讀檔時就放行，留 3 個保證「正在播的那一個」永遠不在刪除範圍內。
  ⚠️ `lib/talkSocket.ts` **不可** import `expo-file-system`：它的離線可測性（`talkSocket.test.ts`不 import 任何 expo 模組）是刻意的設計，故寫檔以注入點 `writeAudio` 由 `talk.tsx` 提供，socket 只負責協定解析。落地失敗仍把訊框交出去（`audio_url` 留空）——字幕與分段資訊照樣有用。
- web 端：內部工具，不做 code splitting 投資；admin 輪詢 5s＋隱藏暫停＋回前景補跑（✅ D-47 維持）。
- web 端對講機協定核心（`talk/talkSocket.ts`／`talk/talkGesture.ts`，P3 Task 3，2026-07-31）：自 `app/src/lib/` 原樣搬移，僅兩處必要的瀏覽器差異——①`connect()` 建立連線後補 `next.binaryType = "arraybuffer"`：瀏覽器 `WebSocket.binaryType` 預設 `"blob"`，而 `asArrayBuffer` 收到 `Blob` 會回 `null`，整個訊框（連字幕一起）被丟掉，是網頁端對講機完全沒有聲音的根因（React Native 的 binary 訊框一律是 `ArrayBuffer`，App 版不需要這行）；②`TalkFrame` 追加 `queued`（`{turn_id, position}`），對應後端容量閘門（P3 Task 1／2，見 06 §5）。
- web 端錄音、播放與 iOS 音訊解鎖（`talk/recorder.ts`／`talk/playback.ts`／`talk/audioUnlock.ts`，P3 Task 4，2026-07-31）：`writeAudio` 注入點在網頁端落地成 blob URL（`playback.ts::writeReplyAudio`），取代 App 版 `lib/replyAudio.ts` 寫入 `Paths.cache/kinsun-reply/*.m4a` 本地檔——這是 P3 Task 3 記載「留待後續任務」的第三處差異，本輪補上。三個瀏覽器特有的實作約束：①**容器格式各家不同**——`MediaRecorder` 錄出來 Chrome／Firefox 是 `webm/opus`、Safari 是 `mp4/aac`，後端不需處理（`services/asr/server.py::_decode_to_mono16k` 交給 ffmpeg 解容器，兩種都吃），但驗收必須跨三家瀏覽器實測、不可只測 Chrome；②**iOS Safari 音訊解鎖**（`audioUnlock.ts`，spec §12 R-1）——iOS 不允許在沒有使用者手勢的情況下播放音訊，而金孫回覆是 WebSocket 訊框抵達時才播、已脫離按下麥克風的手勢鏈，解法是在第一次使用者互動時經同一個播放器播一段極短的**同源靜態**無聲檔（`web/public/silent.wav`，掛在 `/demo/silent.wav`）；⚠️ 無聲檔**不可用 `data:` URI**——`security.py` 的 CSP `media-src 'self' https: blob:` 不含 `data:`，用 data URI 會被自家政策擋掉，症狀與「沒解鎖」一模一樣（皆是「iPhone 上只看得到字、聽不到聲音，桌機一切正常」），兩者混在一起會查到懷疑人生；③**資源必須釋放**——`recorder.ts` 的 `stop()` 與 `MediaRecorder` 建立失敗兩條路徑都要 `track.stop()`（不關的話瀏覽器分頁的錄音指示燈持續亮著）、`playback.ts` 的 `replace()`／`dispose()` 都要回收上一則 blob URL（只回收 `blob:` 開頭，分段續拉的 `https:` 簽章網址回收不得，否則瀏覽器不會自動清、一場展示下來會累積幾十 MB）。⚠️ 另記一則環境相容性瑕疵：`playback.ts::writeReplyAudio(bytes: Uint8Array)` 在 TypeScript 5.9 的 DOM 型別下 `tsc --noEmit` 直接報 `TS2322`——不帶泛型參數的 `Uint8Array` 是 `Uint8Array<ArrayBufferLike>`（緩衝區可能是 `SharedArrayBuffer`），而 `Blob` 建構子的 `BlobPart` 已收窄為要求 `ArrayBufferView<ArrayBuffer>`；修法是 `new Uint8Array(bytes)` 觸發「從 `ArrayLike<number>` 複製一份」的多載，保證回傳 `Uint8Array<ArrayBuffer>`，純型別修正、位元組量通常僅數十 KB 可忽略複製成本。
⚠️ **審查修正（2026-07-31）補三處易漏的邊界**：④`recorder.ts::stop()` 的軌道
關閉與狀態重置移進 `try/finally`——`MediaRecorder.stop()` 依規格在非
recording／paused 狀態呼叫會同步擲出 `InvalidStateError`（例如錄音途中來電／
Siri 介入／藍牙耳機被拔，系統把軌道搶走、`MediaRecorder` 已自行回到
inactive，長輩這時才放開按鈕），原本寫在 `await` 之後的清理碼會被整段跳過；

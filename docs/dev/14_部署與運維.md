## 1. 執行單元與啟停

`scripts/kinsun.sh` 統一管理九服務：`asr(8001) tts(8002) webhook(8000) scheduler rag_worker frontend(5173) app(8081) ngrok opik`——setsid 獨立進程組、log 至 `logs/<name>.log`、PID 至 `.run/<name>.pid`。

⚠️ **排程跑在兩個程序**：`scheduler`（`python -m kinsun.cron`）與 `rag_worker`（`python -m kinsun.rag.worker`，只有 RAG 週更）。兩者的 job 清單同出於 `cron/registry.py`，後台 `GET /admin/jobs` 讀全集並在每列標出 `owner`——owner 的字面就是這裡的服務名，看到逾期告警可直接 `kinsun.sh restart <owner>`。

⚠️ 排程器改名的部署後果（2026-07-27）：`kinsun.scheduler` 已更名 `kinsun.cron`，systemd unit 的 ExecStart 隨之改動。**DGX 上已安裝的那份不會自動更新**——升級後第一次重啟排程器前，必須重新複製：
`cp deploy/kinsun-scheduler.service ~/.config/systemd/user/ && systemctl --user daemon-reload`。
未複製前排程器仍在跑（模組已載入記憶體），但一重啟就 ModuleNotFoundError。unit 檔名與服務名維持 `kinsun-scheduler`／`scheduler` 不變。

| 指令 | 行為 |
| :--- | :--- |
| `scripts/kinsun.sh start|stop|restart [服務]` | 全部或指定服務（如 `restart app`） |
| `scripts/kinsun.sh status` | PID 存活檢查；`app` 那列即 Expo Go 要掃的 `exp://` 位址 |

**App（Expo dev server）**：**預設走 tunnel**（✅ 團隊測試手機與 DGX 從不在同一個 Wi-Fi）——Expo 經 `exp.direct` 反向隧道對外，任何網路的手機都連得到，`status` 顯示形如 `exp://xxx-anonymous-8081.exp.direct` 的對外位址供 Expo Go 掃描（iOS 用相機、Android 用 Expo Go 內建掃碼）。

- **位址從哪來**：Expo 只在互動終端印 QR／網址，背景啟動時 log 裡一個字都沒有——`status` 改問 Metro 的 manifest（`launchAsset.url` 的 host 即手機實際要連的位置），tunnel 與 LAN 兩種模式都準。
- **tunnel 偶發失敗**：`exp.direct` 端會出現 `remote gone away`，且失敗時 Expo 整個退出、連 Metro 都不留。故啟動時會等到 tunnel 就緒才算數，**失敗自動重試一次**（實測命中率頗高）。兩次都失敗時另有明確提示。
- **區網模式**：`KINSUN_EXPO_TUNNEL=0`（僅同網段可用、啟動較快）。此模式以 `REACT_NATIVE_PACKAGER_HOSTNAME` 釘住區網 IP——DGX 有 docker(172.17.x)／Tailscale(100.x) 等多張網卡，不釘住則 Expo 可能挑錯介面、手機抓不到 bundle。

to-be：API 改多 worker 啟動（✅ D-20）。

### 排程器常駐（2026-07-26 全流程模擬實測後新增）

`scripts/kinsun.sh` 是**手動**啟停，而夜間批次排在凌晨 3:05——實測發現 `daily-consolidation`
自 2026-07-13 起就沒有自動跑過（13 天、287 輪對話沒進長期記憶、家屬看不到任何摘要）。
故交付 systemd user unit（這台 DGX 已 `Linger=yes`，不必登入即可開機自動啟動）：

```bash
mkdir -p ~/.config/systemd/user
cp deploy/kinsun-scheduler.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now kinsun-scheduler
journalctl --user -u kinsun-scheduler -f      # 看日誌
```

**已於 2026-07-27 00:01 安裝並啟用**（安裝當下 `scheduler_state` 全部是最新的，補跑量為零）。

`kinsun.sh` 已認得這個 unit，三處行為都對齊了：

| 指令 | systemd 常駐時的行為 |
| :--- | :--- |
| `start [scheduler]` | 偵測到 unit 在跑就**跳過**，不會起出第二個，並印出 systemctl 管理指令 |
| `status` | scheduler 那列顯示 `SYSTEMD` ＋ 真正的 MainPID ＋ 心跳年齡（若沿用舊邏輯會顯示成 STOPPED——那是說謊，正是本次事故的病灶） |
| `dump scheduler` | 訊號送給 unit 的 MainPID（unit 直接跑 venv python，不經 uv 外殼） |

日常仍用 `kinsun.sh status` 觀察即可；要重啟排程器改用
`systemctl --user restart kinsun-scheduler`（`kinsun.sh restart scheduler` 只會跳過）。

⚠️ **停用前先讀「補跑的爆量」**（見下）：停久了再啟用，積欠的 job 會補跑一次。

### 補跑的爆量（啟動前必看）

排程器有補跨語意（`scheduler.py::_claim_if_due`）：上次執行時間的下一個 cron 時刻早於
現在就會**立刻補跑一次**。停擺很久之後啟動，等於一次補完積欠的 job：

| job | 補跑會發生什麼 | 護欄 |
| :--- | :--- | :--- |
| `daily-greeting` | 對當天還沒被問候的長輩送「早安」 | ✅ 補跑時限 240 分（2026-07-26 新增）——晚超過就跳過，不會在夜裡發早安 |
| `inactivity-care` | 對久未互動的長輩推播關懷 | ✅ 同上 |
| `schedule-dispatch` | 派送到期提醒 | ✅ 既有的 `SCHEDULE_DISPATCH_WINDOW_SECONDS=90`（過期就不發） |
| `daily-consolidation` | 對**全部**長輩跑整理＋摘要＋反思 | ⚠️ 無護欄：會一次打大量 Gemini。測試期的免費層額度會瞬間見底 |
| `news-crawl`／`news-cleanup`／`observability-cleanup` | 抓新聞、清資料 | 無對外影響 |

想完全放棄補跑（只恢復日常運作），啟動前把 `scheduler_state.last_run_at` 校正到現在即可。

### 排程器「活著但停止運作」

實測抓到兩次：程序在、`status` 顯示 RUNNING、CPU 幾乎零，但每分鐘該跑的派送停了數小時。

**根因（2026-07-26 23:20 定案，取代先前的推論）**：**浮點數等值比對**。
`try_claim` 原本用 `WHERE last_run_at = %s` 做樂觀鎖，而 Supabase 這條連線的
`extra_float_digits = 0`——PostgreSQL 只用 **15 位有效數字**輸出 `double precision`。
實際儲存的 `1785045932.084225` 讀到用戶端變成 `1785045932.08422`，**是另一個 double**：

1. `get_last_run` 讀回被截斷的值
2. `try_claim` 拿它去比對，永遠對不上
3. 該 job **從此再也認領不到**，直到有人手動改資料庫

現場實證：`schedule-dispatch` 卡在 14:05、`daily-consolidation` 卡在 13.8 天前；排程器
每分鐘照掃、心跳正常，只是每一輪都認領失敗。**重啟六次完全無效**——壞掉的值在資料庫裡，
不在記憶體裡。每個 job 各自死在「它的時間戳剛好需要 16 位以上有效數字」的那一刻，
所以是隨機、逐一、無聲地死去，這也是為什麼各 job 停擺時間點全都不一樣。

已改為範圍比對（`last_run_at <= expected + 1ms`，見 `cron/state.py`），雙 worker
防重語意不變（贏家把值推到 now，輸家條件不成立）。合約測試以「讀回值略小於實際值」
涵蓋此情境，Fake 與 Pg 兩個 adapter 同時跑。

> ⚠️ 先前版本記載的根因（「連線對端消失、psycopg 無限期等待」）**是錯的**。當時的
> `ss -tnp` 證據顯示 `Recv-Q` 有積壓，那代表「資料到了沒人讀」而非「對端不見了」，
> 推論並未被證實。`db.py` 的 TCP keepalive 仍保留（防的是另一類真實故障），但它
> **不是**這次停擺的解方。

**怎麼確認它真的活著**（三層，由淺到深）：

| 手段 | 看什麼 | 分得出什麼 |
| :--- | :--- | :--- |
| `scripts/kinsun.sh status` | scheduler 那列的「心跳 N 秒前」 | 行程活著 vs 迴圈凍住（PID 存活無法分辨，2026-07-26 就是被它騙了七小時） |
| `GET /api/v1/admin/jobs` | `is_overdue`、`meta.warnings` | 迴圈在跑但**認領不到工作**（本次事故只有這一層看得出來） |
| `scripts/kinsun.sh dump scheduler` | 送 SIGUSR1，全執行緒堆疊寫進 `logs/scheduler.log` | 真的卡住時，卡在哪一行 |

心跳檔路徑由 `SCHEDULER_HEARTBEAT_PATH` 決定（`kinsun.sh` 啟動時會覆寫成絕對路徑）。
`dump` 不需要 root——DGX 的 `ptrace_scope=1` 讓 py-spy 必須 sudo，事故當下因此拿不到
任何 Python 堆疊，faulthandler 由行程自己印，補的就是這個洞。

排程器另有看門狗：tick 停止推進超過 10 分鐘就自我了結，交給外部監管重啟。
⚠️ **純用 `kinsun.sh` 啟動時沒有監管者**，看門狗結束後排程器就停著——`status` 會誠實
顯示 STOPPED（而非以前那種騙人的 RUNNING），但需要人工 `restart scheduler`。
要自動復活請改掛 systemd（見上），且別讓兩邊同時啟動同一個排程器。

## 3.5 資料庫連線總量（✅ 庚-26／A-55）

⚠️ **上限是 15 不是 60（2026-07-28 實測更正）**：本專案的 `DATABASE_URL` 主機名為
`aws-1-ap-southeast-1.pooler.supabase.com:5432`——**那是 Supabase 連線池（session mode）
的 5432 埠，不是直連**。session mode 每專案上限 `pool_size: 15`，爆掉時的錯誤訊息是
`FATAL: (EMAXCONNSESSION) max clients reached in session mode - max clients are limited to pool_size: 15`。
先前本節寫的「直連約 60 條」是未驗證的推論，據以估算的餘裕並不存在。

每進程開一個連線池，上限 `DATABASE_POOL_MAX_SIZE`（預設 5）。總量公式：

```
（WEB_WORKERS ＋ scheduler 1 ＋ rag_worker 1）× DATABASE_POOL_MAX_SIZE ≤ 15
```

- 預設（WEB_WORKERS=2）滿載即 4×5＝**20 條 > 15，已經超賣**——平時靠各池 `min_size=1`
  沒同時長到上限才相安無事，負載一升高或多開一個 CLI 就爆線。
- 2026-07-28 實證：webhook（2 worker）＋scheduler＋rag_worker 常駐時，
  `python -m kinsun.rag.ingest` 連一條都借不到、每次連線立即 `EMAXCONNSESSION`。
  當時的解法是暫停閒置的 `rag_worker`（`RAG_REFRESH_ENABLED=false` 時它不做事卻佔一份池）
  讓出額度給 CLI，跑完再 `kinsun.sh start rag_worker` 復原。
- 零星加項：記憶整理 CLI、RAG ingest、備份腳本各短暫 +5——**在 15 的天花板下這是奢侈品**，
  跑長時間 CLI 前先確認要讓誰出來。
- ⚠️ 不可為了拉高上限改用 6543 交易池化埠：認證節流（庚-08）依賴 advisory lock，
  交易池化下 session 級鎖語意不成立。
- 爆線症狀＝連線被拒（API 500 或 CLI 起不來），不是變慢——排障時先想到本公式。
- ➡ 待議：`DATABASE_POOL_MAX_SIZE` 是否調降為 3（4 進程×3＝12 ≤ 15），
  或改連真正的直連主機（`db.<ref>.supabase.co`）取得較高上限。尚未拍板。

### RAG 週更 Runbook

- `RAG_REFRESH_ENABLED=true` 且 `RAG_REFRESH_CRON=0 3 * * 0` 時，`rag_worker` 每週日 03:00 建候選版。
- `rag_worker` 使用專用最小設定，只需要 `DATABASE_URL`、`DATABASE_POOL_MAX_SIZE`、`GEMINI_API_KEY`、`TIMEZONE`、`SCHEDULER_TICK_SECONDS` 與 RAG 設定；不應因 LINE、LIFF、ASR、TTS 或音檔設定缺漏而無法啟動。
- `RAG_EMBEDDING_TIMEOUT_SECONDS=60` 限制單次外部呼叫；`RAG_EMBEDDING_BATCH_SIZE=20` 限制同步批次，避免巨型頁面造成無限等待。ANSWER 才建立向量，DISCOVERY 只留文件 membership 與稽核。
- `scripts/kinsun.sh status` 確認 `rag_worker` 存活；失敗原因看 `logs/rag_worker.log` 與 Admin「衛教 RAG 索引」。
- 無 active release 或最近更新失敗時 Admin 會告警；舊 active 仍服務，不得直接改 DB status。

## 工程觀測（Opik）服務

工程／LLM 深度視角的觀測後端，自架於 DGX，**不進版控**（外部基礎設施，比照資料庫）。

- **服務位置**：`/home/leo29/opik`（git clone，非 kinsun repo）；容器名 `opik-opik-*`。
- **啟停**：`cd /home/leo29/opik && NGINX_PORT=5273 SERVER_ADMIN_PORT=8091 PYTHON_BACKEND_PORT=8010 ./opik.sh`（啟動）／`./opik.sh --stop`／`./opik.sh --clean`（清資料）。⚠️ **三個埠必須釘**，不可跑裸 `./opik.sh`：Opik 的 nginx 預設算出 **5173**＝本專案前端開發伺服器的埠（`kinsun.sh` 的 `[frontend]=5173`），裸跑會佔走前端的埠、且 UI 不在 5273（2026-07-25 實際踩過，當時是為了避開公開隧道而繞過 kinsun.sh）。這三個值與 `kinsun.sh` 的 `_opik_backend_start` 一致。也可經 kinsun.sh 一併管理（見下「遠端檢視」——`opik` 服務會連後端 docker 一起起停）。
- **連結顯示**：`scripts/kinsun.sh status`／`start` 結尾會印出 Opik 觀測後台連結（由 `OPIK_URL_OVERRIDE` 去 `/api` 推得，預設 `http://localhost:5273`）、服務是否在跑、以及 `OPIK_ENABLED` 旗標。
- **kinsun.sh 管理（服務名 `opik`＝後端 docker ＋ 公開隧道，複合服務）**：已納入 `START_ORDER`／`STOP_ORDER`，隨 `start`／`stop`／`restart`（全部）一起起停；亦可單獨 `start/stop/restart opik`。
  - `start opik`：先確保**後端 docker**（`./opik.sh`）起來（冷啟等 5273 健康，約 30–60 秒），再開 Cloudflare Quick Tunnel（cloudflared，已裝於 DGX，aarch64）；隧道起來後會**等網址真的寫進 log**（最多 20 秒）才印 `Opik 隧道就緒：<網址>`。cloudflared 約需 3 秒才跟 Cloudflare 要到臨時網域，不等的話 `start` 結尾那張 status 表只印得出「啟動中…」（2026-07-26 修）。
  - `stop opik`：先關隧道（pidfile），再由 `_post_stop_opik` 停後端 docker（`./opik.sh --stop`）。後端非單一 PID，故特別處理（`is_running(opik)`＝後端 :5273 是否在；隧道另用 pidfile 判斷）。
  - `status`：`opik` 那列 STATE＝後端狀態，PORT/HEALTH 欄顯示「後端 :5273 | 隧道 <當前 `*.trycloudflare.com` 網址>」（網址每次重啟會變，讀 `logs/opik.log` 最後一次啟動後的區段；網址尚未寫進 log 時最多再等 8 秒，寧可 status 慢幾秒也不印無法點的「啟動中…」）；另有一行本機後台連結＋`OPIK_ENABLED` 旗標。
  - ⚠️ **Quick Tunnel 限制**：網址每次重啟都不同；且短時間反覆建立會被 Cloudflare 匿名隧道**限流**（新子網域暫時無法解析／不可達）——heavy start/stop churn 後稍等再試即可，這是 Cloudflare 端行為、非本專案缺陷。要固定網址＋認證＋不被限流，需正式版 Named Tunnel＋Access（待有 CF 網域）。
  - ⚠️ **安全**：Quick Tunnel 免網域但【公開、無認證】——Opik 自架版本身無登入，等於任何拿到網址者可讀所有 trace。**注意 `OPIK_ENABLED` 現預設為 `true`**（連得到 Opik 就送 trace），故真實對話內容預設會進 Opik；**接真實長輩資料時，切勿開啟公開隧道**（要遠端檢視改用下方 Named Tunnel＋Access）。純 demo/測試資料臨時開無妨。
  - **正式版（有 Cloudflare 網域時）**：改用 Named Tunnel＋Cloudflare Access（Email/Google 登入），提供固定子網域＋認證。需 `cloudflared tunnel login`（互動授權本人 CF 帳號）後建 tunnel／DNS／Access 政策。目前無網域，故先用 Quick Tunnel。
  - ngrok（webhook :8000）留給 App API（見 §1；`app/.env` 的 `EXPO_PUBLIC_API_URL` 指向該網域），不與 Opik 隧道互搶；免費 ngrok 只有一個網域，故 Opik 不共用 ngrok。
- **對外埠**：僅前端 `5273`（UI＋API 反代）；資料庫（clickhouse/mysql/minio/redis/zookeeper）預設不對外，與 kinsun（postgres 5433／uvicorn 8000）零衝突。
- **資料本體**：docker named volumes（rootless：`~/.local/share/docker/volumes/opik-opik_*`）；**要備份的是這些 volume**，服務程式碼可重新 clone。
- **ARM64**：核心映像原生 aarch64（已驗證）；選配 Guardrails（PII/主題，英文模型、吃 GPU）預設關閉且無 arm64 映像，需用再自 build。

### 環境變數（OPIK_ 前綴；app 端 client）

| 變數 | 預設 | 說明 |
| :--- | :--- | :--- |
| `OPIK_ENABLED` | `true` | 總開關；預設開送 trace，連不到 Opik 服務會安靜降級為 no-op，但**會定期重探並自動接回**（見 `OPIK_REPROBE_INTERVAL_SECONDS`）。開發機不想跑 Opik 設 `false` 明確關（設 false 則一次都不探） |
| `OPIK_URL_OVERRIDE` | `http://localhost:5273/api` | 自架 Opik 後端位址（搬遷只改此值） |
| `OPIK_WORKSPACE` | `default` | 自架工作區 |
| `OPIK_PROJECT_NAME` | `kinsun` | Opik UI 內的分組 |
| `OPIK_PING_TIMEOUT_SECONDS` | `2.0` | 單次連線探測的逾時；在此秒數內判定 Opik 是否可達，連不到即降級 no-op，避免無服務環境（開發機／CI）被連線錯誤洗版 |
| `OPIK_REPROBE_INTERVAL_SECONDS` | `60.0` | 降級後的重探間隔；每隔這麼久重探一次，Opik 起來就自動接回。⚠️ **不要為了省事調成 0**——`is_enabled()` 在對話熱路徑上每個 span 都會走到 |

> **啟動順序與觀測（2026-07-27 事故）**：`START_ORDER` 讓 `opik` **最後**才起（冷啟 30–60 秒），`STOP_ORDER` 讓它**第一個**停，所以 `kinsun.sh restart`（全套）時 webhook 必定早於 Opik 啟動。先前首探失敗即永久停用，該行程整段壽命的長輩對話一筆都不會進 Opik——`restart webhook`（單一服務）反而正常，因為那時 Opik 沒被動到。現已改為定期重探自動接回，`kinsun.sh` 的順序**不需要**跟著改。判讀方式：`logs/webhook.log` 出現「工程觀測暫時停用」是正常過渡，之後應在一個重探間隔內出現「Opik 工程觀測已啟用」；若始終沒有那行，才是 Opik 真的沒起來。

> **安全**：接真實長輩資料時，Opik 自架版預設幾無存取控制；共用或上線前須先處理存取控制與去識別化。

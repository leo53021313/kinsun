# ADR-004: 知識圖譜（Neo4j）移除與四用途拆解

> **狀態:** 已接受 | **日期:** 2026-07-08 | **決策者:** Leo（D-17，重新審視後維持移除）

## 1. 背景與問題

- **上下文**: 架構圖原規劃「知識圖譜」節點（個資／家庭關係／用藥／事件時間軸），由 Mem0 graph 模式＋Neo4j Aura 承載。
- **問題**: 2026-06-29 MEM-UP 實測發現 **mem0 2.0.10 開源版沒有 graph 功能**——`MemoryConfig` 無 `graph_store` 欄位，Neo4j 設定被靜默忽略。圖譜從未真正運作，留著的是死設定＋未使用依賴。
- **重要脈絡**: 2026-07-08 Leo 對當初移除提出疑慮，經完整原委重審後**重新拍板維持移除**（本 ADR 即為此留痕）。

## 2. 考量的選項

- **維持移除**：四用途已各有接盤（見下表），真圖遍歷 v1 無場景。
- **重啟為獨立項目**：自建 Neo4j 層（獨立於 mem0）做家庭關係網／事件圖查詢；工程量大，8/20 前不現實。

## 3. 決策

**選擇**: 維持移除。原「知識圖譜」四用途的歸宿：

| 用途 | 接盤者 | 程式碼歸屬 |
| :--- | :--- | :--- |
| 對話個人化檢索 | Mem0 v1.1 語意檢索（ADR-003） | **Mem0 套件內建**；專案只有薄包裝 `memory/longterm/store.py` |
| 穩定事實每輪浮現 | Mem0 檢索＋事實注入層 | **混合**：語意檢索是 Mem0 內建；「每輪固定健康查詢」（`store.py:15`）與事實層（`medications/facts.py`、`appointments/facts.py`、`memory/recall.py`）是**專案自寫**、直查 Postgres 不經 Mem0 |
| 精確結構化查詢（回診時間等） | Postgres 表 `medications`／`appointments`＋提醒 jobs | **專案自寫**，與 Mem0 完全無關 |
| 家庭關係 | `accounts`／`elder_guardians` 表 | **專案自寫**，與 Mem0 完全無關 |

**理由**: 提醒引擎要的是精確時間查詢，關聯表比圖／向量可靠；真圖遍歷場景 v1 不存在（YAGNI）。

## 4. 後果

- **正面**: 少一個雲服務依賴；提醒引擎更單純可靠。
- **負面**: 若提案簡報仍把「知識圖譜」當賣點，發表敘事需同步修正（提醒：檢查簡報）。
- **重新評估觸發**: 出現真・圖遍歷需求（多代家庭網絡、跨事件因果查詢）時，以獨立自建 Neo4j 層另案評估。

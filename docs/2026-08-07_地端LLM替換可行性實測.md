# 地端開源 LLM 替換 Gemini 可行性實測（2026-08-07）

> **一句話**：`qwen3.6:35b-a3b` **關掉 thinking** 之後，工具調用與 `gemini-3.5-flash-lite` 打平（6/10 vs 7/10，差距在雜訊內），單次延遲也打平（1.48s vs 1.39s）——地端從「不可行」變成「值得認真評估」。但**這不足以支持現在就換**，缺的驗證列在 §6。
>
> **問題來源**：Leo 問「有沒有開源地端模型能力比 gemini-3.1／3.5-flash-lite 強」，用途為對話與工具調用；動機為**降低語音對話延遲**。
>
> 量測環境：DGX Spark（GB10，121GB 統一記憶體）｜Ollama 0.30.10｜分支 `Leo`｜**未改動任何程式碼**
> 量測腳本：session scratchpad 之 `measure_latency.py`／`trace_regression.py`／`clean_baseline.py`／`bench_v2.py`／`bench_gemini.py`——**未固化入 repo**

## 1. 先更正一個流傳中的錯誤數字

`docs/2026-07-26_延遲優化報告.md` 給隊友的第一行寫著「14.2 秒縮短到 6.6 秒」。**6.6 秒從來不是生產環境的數字。**

從觀測庫（`replies.round_trip_ms`）取真實生產資料，剔除 07-29／07-30 兩個自動化測試日（07-29 有 160/192 筆 TTS 延遲為 0ms，是假 TTS）：

| 日期 | 端到端 p50 | 備註 |
| :--- | ---: | :--- |
| 07-26 | **11,668ms** | 報告寫作當天。報告聲稱 6,590ms |
| 07-27 | 10,912ms | |
| 07-28 | 13,453ms | |
| 08-01 | 10,913ms | |
| 08-07 | 11,016ms | **比報告當天略快** |

那份 6.59 秒是 n=5、同一測試者、同時段相鄰執行的 A/B 對照組。報告 §2 自己註明過「生產起點是 p50 16.8 秒（高於對照組的 14.2 秒）」——作者知道對照組跑得比生產快，但那句話寫在腳註，而「6.6 秒」寫進了給隊友看的第一行。

**正確的認知：這半個月端到端是 11.7s → 11.0s，持平略好，沒有退步。**

## 2. agent LLM 沒有變慢，但變成了另一種東西

| 日期 | agent p50 | 輸入 token | 輸出 token | 回覆字數 |
| :--- | ---: | ---: | ---: | ---: |
| 07-26 | 4,281ms | 3,991 | **32** | 41 |
| 07-27 | 2,907ms | 4,823 | **306** | 30 |
| 07-28 | 5,785ms | 7,458 | **712** | 31 |
| 08-01 | 3,660ms | 6,681 | 759 | 34 |
| 08-07 | 3,899ms | 8,807 | **879** | 29 |

兩件事同時發生，都指得出確切位置：

**（a）輸出 token 在 07-27～07-28 兩天內從 32 跳到 712，翻 22 倍，而回覆字數反而從 41 掉到 31。** 多出來的七百個 token 一個字都沒唸給長輩聽——那是思考。對應 `src/kinsun/llm.py:342` 的 `TOOL_TURN_THINKING_LEVEL = "MEDIUM"`，與 2026-07-27「不設 thinking 工具形同失效」的診斷同一天。

**（b）輸入 token 從 3,991 漲到 8,807，翻 2.2 倍**（07-25 話題新聞工具、之後的交通工具、08-05 人設，每加一段每輪都重付）。

但 agent p50 從 4,281ms 變 3,735ms（最近兩個真實日）——**反而快了**，因為 Gemini 的 prefill 便宜，膨脹主要落在輸入側。

> ⚠️ 若用「最近 100 筆」計算會得到 6,097ms，那是錯的：那 100 筆有七成落在 07-29／07-30 兩個壓測日。

## 3. 核心實測：同一套題、同一份提示詞、同樣 13 個工具

題目 10 題、真實 `agent.SYSTEM_PROMPT`（1,861 字元）、13 個真實 `ToolSpec`、5,500 字元情境。

| 配置 | 工具正確率 | 單次 p50 | 平均輸出 |
| :--- | :---: | ---: | ---: |
| **gemini-3.5-flash-lite**（thinking MEDIUM＝生產設定） | **7/10** | **1.39s** | — |
| **qwen3.6:35b-a3b（thinking 關）** | **6/10** | **1.48s** | 23 tok |
| qwen3.6:35b-a3b（thinking 開） | 6/10 | **23.34s** | 1,216 tok |

### 逐題對照

| 題目 | Gemini | qwen（thinking 關） |
| :--- | :--- | :--- |
| 今天天氣好嗎？我在台南 | ✅ get_weather 1.06s | ✅ get_weather 1.50s |
| 提醒我明天早上八點吃血壓藥 | ✅ create_schedule 3.99s | ❌ 沒叫工具 |
| 附近有沒有藥局？ | ✅ search_nearby_places 1.30s | ✅ search_nearby_places 1.52s |
| 我下禮拜三要回診，幫我記一下 | ❌ 沒叫工具 | ❌ 沒叫工具 |
| 血壓高要注意什麼？ | ✅ health_education_rag 0.99s | ✅ health_education_rag 1.61s |
| 最近有什麼新聞？ | ✅ get_news 0.89s | ✅ get_news 1.34s |
| 我孫子昨天打電話來，講了好久 | ✅ 不叫工具 2.34s | ✅ 不叫工具 1.44s |
| 公車幾點到？我在台南火車站 | ❌ 沒叫工具 | ❌ 沒叫工具 |
| 我明天早上的藥有哪些？ | ❌ 沒叫工具 | ✅ list_schedules 1.37s |
| 腰痠背痛要看哪一科？ | ✅ health_education_rag 1.29s | ❌ 沒叫工具 |

### 三個結論

**（1）thinking 對 qwen 沒有幫助，對 Gemini 才有。** qwen 開不開 thinking 都是 6/10，但延遲從 1.48s 變成 23.34s（15.8 倍），且 3 題吐滿 2,048 token 上限仍未叫工具。**Gemini 的經驗不可平移**——07-27 那次「開 thinking 救回工具調用」是 Gemini 的性質，不是通則。

**（2）兩個模型都叫不出 `get_bus_arrival`。** 同一題、兩個獨立模型、同時失敗——**這是提示詞問題，不是模型問題**。這是本次實測的意外收穫，與換不換模型無關，值得單獨修。

**（3）Gemini 現在漏 `list_schedules`。** 「我明天早上的藥有哪些？」Gemini 沒叫工具、qwen 叫對了。這是生產環境**現在就有**的漏洞。

## 6. 這份實測**不足以**支持現在就換（五個缺口）

| 缺口 | 為什麼重要 |
| :--- | :--- |
| **每題只跑一次** | 6/10 vs 7/10 是 n=1 的單次抽樣，差距不具統計意義。要判定優劣需每題重複 5–10 次 |
| **只測了工具迴圈的第一段** | 測的是「決定叫哪個工具」。生產的 agent p50 3.7s 涵蓋 leg1＋工具執行＋leg2（拿到結果後生成回覆）。**全輪往返沒有測過** |
| **情境字串每題相同，prefix cache 幾乎全命中** | 生產每輪情境都不同（記憶、事實、RAG 都在變）。冷快取 prefill 是 2,603 tok/s，6,800 token 要 2.6 秒——**每個 leg 都要付**。真實 prefill 成本比本次實測高 |
| **完全沒測回覆品質** | 只測工具選擇。台灣用語、口語程度、30 字上限、人設語氣、不洩漏系統設定——一項都沒驗。`evals/` 那套必須對地端重跑 |
| **沒測併發與 GPU 互搶** | `TURN_CONCURRENCY_LIMIT=2`，而地端 LLM 會與 CosyVoice 搶同一顆 GB10。07-26 報告 §5 已實測過三個 CosyVoice 互搶會**更慢**（5.83s→8.26s），同樣物理適用於 LLM |

## 7. 建議的下一步（依投報比排序）

| # | 項目 | 為什麼排這個位置 | 成本 |
| :-- | :--- | :--- | :--- |
| 1 | **修 `get_bus_arrival` 叫不出來** | 兩個模型同時失敗＝提示詞問題，與換模型無關，是現在就在漏的功能 | 小 |
| 2 | **修 `list_schedules` 漏叫** | 生產環境現有漏洞，qwen 叫得出來代表題目本身沒問題 | 小 |
| 3 | **補齊 §6 的全輪往返實測** | 決定換不換的關鍵數字現在還不存在。只測一半的實測比沒測更危險 | 中 |

**不建議現在做**：直接把對話大腦切到地端。§6 五個缺口有三個是「可能推翻結論」等級。

## 8. 對原始問題的回答

> 「有什麼開源地端模型的能力比 gemini-3.1／3.5-flash-lite 強？」

以**工具調用**論，在這台 DGX Spark 上：**沒有比它強的，但 `qwen3.6:35b-a3b` 關掉 thinking 後與它打平**，而且省下全部 API 配額、資料不出境。

以**延遲**論（原始動機）：**單次呼叫打平**（1.48s vs 1.39s），但全輪往返未測、prefill 成本未計、GPU 互搶未評估——**目前沒有證據支持「換地端會更快」**。

真正的降延遲空間不在模型跑在誰家，而在：端到端 11 秒裡 agent 只佔 3.7 秒，TTS 與其餘往返才是大頭。

# 帳號欄位收縮與觀測後台換鍵（階段 1D）實作計畫

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 擴張—收縮遷移的收縮步：退役 `elders.line_user_id`／`guardians.line_user_id` 欄位與雙寫；同時修正觀測後台在 1B 之後殘留的舊鍵查詢（feed／timeline 仍以 `line_user_id` JOIN，新資料在後台看不到，且 SQL 直接引用即將退役的欄位）。

**Architecture:** 先修觀測（T1）再退役欄位（T2）——順序不可反，因為觀測 SQL 引用 `elders.line_user_id`，欄位先退會直接 500。觀測後台的人物鍵統一為 `elder_id`；觀測五表本身維持通道識別（external_id），時間軸的語音分支改經 `channel_bindings` JOIN 映回本人（不補欄、不改 record 簽名——貫徹 spec §4.1.5 的 YAGNI 決定）。

**Tech Stack:** 同前；前端另需 `cd frontend && npm run typecheck && npm run build:admin` 驗證。

## Global Constraints

- 同 1A–1C 計畫。設計源頭：spec §4.1(1)「欄位資料遷入本表後退役」。
- 共用真庫已完成 1A 回填與 1B 遷移（`KINSUN_IT=1` 測試跑過 `ensure_schema`），因此引用退役欄位的歷史回填 DDL（`CHANNEL_BINDINGS_BACKFILL_DDL`、`SESSION_KEY_MIGRATION_DDL` 的三段 UPDATE）功成身退、一併移除；若未來出現「尚未跑過回填的舊庫」屬人工遷移範疇（repo 無 migration 工具，見 06_DB_Schema §3 ⚠ E-04）。

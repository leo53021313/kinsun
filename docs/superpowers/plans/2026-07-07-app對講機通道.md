# App 對講機通道與家屬雙認證（階段 3）實作計畫

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** App 通道後端成形：`POST /api/app/turns` 對講機語音 API（上傳錄音 → 既有 ASR→LLM→TTS 管線 → 同一回應回文字＋回覆音檔 URL），家屬 REST 改「App token／LIFF idToken」雙認證。

**Architecture:** 對講機路由是 `channels/line/` 之外的第二通道 adapter（`channels/app/turns.py`）：HTTP 請求正規化成 `InboundMessage(Channel.APP, external_id, "audio", …)` 進**既有 `dispatch`**——閘門（同意複核）、危急偵測、記憶、觀測、語音回覆（`VoiceReplyDelivery` 上傳 Supabase 取公開 URL）全部重用；`reply`／`reply_voice` 改為收集器（collector），dispatch 結束後轉成 JSON 回應。家屬 REST 認證收斂到「`guardian_id` 中心」：`AccountService` 拆出 `create_elder_for_guardian`／`elders_of_guardian` 核心方法（by-line 版變薄包裝），`web/api.py` 的 `current_guardian` 依賴改回傳 `GuardianAuth(guardian_id, line_user_id)`，先查 App token（本地、快）、miss 再走 LIFF 驗證（打 LINE API）。

**Tech Stack:** 同前，零新依賴。上傳走 **raw body**（`Content-Type: audio/m4a`、body＝音檔 bytes）——實查 `python-multipart` 不在依賴中，raw body 免加套件且客戶端更簡單（fetch 直接帶 blob）。

## Global Constraints

- 同前計畫。設計源頭：spec §4.3。
- 對講機請求上限 10MB（413）；`content_type` 固定 `audio/m4a`（expo-audio 預設，與 LINE 路徑一致）。
- 同意撤回的長輩：token 仍在但閘門擋下 → 403 `consent_revoked`（token 不代表同意，撤回即時生效）。

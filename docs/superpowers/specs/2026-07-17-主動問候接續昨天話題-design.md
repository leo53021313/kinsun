## 背景與動機

主動問候走的記憶組裝路徑，與長輩主動開口時**完全相同**，沒有走簡化捷徑：

```
agent.proactive → _envelope(elder_id, query) → SessionMemory.assemble(elder_id, query)
                                                 ├─ long_term.search(elder_id, query)   ← 問題在這
                                                 ├─ short_term.recent(elder_id)          ← 早上必為空
                                                 └─ 事實提供者各段
```

問題不在「有沒有查記憶」，而在**拿什麼去查**。

### 問題 1：檢索關鍵字是萬年不變的 intent 字串

`proactive` 直接把 intent 當檢索 query（`agent.py:101`）：

| 推播 | 當成檢索關鍵字的字串 |
| :--- | :--- |
| 早安問候 | 「早安問候，關心長者今天的狀況」 |
| 想念關心 | 「長者已經一段時間沒有互動了，主動表達想念與關心」 |

Mem0 是語意檢索。**每天早上、每一位長輩，都拿同一句話去比對向量**，撈回的必然是與「問候／關心／狀況」語意相近的那幾條——與她昨天講了什麼無關。等於用同一把萬用鑰匙開所有人的門。

唯一有針對性的是 `HEALTH_QUERY`（`store.py:15`，固定 `health_top_k=3`），它穩定撈回用藥／回診／慢性病。於是主動問候的內容長期收斂到健康罐頭：「今天有沒有記得吃血壓藥呀？」

### 問題 2：今日對話在早上必然是空的

`MemoryStore.recent()` 只回今天 00:00 起的對話（`shortterm.py:79-80`）。早安問候在早上跑，那時今天尚未開始對話 → `history` 為空。**昨天講的事完全不在這一層**，只能寄望長期記憶——而那條路卡在問題 1。

## 為什麼不用「昨晚整理進長期記憶的那幾條」

此為初選方案，經查證後否決。兩個獨立的理由，任一個都足以否決：

**理由一：那裡面刻意沒有閒聊。** `CUSTOM_FACT_EXTRACTION_PROMPT`（`provenance.py`）第 4 條明訂：

> 「只抽取明確、穩定、可長期參考的資訊；**閒聊與情緒由系統另行處理**。」

所以 consolidation 寫進 Mem0 的是「長者有高血壓」「長者有三個孫子」這類穩定事實——**正是問題 1 已經在撈的那些東西**。拿它當關鍵字＝撈回更多罐頭，繞一圈回到原點。

**理由二：日期對不上。** consolidation 於凌晨 3 點執行、整理的是**昨天**的對話，但 Mem0 的 `created_at` 記的是**寫入時刻（今天）**。想靠日期把「昨晚那批」挑出來，第一步就對不上。

> ⚠️ 附帶發現（**已於本次一併修復**，Leo 指示）：同一個時間偏移代表 `MemoryItem.date` 系統性地比對話實際發生日**晚一天**。該欄位會餵給模型（`_MEMORY_PREFIX` 宣稱「附記錄日期」）。修法：consolidation 把對話日寫進 metadata 的 `occurred_on`，`MemoryItem.date` 優先取它；排序鍵一併改為「先對話日、再寫入時刻」——停機補整理會把多個對話日在同一秒寫入，只靠 `created_at` 排序時寫入序與對話序無關，而 prompt 明著跟模型說記憶「已由新到舊排列」。見「已知限制 6」。

## 方案：用對話摘要

`CUSTOM_FACT_EXTRACTION_PROMPT` 那句「閒聊與情緒**由系統另行處理**」，指的就是 `reports/summaries.py`。那條路已經在跑。

`summarize_day`（每晚與 consolidation 同一批次執行）現況：

- 讀 `short_term.previous_day(elder_id)` ＝ 昨天整天對話
- 丟給 Gemini：「用一兩句溫暖、客觀的台灣繁體中文摘要長輩這天的狀況與情緒」
- 存成 `conversation_summaries(elder_id, date, content, created_at)`，`date = 今天 - 1 天`

它天生就是本功能要的東西：

| 需求 | 摘要為何滿足 |
| :--- | :--- |
| 內容要是她的話題與情緒 | `SUMMARY_PROMPT` 就是這麼寫的——正是 Mem0 刻意排除的**另一半** |
| 當檢索關鍵字要夠集中 | 只有一兩句，不像整天對話那樣雜訊蓋過訊號 |
| 取用要確定，不能靠猜 | 以 `(elder_id, date)` 為鍵直接取；日期由 `last_active` 定位（見元件設計 4） |
| 日期要正確 | `day = 今天 - 1`，記的是**對話發生日**、非寫入時刻——與 Mem0 的 `created_at` 正好相反 |
| 沒講話要能回退 | `if not turns: return` → 該日無列 → 天然的回退訊號 |
| 不應增加成本 | 已經每晚在跑（家屬報告用），本功能只是多讀一次 |

## 元件設計

### 1. `ConversationSummaryStore.get_for_date`（新增）

三件套同步新增（Protocol ＋ `PgConversationSummaryStore` ＋ `FakeConversationSummaryStore`），回傳 `ConversationSummary | None`。命名依 AGENTS.md：`get_*` 取單筆。

為何不重用既有 `list_for_elder` 再過濾：它無 `limit`，回傳該長輩**全部**摘要（長期使用者可達數百列），為了取一列而全撈。

### 2. `CareAgent.proactive(..., *, recall=None)`

```python
@dataclass(frozen=True)
class Recall:
    content: str      # 摘要本文
    days_ago: int     # 0＝今天稍早、1＝昨天、N＝N 天前

def proactive(self, elder_id: str, intent: str, *, recall: Recall | None = None) -> str:
```

- 檢索關鍵字：`_envelope(elder_id, recall.content if recall else intent)`
- `recall=None` → 一字不差維持現行行為（這就是回退路徑，不需另寫分支）
- CareAgent **不因此依賴 `reports/`**：由呼叫端負責取摘要傳入

**`days_ago` 非帶不可**（探針證據）：主動推播可能在她沉默多日後才發，摘要講的是好幾天前的事。不講幾天前，模型把舊摘要當成剛發生：實測金孫說出「妳好久沒找我聊天了……孫子這週末要回去」——一句話自相矛盾。帶了之後改為「這週末孫子**有來看妳嗎**？」，正確地當成可能已發生。

### 3. 摘要直接注入 prompt ＋ 任務描述條件式加碼

檢索終究是機率——關鍵字對了也不保證撈得回來。摘要既然已經在手上，直接注入才能讓「它記得我上次講什麼」是**確定的**。

情境段重用既有的 `FactSection` ＋ `format_injected_context`，不新增排版函式；段首由 `_recall_title(days_ago)` 依天數產生（「昨天」／「5 天前」）。刻意**不**走 `FactProvider` 介面：那會讓摘要進入**每一輪**對話（含長輩主動開口時），加重每次 prompt，超出本次範圍。

**但情境段不夠**（探針證據，本文最重要的發現）：想念推播連測四輪**穩定**不理會摘要，只講「好久沒聽到您的聲音，很想您」。根因不在段首措辭（改寫兩版皆無效），而在**任務描述**——`_PROACTIVE_DIRECTIVE` 給模型的任務是「主動表達想念與關心」，那本身是個做得完的任務，做完就停。早安那條會用摘要，是因為它的 intent 有「關心長者今天的**狀況**」，字面對上了段首的「跟你聊天的**狀況**」。

故 `recall` 存在時，於任務描述後條件式附加 `_PROACTIVE_RECALL_DIRECTIVE`（「順著上面她上次聊天的狀況，關心那件事後來怎麼樣了」）。加上後想念推播即穩定追問。

⚠️ **條件式是安全關鍵**：無條件附加會讓沒有摘要的長輩被憑空編一段回憶。實測現況（無摘要時）金孫不編故事，不可回頭破壞——`test_proactive_never_asks_to_follow_up_without_a_recall` 守這條線。

### 4. `worker._recall` 接線

```python
last = memory.last_active(elder_id)          # 她最後一則 user turn
if last is None: return None                 # 從沒開口過（新長輩）
spoke_on = datetime.fromtimestamp(last, clock().tzinfo).date()
row = summaries.get_for_date(elder_id, spoke_on.isoformat())
return Recall(row.content, (clock().date() - spoke_on).days) if row else None
```

**為何以 `last_active` 定位而非「今天減一天」**（探針證據，本文原訂設計的錯）：

1. 失聯關心的觸發條件是「≥2 天沒開口」，與「昨天有她的對話」**互斥**——照昨天讀，這條路對想念推播**永遠是 None**，等於「兩個一起修」只修了一半。
2. 更糟：主動推播每次都寫一則 assistant turn，而 `summarize_day` 只看「昨天有沒有任何對話」、不分是誰講的。所以她沉默期間，昨天**仍會有**一份摘要——內容是**金孫自言自語**。照昨天讀會拿這個當成她的近況。

`last_active` 已是 `MemoryStore` 現成方法（失聯 job 自己就在用），`get_for_date` 已於本次新增，故不需再加 store 方法。

摘要讀取失敗**不可**擋下問候：吞例外、記 warning、回 `None` → 退回現行行為。理由與既有的問候偏好讀取失敗一致（`proactive/jobs.py`）：降級成本功能之前的行為，比整批長輩沒人理她好。

`memory`／`summaries`／`clock` 在該作用域皆已有，不需新增依賴。

## 已知限制

1. **摘要的視角是寫給家屬看的**，不是為 prompt 注入而寫（「阿嬤今天心情不錯，聊到……」是第三人稱敘述）。✅ 探針實測未出現讀報告語氣（「阿嬤早安，昨天膝蓋比較不痛了，今天有沒有感覺好一點呢？」），`_recall_title` 的「不必逐字複述」有效。
2. **她從沒開口過 → 無摘要 → 退回現行罐頭行為**。此為刻意：寧可平庸，不可胡編。✅ 探針實測無摘要時不編故事。
3. **不設天數上限**（Leo 核定）：她若九天前說「孫子這週末要來」，那個週末已過，金孫仍會拿它開話題。緩解靠 `days_ago` 進 prompt——實測模型會改用過去式追問（「有來看妳嗎」）。⚠️ 未實測極端舊（如 30 天）的表現。
4. **一般對話不受影響**：只改 proactive 路徑。長輩自己開口時，仍看不到摘要。
5. **摘要不分是誰講的**（既有設計，未修）：`summarize_day` 只要昨天有任何 turn 就摘要，含金孫的主動推播獨白。本功能以 `last_active` 定位繞開了它，但那些「獨白摘要」仍會落庫、仍會出現在家屬的對話報告裡。
6. **Mem0 `date` 晚一天已一併修復**（本次）：`occurred_on` 進 metadata、排序改以對話日為主鍵。⚠️ 舊資料無此欄位，仍沿用晚一天的 `created_at`——刻意不回推「減一天」，因補整理批次會在同一時刻寫入多個對話日，減一天對它們是錯的。

## 背景與動機

主動問候走的記憶組裝路徑，與長輩主動開口時**完全相同**，沒有走簡化捷徑：

```
agent.proactive → _envelope(elder_id, query) → SessionMemory.assemble(elder_id, query)
                                                 ├─ long_term.search(elder_id, query)   ← 問題在這
                                                 ├─ short_term.recent(elder_id)          ← 早上必為空
                                                 └─ 事實提供者各段
```

問題不在「有沒有查記憶」，而在**拿什麼去查**。

### 問題 1：檢索關鍵字是萬年不變的 intent 字串

`proactive` 直接把 intent 當檢索 query（`agent.py:101`）：

| 推播 | 當成檢索關鍵字的字串 |
| :--- | :--- |
| 早安問候 | 「早安問候，關心長者今天的狀況」 |
| 想念關心 | 「長者已經一段時間沒有互動了，主動表達想念與關心」 |

Mem0 是語意檢索。**每天早上、每一位長輩，都拿同一句話去比對向量**，撈回的必然是與「問候／關心／狀況」語意相近的那幾條——與她昨天講了什麼無關。等於用同一把萬用鑰匙開所有人的門。

唯一有針對性的是 `HEALTH_QUERY`（`store.py:15`，固定 `health_top_k=3`），它穩定撈回用藥／回診／慢性病。於是主動問候的內容長期收斂到健康罐頭：「今天有沒有記得吃血壓藥呀？」

### 問題 2：今日對話在早上必然是空的

`MemoryStore.recent()` 只回今天 00:00 起的對話（`shortterm.py:79-80`）。早安問候在早上跑，那時今天尚未開始對話 → `history` 為空。**昨天講的事完全不在這一層**，只能寄望長期記憶——而那條路卡在問題 1。

## 為什麼不用「昨晚整理進長期記憶的那幾條」

此為初選方案，經查證後否決。兩個獨立的理由，任一個都足以否決：

**理由一：那裡面刻意沒有閒聊。** `CUSTOM_FACT_EXTRACTION_PROMPT`（`provenance.py`）第 4 條明訂：

> 「只抽取明確、穩定、可長期參考的資訊；**閒聊與情緒由系統另行處理**。」

所以 consolidation 寫進 Mem0 的是「長者有高血壓」「長者有三個孫子」這類穩定事實——**正是問題 1 已經在撈的那些東西**。拿它當關鍵字＝撈回更多罐頭，繞一圈回到原點。

**理由二：日期對不上。** consolidation 於凌晨 3 點執行、整理的是**昨天**的對話，但 Mem0 的 `created_at` 記的是**寫入時刻（今天）**。想靠日期把「昨晚那批」挑出來，第一步就對不上。

> ⚠️ 附帶發現（本次不修，另案）：同一個時間偏移代表 `MemoryItem.date` 系統性地比對話實際發生日**晚一天**。該欄位會餵給模型（`_MEMORY_PREFIX` 宣稱「附記錄日期」）。因為是整批平移，不影響「以較新的記錄為準」的相對排序，但絕對日期是錯的。

## 方案：用昨天的對話摘要

`CUSTOM_FACT_EXTRACTION_PROMPT` 那句「閒聊與情緒**由系統另行處理**」，指的就是 `reports/summaries.py`。那條路已經在跑。

`summarize_day`（每晚與 consolidation 同一批次執行）現況：

- 讀 `short_term.previous_day(elder_id)` ＝ 昨天整天對話
- 丟給 Gemini：「用一兩句溫暖、客觀的台灣繁體中文摘要長輩這天的狀況與情緒」
- 存成 `conversation_summaries(elder_id, date, content, created_at)`，`date = 今天 - 1 天`

它天生就是本功能要的東西：

| 需求 | 摘要為何滿足 |
| :--- | :--- |
| 內容要是昨天的話題與情緒 | `SUMMARY_PROMPT` 就是這麼寫的——正是 Mem0 刻意排除的**另一半** |
| 當檢索關鍵字要夠集中 | 只有一兩句，不像整天對話那樣雜訊蓋過訊號 |
| 取用要確定，不能靠猜 | 以 `(elder_id, date)` 為鍵，直接取昨天那列 |
| 日期要正確 | `day = 今天 - 1`，記的是對話發生日，非寫入時刻 |
| 昨天沒講話要能回退 | `if not turns: return` → 該日無列 → 天然的回退訊號 |
| 不應增加成本 | 已經每晚在跑（家屬報告用），本功能只是多讀一次 |

## 元件設計

### 1. `ConversationSummaryStore.get_for_date`（新增）

三件套同步新增（Protocol ＋ `PgConversationSummaryStore` ＋ `FakeConversationSummaryStore`），回傳 `ConversationSummary | None`。命名依 AGENTS.md：`get_*` 取單筆。

為何不重用既有 `list_for_elder` 再過濾：它無 `limit`，回傳該長輩**全部**摘要（長期使用者可達數百列），為了取一列而全撈。

### 2. `CareAgent.proactive(..., *, recall=None)`

```python
def proactive(self, elder_id: str, intent: str, *, recall: str | None = None) -> str:
```

- 檢索關鍵字：`_envelope(elder_id, recall or intent)`
- `recall=None` → 一字不差維持現行行為（這就是回退路徑，不需另寫分支）
- CareAgent **不因此依賴 `reports/`**：由呼叫端負責取摘要傳入，agent 只收一個字串

### 3. 摘要直接注入 prompt

檢索終究是機率——關鍵字對了也不保證撈得回來。摘要既然已經在手上，直接注入才能讓「它記得我昨天講什麼」是**確定的**，而不是碰運氣。

重用既有的 `FactSection` ＋ `format_injected_context` 排版機制，不新增排版函式：

```python
_RECALL_TITLE = "\n以下是她昨天的狀況（系統摘要，供你自然接續話題，不必逐字複述）：\n"
```

刻意**不**走 `FactProvider` 介面：那會讓摘要進入**每一輪**對話（含長輩主動開口時），加重每次 prompt，超出本次範圍。

### 4. `worker._push_to_elder` 接線

```python
day = (clock().date() - timedelta(days=1)).isoformat()
row = summaries.get_for_date(elder_id, day)
```

摘要讀取失敗**不可**擋下問候：吞例外、記 warning、回 `None` → 退回現行行為。理由與既有的問候偏好讀取失敗一致（`jobs.py:51-55`）：降級成本功能之前的行為，比整批長輩沒人理她好。

`summaries` 與 `clock` 在 `_push_to_elder` 的作用域已經有了（`worker.py:67`），不需新增依賴。

## 測試計畫

- `test_reports_summaries_store_contract.py`：`get_for_date` 加進既有合約，`Fake` 與 `Pg` 參數化同跑（Pg 需 `KINSUN_IT=1`）——取得到、取不到回 `None`
- `test_agent.py`：帶 `recall` → `assemble` 收到的 query 是 recall 而非 intent，且 system_prompt 含摘要文字；不帶 → 維持 intent（回退）
- `test_scheduler_worker.py`：問候會帶昨天摘要進 `proactive`；摘要讀取炸掉時仍照常問候（不可因此漏問候）

## 已知限制

1. **摘要的視角是寫給家屬看的**，不是為 prompt 注入而寫（「阿嬤今天心情不錯，聊到……」是第三人稱敘述）。金孫會不會複述得像在讀報告，需人工複驗；先以 title 措辭（「不必逐字複述」）抑制。
2. **昨天沒講話 → 無摘要 → 退回現行罐頭行為**。此為刻意：寧可平庸，不可胡編。
3. **不解 Mem0 `date` 晚一天**（見上方附帶發現），另案處理。
4. **一般對話不受影響**：只改 proactive 路徑。長輩早上自己開口時，仍看不到昨天摘要。

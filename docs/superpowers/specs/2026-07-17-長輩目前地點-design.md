## 背景與動機

天氣工具 `get_weather` 吃的是城市名字串（`src/kinsun/tools/weather.py`），系統提示又明令「查天氣前若不知道長輩人在哪個城市，先親口問清楚，不要自己猜地點」（`src/kinsun/agent.py`）。兩者相加的實際行為是：**長輩每問一次天氣，就被反問一次「您人在哪個城市？」**

系統從來沒有任何管道知道長輩在哪。而長輩手上那支手機知道。

### 核心洞察：GPS 是線索，不是答案

這是本設計最重要的一句話，也是所有取捨的來源。

「阿公說：晚上九點半要去吃飯，有什麼推薦的餐廳？」——他問的地點**不必然是他站著的地點**。他可能要去兒子家附近吃、可能要去廟口。拿 GPS 直接當答案，錯得會很有自信。

所以定位資料的定位（雙關）是：**一條供模型參考的線索**。模型仍須自行判斷這句話問的是不是他的所在地；語意上不明確時，照舊開口問。本設計要消滅的是「每次都反問」，不是「永遠不反問」。

## 方案選擇

| 方案 | 說明 | 結論 |
| :--- | :--- | :--- |
| A：`FactProvider` 自動注入 | 位置每輪隨用藥、回診、策略一起進 system prompt | ✅ 採用 |
| B：做成工具 `get_current_location` | 模型要用才呼叫，與 `get_current_time` 對稱 | ❌ 見下節 |
| C：家屬在 App 設常住城市 | 不碰 GPS、零隱私成本、工程量最小 | ❌ 阿公去高雄住一週，天氣就整週答錯；且這不是「目前地點」 |
| D：上傳座標，後端反查地名 | 譯法可控、可換服務 | ❌ 多一個外部 API 要串；且資料庫會存下阿公的精確座標，敏感度躍升 |

### ⚠️ 為什麼不做成工具（Leo 核定，但這是本設計最接近的一次分岔）

做成工具在語意上其實更漂亮：`get_current_time` / `get_current_location` 完全對稱，`get_current_location → get_weather` 是真正的兩段串連，而且**模型必須先自問「我需要知道他在哪嗎」才會呼叫**——那個提問動作本身就是核心洞察要的那道確認。方案 A 反而有 anchoring 風險（見下）。

擋下它的是架構事實：**工具層拿不到 `elder_id`**。`ToolRegistry` 的 handler 一律是 `Callable[[dict], str]`（`src/kinsun/tools/registry.py`），參數只有模型給的 arguments。天氣、時間、衛教 RAG、上網查證都不需要知道是誰在講話，所以這個限制從未浮現——但「查他的位置」非知道不可。`CareAgent.handle(elder_id, ...)` 手上有，但 `_run_tool_loop` 沒接、`dispatch` 沒傳。

要補有兩條路：改 handler 協定（波及全部五個工具與測試替身），或走 contextvars（`src/kinsun/llm.py` 的 `_usage_collector` 已有同款先例與寫下的理由）。兩條都可行，但都是為了一個功能去動所有工具共用的地基。

**絕對不可行的第三條**：讓模型把 `elder_id` 當工具參數傳。模型會幻覺，也可能被長輩的話術帶偏，結果是查到別位長輩的位置——跨帳號資料外洩。此路封死，日後若真要做成工具也不得走這條。

代價另計：工具方案要多一輪 Gemini 往返（問天氣從兩輪變三輪，約多 1–2 秒），而對講機是語音，長輩在等。

**結論**：本輪走 A。日後若要加地點類工具（如餐廳搜尋），屆時再一併處理 `elder_id` 進工具層的問題，不要為了這個功能提前動地基。

## 元件設計

### 1. App 端取位（`app/src/app/elder/talk.tsx`）

長輩按下對講機時，順手取一次位置，與錄音併行、不阻塞：

- 權限：`Location.requestForegroundPermissionsAsync()`。**只要前景權限**——不申請背景定位（長輩要多點一次同意，iOS 上架還要交代理由，且最接近「監控長輩」的觀感）。
- 取座標：`Location.getLastKnownPositionAsync()`，**不是** `getCurrentPositionAsync()`。官方文件載明後者可能要等好幾秒；長輩按下對講機是要馬上講話的，等不起。快取位置對城市級精度綽綽有餘。
- 譯地名：`Location.reverseGeocodeAsync(coords)` → 取 `city`（缺則退 `subregion` → `region`）。

⚠️ **經緯度不離開手機**。譯完就丟，只有地名字串上傳。

### 2. 傳輸：`POST /turns?location=台南市`

`create_app_turns_router` 現在收的是**裸音檔 body**（`await request.body()`，且以 `content_type.startswith("audio/")` 擋非音訊，回 415），不是 multipart。地名在 body 裡沒有位置可放，只剩 header 或 query param：

| 作法 | 結論 |
| :--- | :--- |
| query param | ✅ FastAPI 原生解 UTF-8，client 自動編碼，可測 |
| header（如 `X-Elder-Location`） | ❌ HTTP header 預設 latin-1，「台南市」得自行 percent-encode，兩端都要記得 |
| 改 multipart | ❌ 要動 415 檢查與 App 既有上傳程式碼，代價最大、收益為零 |

簽章：`location: str = ""`。未帶、空字串、純空白一律視同「這輪沒有位置」，**不寫入、不清空既有資料**。

⚠️ **寫入必須排在 `dispatch` 之前**。長輩這句話問的就是天氣時，這一輪就得用得到；排在後面等於永遠慢一輪。

### 3. 持久層：`src/kinsun/locations/store.py`

三件套，比照 `medications/`、`appointments/` 的形狀；`ElderLocation` dataclass 同檔（D-42 例外，比照 `proactive/preferences.py`）。

```python
@dataclass(frozen=True)
class ElderLocation:
    elder_id: str
    place: str        # 地名，如「台南市」
    recorded_at: float  # epoch 秒

class LocationStore(Protocol):
    def save(self, location: ElderLocation) -> None: ...
    def get_for_elder(self, elder_id: str) -> ElderLocation | None: ...
```

`save` 為 upsert（`ON CONFLICT (elder_id) DO UPDATE`），即 Leo 核定的「存最新一筆、覆寫式」——不留歷史軌跡。`Fake` 與 `Pg` 兩個實作，以合約測試釘住等價。

**刻意不做 `list_all`**：目前無任何呼叫端需要列出所有長輩的位置，而「一次撈出全體長輩現在在哪」正是這份資料最不該有的介面。YAGNI 與最小權限在此同向。

### 4. 注入：`src/kinsun/locations/facts.py`

`LocationFacts` 實作既有的 `FactProvider` 協定（`facts(elder_id) -> FactSection | None`），接進 `composition.py` 既有的 facts 清單，與 `MedicationFacts`、`AppointmentFacts`、`StrategyFacts` 並列。

無資料、或已過期 → 回 `None`（該段完全不出現在 prompt）。

未過期 → 措辭必須把「線索」的語意寫死在字面上，不能只寫「長輩在台南市」：

> 這位長者的手機在 3 分鐘前回報他人在台南市。這只是參考——他問到的地點不一定是這裡。

⚠️ **相對時間（「3 分鐘前」）而非絕對時間戳**：模型對「1752739200」無感，對「3 分鐘前」有感。過期硬門檻擋掉最糟的情況，相對時間讓模型在門檻內的邊界情況上仍有判斷依據。

### 5. Prompt 改動：`src/kinsun/agent.py`

現行這句要改寫：

> 查天氣前若不知道長輩人在哪個城市，先親口問清楚，不要自己猜地點。

改為（定稿，實作時逐字採用）：

> 情境有時會附上長輩手機回報的目前位置。那是參考，不是答案——他問到的地點不一定是他人在的地方。
> 他明確在問所在地的天氣，就直接用那個地點，不要多問；
> 他提到要去別的地方（例如等下要去哪裡吃飯），就問清楚是哪裡，不可拿他目前的位置去查。
> 情境沒有附位置時，一律先問，不要自己猜。

三句話對應三種情形，缺一不可：第二句消滅「每次都反問」（本功能的目的），第三句擋住 anchoring（本功能最大的坑），第四句保住沒有位置時的現行行為。

### ⚠️ anchoring：本方案最大的坑

方案 A 的結構性弱點：位置**每輪無條件**進 prompt，即使長輩在聊完全無關的事。模型看到「他在台南」，問到天氣時就很容易順手查台南——正是核心洞察要防的事。工具方案沒有這個問題（模型得主動要），我們用 A 就得靠措辭扛。

因此第 4 節的措辭與第 5 節的 prompt **是本設計的功能本體，不是文案潤飾**。實作時必須有測試釘住「長輩問別處的天氣時，金孫不會拿他的所在地去查」。若上線後實測發現措辭扛不住，正確的反應是回頭重估工具方案（並一併解決 `elder_id` 進工具層），而不是加更多句提示詞。

## 錯誤處理

| 情況 | 行為 |
| :--- | :--- |
| 長輩拒絕定位權限 | **靜默降級**成現行行為（照舊反問）。絕不阻擋對講機、絕不重複騷擾要權限 |
| `getLastKnownPositionAsync` 回 null（沒有快取位置） | 同上，這輪不帶 `location` |
| `reverseGeocodeAsync` 失敗或回空陣列 | 同上。不退回傳座標——寧可沒有，不可破例 |
| `location` 帶了但寫入失敗 | 記 log，**不中斷對話**。比照工具失敗的既有政策：位置是加分項，不是對話的前提 |
| 資料已過期 | `LocationFacts` 回 `None`，prompt 裡完全不提位置 |

## 設定（環境變數）

| 鍵 | 預設 | 說明 |
| :--- | :--- | :--- |
| `LOCATION_STALE_AFTER_HOURS` | `2` | 位置超過幾小時就不再採信、不注入 prompt |

`Settings` 欄位名 `location_stale_after_hours`，一一對應。需同步補進 `.env.example` 並附中文註解。

`LOCATION_` 為新前綴，加入既有前綴清單（`GEMINI_`、`LONGTERM_`、`PROACTIVE_`、`REFLECTION_`、`SCHEDULER_`、`ASR_`、`TTS_`、`AUDIO_`、`SUPABASE_`、`LIFF_`、`LINE_`、`INTERNAL_TESTING_`）。

### 為什麼是 2 小時（Leo 核定：保守）

長輩講話時才抓位置，所以**對話中的位置永遠是幾秒前的、必然新鮮**——門檻對對話路徑毫無作用。它只影響一個地方：金孫主動開口的那一刻，讀到的是上次講話時的位置。

2 小時的實效：昨晚八點講的話，隔天早上八點的問候不會提地點（已過 12 小時）；早上八點講的話，十點的失聯關心還用得到。代價是主動問候多數時候不會提地名——這正是保守的用意。

## 資料庫遷移

新增 `ELDER_LOCATIONS_DDL`，接進 `ensure_schema`：

```sql
CREATE TABLE IF NOT EXISTS elder_locations (
    elder_id TEXT PRIMARY KEY,
    place TEXT NOT NULL,
    recorded_at DOUBLE PRECISION NOT NULL
)
```

表名 `elder_locations` 合既有慣例（`elder_guardians`、`elder_accounts`）。`elder_id` 為天然唯一鍵，直接當主鍵（比照 `greeting_preferences`）。時間戳 `DOUBLE PRECISION`（epoch 秒），合命名規範。

**無遷移路徑風險**：這是全新的表，既有庫沒有任何舊資料要升級，`CREATE TABLE IF NOT EXISTS` 在新庫與既有庫的結果相同。**不需要** `ALTER` 補欄位，故無 `db.py` 裡那類「本段須排在某某 DDL 之後」的排序約束。**不建額外索引**：主鍵即唯一查詢維度。

## 已知限制

### 1. LINE 通道永遠沒有位置

`locations` 只由 App 的 `/turns` 寫入。LINE 使用者的體驗維持現狀（每次反問）。這是通道能力差異，非缺陷。

### 2. 主動問候多數時候不會提地點

2 小時門檻的直接後果（見「為什麼是 2 小時」）。且 `CareAgent.proactive` 走的是 `generate` 而非工具迴圈（`src/kinsun/agent.py`），**主動問候時本來就沒有天氣工具可用**——但 `_envelope` 有跑 `assemble`，所以 facts 仍會注入。淨效果：主動問候時，位置至多影響金孫的措辭（「在台南還好嗎」），影響不了任何實際查詢。這是刻意的，記載以免日後有人以為位置在主動問候路徑上會做更多事。

### 3. 室內取不到位置

`getLastKnownPositionAsync` 回的是快取。長輩整天沒出門、手機沒更新過位置，可能回 null 或回一個舊座標。後者由過期門檻擋（`recorded_at` 是**我們收到的時刻**，不是 GPS 定位的時刻——這兩者可能有落差，是本設計未處理的誤差來源）。

### 4. 地名精度取決於裝置

`reverseGeocodeAsync` 用的是手機作業系統內建的地理編碼服務，各家回傳的 `city` 欄位粒度不完全一致（可能是「台南市」也可能是「東區」）。退階順序 `city → subregion → region` 是緩解，不是保證。若實測發現粒度不穩到影響天氣查詢，再評估方案 D（後端反查）。

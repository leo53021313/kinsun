# JS 端測試基建設計文件

- 日期：2026-07-17
- 狀態：**已實作**（Task 1–6）。實作與本文一致，無設計層級的更正；三處實作細節值得載明：(1) 兩份 `transformIgnorePatterns`／eslint test globals 的預備方案都沒用上——`jest-expo` preset 一設即可跑，測試碼用明確 import 而非全域。(2) `usePolling` 的測試證實了本文未預見的一件事：PR #56 之前的舊寫法能讓六條測試全綠，但 eslint 的 `react-hooks/refs` 會紅——測試釘行為、linter 釘實作正確性，兩道護欄守的不是同一件事。(3) 遷移七頁時漏改兩個「重新整理」按鈕，由 `tsc` 抓到——型別檢查在測試涵蓋不到之處仍有價值。
- 相關決策：目標＝先蓋住真風險而非鋪便宜的一層（Leo 核定）、七頁先抽共用 hook 再測一次（Leo 核定）、本輪不追 80% 覆蓋率（Leo 核定，見「與既有規則的抵觸」）

## 背景與動機

`app/` 與 `frontend/` **完全沒有測試框架**——沒有 jest／vitest、沒有任何 `.test.*` 檔、`package.json` 無 test script。後端有 1221 條測試守著，JS 端是零。

這不是抽象的技術債。就在今天，兩次改動都撞上它：

- **長輩地點功能**（PR #55）：`app/src/lib/location.ts` 處理定位權限、座標反查地名、四條失敗降級路徑——沒有任何自動化驗證。有人把 `return ""` 改成 `return "台北"`，跑遍全專案的測試都不會紅。
- **JS 端 linting**（PR #56）：一次改了 7 頁 admin 的錯誤橫幅時機——守著它們的只有 `tsc` 與 `npm run build`，兩者都證明不了畫面還能運作。

兩次的驗證方式都是「Leo 拿手機／開瀏覽器點一遍」。那不會累積，也不會在第三次改動時保護我們。

### 核心洞察：便宜的測試蓋不到真風險

測試有兩層。便宜的一層測純計算（`shared/format.ts` 把 epoch 秒譯成「7/17 13:20」），快、穩、不易壞。貴的一層測「畫面真的能用嗎」，要先假造原生模組與網路回應，慢且難寫。

**今天燒到的兩處，恰好只有貴的那層抓得住。** 純函式測試一條都攔不住 `location.ts` 或那七頁。所以本輪直接做貴的那層（Leo 核定），不從便宜的鋪起——鋪了也只是讓覆蓋率數字好看，該擋的還是沒擋住。

## 方案選擇

### Runner：兩套，不共用

| 方案 | 說明 | 結論 |
| :--- | :--- | :--- |
| A：`frontend/` vitest ＋ `app/` jest-expo | 各用各生態的原生選擇 | ✅ 採用 |
| B：兩邊都用 vitest | 一套工具、一套心智模型 | ❌ Expo v54 官方文件推薦 jest-expo 並明列 `@testing-library/react-native`，**vitest 隻字未提**。React Native 的 transform／原生模組 mock 由 `jest-expo` preset 處理，硬用 vitest 是跟生態打架 |
| C：兩邊都用 jest | 同上 | ❌ `frontend/` 是 Vite；vitest 可直接複用 `vite.config.ts`（含 `kinsun-shared` 的 alias），改用 jest 要另外維護一份等價的 transform 與 alias 設定 |

理由與上一輪「兩套 eslint 設定」完全相同：**兩個執行環境**。`app/` 是 React Native、`frontend/` 是瀏覽器 Vite app。

### 順序：先釘住現有行為，再重構

七頁 admin 要先抽共用 hook 再測（Leo 核定），但**重構當下還沒有測試守著**——這是雞生蛋。解法是把順序排對：

1. 立起 vitest，對**現有的**其中一頁寫測試 → 同時證明工具可用、並把現有行為釘住
2. TDD 寫 `useLoadable`（測試先行）
3. 七頁遷移到 hook
4. 第 1 步那份測試**仍須綠** ← 這就是重構沒改壞行為的證據

若把重構排在建立測試之前，第 4 步的證據就不存在，我們只能再一次靠「Leo 點一遍」。

- script：`"test": "vitest run"`（CI 用；本機開發可自行 `npx vitest`）

### 2. `app/` 的 jest-expo

- 依賴：`jest-expo`、`jest`、`@types/jest`、`@testing-library/react-native`
- 設定：`app/package.json` 的 `"jest"` 區塊，`preset: "jest-expo"`，並依 Expo 文件帶上 `transformIgnorePatterns`
- script：`"test": "jest"`（**不用** `--watchAll`：文件的範例是給本機開發用的，CI 會卡住不結束）

### 3. `useLoadable`：抽出七頁重複的載入模式

檔案：`frontend/src/admin/useLoadable.ts`

現況七頁（`SystemPage`、`ElderTimelinePage`、`TraceDetailPage`、`AccountTab`、`MemoryTab`、`RemindersTab`、`RiskNotificationsTab`）都是同一個手寫模式：`useState` 資料 ＋ `useState` 錯誤 ＋ `useCallback` 載入 ＋ `useEffect(load, [load])`。

介面：

```ts
export function useLoadable<T, E = true>(
  /**
   * 取資料。**必須是穩定參考**（以 useCallback 包過），否則每次 render 都會重載。
   * 回傳 null ＝ 條件未滿足（如 elderId 尚未從路由解析出來），這輪不載入。
   */
  fetcher: () => Promise<T> | null,
  /** 把例外譯成錯誤值。預設回 true。**不需要**穩定參考（見下）。 */
  mapError?: (exc: unknown) => E,
): { data: T | null; error: E | null; reload: () => void };
```

⚠️ **錯誤型別必須可由呼叫端決定**，不能寫死成 boolean：六頁用布林就夠，但 `TraceDetailPage` 要區分 404「查無此筆」與一般失敗，它的 error 是字串。這是抽象時最容易做錯的一步——把七頁裡的六頁當成全部。

⚠️ **`mapError` 由 hook 內部以 ref 保存**，故呼叫端不必 `useCallback` 包它。理由與 `usePolling` 相同（該 hook 已用此模式）：它是每次 render 都可能是新參考的回呼，若列入相依會讓載入無限重跑；用 ref 保存則永遠取到最新的、又不影響相依。

⚠️ **`setError` 一律在非同步回呼中呼叫**，不得寫在函式開頭——那正是 PR #56 修掉的 `set-state-in-effect`，抽成 hook 後只有一處會犯，但也只有一處守得住。

呼叫端形狀（以 `MemoryTab` 為例）：

```tsx
const { data, error } = useLoadable(
  useCallback(() => (elderId ? getElderMemory(elderId) : null), [elderId]),
);
if (error) return <p className="error-banner">{strings.common.loadFailedRefresh}</p>;
if (!data) return <p>{strings.common.loading}</p>;
```

`TraceDetailPage`：

```tsx
const { data: trace, error } = useLoadable(
  useCallback(() => (traceId ? getTrace(traceId) : null), [traceId]),
  (e: unknown) =>
    (e as { status?: number })?.status === 404
      ? strings.trace.notFound
      : strings.common.loadFailedRefresh,
);
```

## 測試策略

本設計的交付物**就是**測試。驗證方式：

| 項目 | 方法 |
| :--- | :--- |
| 兩套 runner 可跑 | `cd frontend && npm test`、`cd app && npm test` |
| 測試真的會抓 | 故意改壞 `useLoadable`（如讓 `reload` 不清錯誤），確認測試紅；還原 |
| 重構未改壞行為 | `MemoryTab.test.tsx`（重構前寫的）在遷移後仍綠 |
| 未破壞既有檢查 | 兩邊 `npm run lint`、`npm run typecheck`、`npm run build`、`npm run build:admin` |
| 後端不受影響 | `uv run pytest`（應與現在同為 1221 passed） |

### ⚠️ 與既有規則的抵觸（Leo 核定）

`.claude/rules/testing.md` 訂「最低覆蓋率 80%」與「測試驅動開發（強制）」。**本輪不追 80%**，且部分工作（抽 hook 前的釘樁測試）是 characterization test 而非 TDD。

理由：JS 端現在是 0%。真要在這輪湊到 80%，就得幫 `theme.ts`、`strings.ts` 這類常數字典寫沒有意義的測試——那是為數字服務，不是為正確性服務，而且會把這輪撐成一個沒人 review 得動的 PR。

本輪的成功標準是**基建可用 ＋ 蓋住今天真正燒到的地方**，覆蓋率隨新功能自然長（新功能仍走 TDD）。

那條規則的措辭是否該區分後端與前端、或改為「新增程式碼須有測試」而非全庫覆蓋率——是另一個議題，不在本輪，但值得 Leo 日後決定。**本文載明此抵觸，是為了讓它是一個有意識的例外，而不是一次無聲的違規。**

## 已知限制

### 1. 七頁只有一頁有元件層測試

`MemoryTab` 之外的六頁不寫各自的元件測試——它們遷移後共用同一個 `useLoadable`，而 hook 有扎實的測試。代價是「某頁忘了接 hook 或接錯」這種錯誤只有 `MemoryTab` 那條路徑守得住，其餘六頁仍靠 `tsc` 與人工。這是刻意的取捨：七份幾乎一樣的元件測試，維護成本與重複程度跟原本七份手寫載入邏輯是同一個問題。

### 2. `app/` 只測 `location.ts`，不測畫面

`talk.tsx`（對講機）、`home.tsx` 等元件本輪不寫測試。RN 元件測試要 mock `expo-audio`、`expo-haptics`、路由等一整串，成本遠高於本輪要蓋的風險。`location.ts` 是純邏輯 ＋ 一個可 mock 的模組，投報率最高。

### 3. `shared/` 仍無測試

`shared/`（`format.ts`、`envelope.ts`、`client.ts`）被三端共用、零測試，那裡的 bug 會同時打到長輩 App、家屬 App 與後台。本輪不含它——它屬於「便宜的那一層」，而本輪的目標是先蓋住貴的那層真風險（Leo 核定）。它在上一輪 linting 也被排除（該 spec 已知限制 1），**已連續兩輪被跳過，值得排進下一輪**。

### 4. 沒有 E2E

本設計不含 Playwright／Detox。人工複驗仍是「整條路真的通嗎」的唯一驗證。

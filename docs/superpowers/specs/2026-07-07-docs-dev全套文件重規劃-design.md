# docs/dev 全套文件重規劃（設計）

- **日期**：2026-07-07
- **狀態**：已核准（Leo，2026-07-07）
- **背景**：專案早期由 AI 快速產碼，大量「本該由人判斷的細項」被 AI 直接代決；App 轉型（階段 1–4 已併入 main）後 docs/ 既有文件全數過時。Leo 決定以老師的 VibeCoding_Workflow_Templates（17 份模板）重新規劃全套開發文件，重新做每項細節決策，最後一次性重構程式碼。

## 0. 最高原則（Leo 拍板，覆蓋本設計其餘條文）

1. **舊文檔僅供參考，結論不繼承**：docs/mvp/、全庫人工決策盤點-待議.md、archive/dev_docs/ 舊設計只當「領域地圖」提示，所有結論從現行程式碼重新推導。
2. **每項決策重新問過 Leo**：包含程式碼中**已經成形、看似已決定**的抉擇——快速開發時 AI 代決的部分一律視同「未決策」。「程式碼有寫」≠「有人決定過」。
3. 例外：Leo 本人近期明確拍板過的決定（如 2026-07-07 App 轉型五階段），列為「已拍板項」供快速確認維持與否，不展開選項。
4. AI 不得代填任何決議欄；未拍板者一律標 ⚠ 待議並登記決策清單。

## 1. 範圍與模式

- 產出**全套 16 份文件**（模板 02–17），置於 `docs/dev/`。老師手冊模式判準：本專案涉及長輩健康隱私資料 → 完整流程模式。
- 內容基準：**as-is＋to-be 對照**（Leo 拍板）。to-be 為重構契約，未定處標待議。
- 施工順序：**方案 B（邊寫邊問）**——按模板逐份寫，寫到哪份就重掃該領域程式碼並問該份的決策點；全庫「重新盤點」由各文件的領域重掃＋最終漏網掃描共同達成。

## 3. 文件內部格式

每個主題節固定四段：

1. **現況（as-is）**——附 `file:line` 證據
2. **目標（to-be）**——重構後狀態
3. **差距與重構項**——條列，最終餵給 16_WBS
4. **⚠ 待議**——連結 `D-xx`

文件開頭：版本／日期／狀態／拍板紀錄。

## 4. 決策清單（00_決策清單.md）

- 全新編號 `D-xx`（全域流水號，依遇到順序配號）。
- 每項欄位：主題、出處文件、現況（含證據）、選項、建議、影響、優先級（P0/P1/P2）、**決議欄**（Leo 拍板內容／「帶團隊會議」）、拍板人＋日期、舊 T-xx／E-xx 對照（純追溯）。
- 16 份完成後重排「**會議議程版**」：按 P0→P2、按主題分節（安全隱私／產品 UX／工程）。

## 5. 每份文件的工作循環

1. 重掃該領域程式碼（平行子代理；舊文檔僅當領域地圖）
2. 萃取決策點——**含已成形抉擇**（原則 0.2），分兩類
3. 問 Leo（混合式）：產品／倫理／花錢／P0 類 → 問題卡逐項；工程參數類 → 分節貼清單批次回覆
4. 拍板者寫定案（註記人＋日期）；帶會議者標 ⚠ 登記決策清單
5. 寫出該份文件，**一份文件一個 commit**（Leo 分支，不 push，等 Leo 指示）

## 6. 寫作順序

02 PRD → 03 BDD → 04 ADR → 05 架構 → 06 API → 07 模組 → 08 結構 → 09 依賴 → 10 類別 → 12 前端架構 → 17 前端 IA → 11 審查指南 → 13 安全 → 14 部署 → 15 維護 → 16 WBS。

**Fallback（Leo 拍板）**：明天會議前若跑不完，**決策清單優先**——確保 00_決策清單＋會議議程版完整（含漏網掃描），文件寫完幾份算幾份，其餘會後續寫。

## 7. 掃尾與舊文件處置

- 16 份完成後：跑一輪「漏網決策點」全庫掃描（模板未涵蓋的角落），補進決策清單。
- 定稿後：`docs/mvp/`（九份）與 `docs/全庫人工決策盤點-待議.md` 移入 `docs/archive/`，README 註記「已由 docs/dev 取代」。

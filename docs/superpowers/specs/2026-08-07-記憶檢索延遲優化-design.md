# 記憶檢索延遲優化（連線池／排程查詢合併／地端 embedding）設計

> **日期**：2026-08-07
> **狀態**：已核可（Leo 於對話中核定方案 A、實作順序「先做①②、③等驗證」、embedding「先驗，比輸了就不換」）
> **目的**：把 `SessionMemory.assemble` 從實測 822ms 降到約 530ms，且在不確定地端 embedding 檢索品質之前，不動任何不可逆的資料庫結構。

## 背景：本次量測

2026-08-07 於 DGX 實測，樣本為真實長輩（`a85acd2f…`，16 筆長期記憶、全庫 64 筆），
腳本見 scratchpad `09_assemble_baseline.py`／`10_rtt_breakdown.py`／`11_pool_minsize.py`。

### assemble 三段（各自單跑）

| 段 | p50 | 組成 |
| :--- | ---: | :--- |
| 今日對話 `short_term.recent` | 385 ms | 1 次 Supabase 往返 |
| **長期記憶 `long_term.search`** | **846 ms** | Gemini embed 317＋Supabase 向量 434（兩路並行） |
| 結構化事實 `_gather_facts` | 517 ms | 5 路碰 DB，擠 3 條連線 |
| **assemble（三段並行）** | **822 ms** | ≈ 最慢那段 |

### 單次 Supabase 往返 380ms 的拆解

| 量測 | p50 |
| :--- | ---: |
| TCP 建立連線（≈ 一次網路來回） | 83 ms |
| `SELECT 1`（連線已在手上） | 81 ms |
| 真實查詢 `schedules`（同一條連線） | 87 ms |
| **同一查詢，走專案連線池** | **255 ms** |
| 從頭建立一條新連線 | 648 ms |

**查詢本身只花 6 ms，網路來回 83 ms 是物理極限。**其餘是連線池開銷。

### 連線池 min/max 對照

| 設定 | 單次查詢 | 六路並行 |
| :--- | ---: | ---: |
| `min=1 max=3`（現況） | 264 ms | 670 ms |
| `min=3 max=3` | 310 ms | 673 ms |
| `min=6 max=6` | 204 ms | 340 ms |

**`min_size` 常駐無效，`max_size=3` 才是元凶**：六路並行擠三條連線得跑兩批。
（原假設「連線沒常駐、反覆重建」已被此表推翻，不可寫進根因。）

## 木桶效應（本設計的核心約束）

`assemble` 三段**並行**，總耗時 ≈ 最慢那段。單獨優化任何一段，第二慢的立刻成為新瓶頸：

| 做法 | 今日對話 | 長期記憶 | 結構化事實 | assemble |
| :--- | ---: | ---: | ---: | ---: |
| 現況 | 385 | **846** | 517 | **822** |
| 只調連線池 | 300 | **846** | 340 | **846**（沒省到） |
| 只換 BGE-M3 | 385 | **530** | **517** | **530** |
| 連線池＋BGE-M3 | 300 | **530** | 340 | **530** |

故三個工項必須成套評估，不可各自宣稱收益。

## 目標

**本次交付（工項 ①②）**：往返次數 5 → 3、`_gather_facts` 517 ms → 約 300 ms。
⚠️ **`assemble` 總耗時不會改變**（仍卡在長期記憶 846 ms）——這兩項是為 ③ 清路，
不可對外宣稱降低了端到端延遲。

**條件式（工項 ③，通過驗證閘門才做）**：`assemble` 822 ms → 約 530 ms。

**貫穿全案**：在未驗證地端 embedding 檢索品質之前，不執行任何不可逆的資料庫改動。

## 非目標

- **不搬資料庫**：DGX 地端 PostgreSQL（方案 C，可達約 30 ms）本次不做。
- **不碰寫入路徑的時序**：`record_turn` 與夜間整理批次一字不動。
- **不碰 GPU 共租**：TTS 那 8.2 秒是整輪最大單項（整輪 20.4 秒），但屬協調問題、非本設計範圍。誠實記載比例尺：assemble 省 292 ms ≈ 整輪的 1.4%。

## 工項 ①：合併三路排程查詢

### 現況缺陷

`ScheduleFacts` 一個 kind 一個實例，由 `composition.assemble_core` 註冊三次
（MEDICATION／APPOINTMENT／CUSTOM）。而 `facts.py:53` 每一路都呼叫
`self._store.list_for_elder(elder_id)`——撈的是該長輩的**全部**排程，再各自在記憶體裡
`if s.kind == self._kind` 過濾。

**三次跨海往返，拿回完全相同的資料。**

### 作法

查一次、分三段。`_gather_facts` 的並行度 6 → 4，往返 5 次 → 3 次。

### 硬約束

段落標題與行文**一字不可變**——那是 prompt 契約（`test_agent.py` 與 schedules 測試守著），
段落順序（時間 → 用藥 → 回診 → 自訂 → 守則 → 位置）同樣是契約，見
`recall._gather_facts` 的 ⚠️ 說明。三個 kind 中任一無排程時仍須各自回 `None`（該段缺席），
不可因合併而變成「一段包三種」。

### 預期

結構化事實 517 ms → 約 300 ms。**assemble 不變（仍卡在長期記憶 846 ms）**——
本工項的價值是釋放連線預算與減少跨海次數，不是縮短 assemble。

## 工項 ②：連線池 `max_size`

做完 ① 之後並行只剩 4 路，先重量再決定調不調、調多少。

### 預算上限

常駐進程 4 個（`WEB_WORKERS=2`＋scheduler＋rag_worker），各持一個池。
Supabase Supavisor pool 上限 25（Leo 於 2026-07-30 由 15 調升），另需留給 mem0 的 vecs 連線與 CLI。

| `DATABASE_POOL_MAX_SIZE` | 4 進程合計 | 判斷 |
| ---: | ---: | :--- |
| 3（現況） | 12 | 並行 4 路仍要跑兩批 |
| **5** | **20** | 留 5 條餘裕，建議值 |
| 6 | 24 | 太貼上限，2026-07-30 曾因連線饑荒吃過虧，不採 |

## 工項 ③：Gemini embedding → 地端 BGE-M3（**擋在驗證之後**）

### 接法

在 `services/embedding/server.py` **新增** OpenAI 相容端點 `/v1/embeddings`
（現有 `POST /embed` 保留給 RAG，兩者共用同一顆已載入的模型）。mem0 設定改為：

```python
"embedder": {
    "provider": "openai",
    "config": {
        "model": "BAAI/bge-m3",
        "embedding_dims": 1024,
        "openai_base_url": "http://127.0.0.1:8003/v1",
        "api_key": "<內網共用金鑰>",
    },
}
```

**為何不用 mem0 的 `huggingface` provider**：它在模組頂層 `import sentence_transformers`
（連帶拉進 torch），API 環境不該裝這些。`openai` 套件已在依賴中（2.44.0），走 OpenAI
相容協定**零新增依賴**。

⚠️ mem0 的 `OpenAIEmbedding` 在 `embedding_dims` 有值時會把 `dimensions` 參數傳給 API
（`openai.py:17`），故新端點必須接受並忽略（或驗證等於 1024）該參數。

### 不可逆的部分

維度 768 → 1024，**兩張表都要重建**：

| 表 | 筆數 |
| :--- | ---: |
| `vecs.kinsun_memories` | 64 |
| `vecs.kinsun_memories_entities` | 21 |

記憶原文存在 `metadata->>'data'`，可重算。但舊向量丟棄後不可回復，故**先把 85 筆完整
dump 成 JSON 存檔，再重建**。

⚠️ 讀寫必須同時切換：夜間整理批次（`consolidation.py`）與即時檢索共用同一份 mem0 設定，
維度不一致會讓向量查詢直接失敗。

## 驗證 ③ 的前置閘門（Leo 核定：比輸了就不換）

**不可沿用 2026-08-01 的 RAG A/B 結論。**那次語料是衛教文章（長句、有標題、書面語），
長期記憶是短句、口語、第三人稱（「Leo2的阿公喜歡吃壽司」），文字型態不同。

### 作法

以現有 64 筆記憶為語料，出 15–20 題長輩口語查詢（避開記憶原文用字，否則退化成字串比對），
Gemini 與 BGE-M3 各跑一輪，比對 R@1／R@3／MRR。

### 決策規則

省 292 ms 不值得讓金孫忘記阿公有高血壓，故：

- **R@1 落後 Gemini 5 個百分點以上 → 放棄工項 ③。**
- **任一題「Gemini 撈得到、BGE-M3 撈不到」且該筆是健康事實 → 放棄**（健康事實漏接的代價與一般話題不同量級，不進平均分數）。
- 兩者皆未觸發 → 採用。

門檻先寫死在此，避免看到數字才決定「多少算差」。若實測後認為門檻本身不合理，
須明著改本文件並說明理由，不可默默放行。樣本僅 64 筆記憶、15–20 題查詢，
統計上很薄——結論只用於「要不要換」這個二選一，不可外推成模型優劣的一般結論。

## 測試

- 工項 ②：設定值變更，無新增測試；以 `09_assemble_baseline.py` 重量驗收。
- 工項 ③：暫不實作，故無測試。

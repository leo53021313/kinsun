## 背景與動機

### 現況：一輪對話是一條不能中斷的直線

一輪 ＝ 一次 HTTP 請求／回應。App 端 `POST /turns` 上傳音檔，等整輪跑完才拿到文字與音檔網址（`src/kinsun/channels/app/turns.py:114-152`）。工具迴圈是嚴格序列的：

```python
# src/kinsun/agent.py:542-557
for _ in range(self._max_tool_iters):
    turn = self._llm.generate_tool_turn(...)
    if not turn.tool_calls:
        return turn.text or FALLBACK_REPLY
    for call in turn.tool_calls:                      # ← 多個工具排隊跑
        results.append(ToolResult(call, self._tools.dispatch(...)))
```

於是「有呼叫工具的輪」比「沒呼叫工具的輪」多付的不只是工具本身，而是**工具回來之後還要再跑一次完整的 LLM 生成**：

| | 沒有工具 | 有工具 |
| :--- | :--- | :--- |
| 流程 | LLM ×1 → TTS | LLM ×1（決定呼叫）→ 工具 → LLM ×2（消化並講人話）→ TTS |

`generate_tool_turn` 掛著 `thinking_level=MEDIUM`（`src/kinsun/llm.py:38`，該設定是必要的——不設等於工具形同不存在），實測中位數 2.33 秒。也就是說**光是「多的那一次 LLM」就固定多付兩秒以上**，工具本身的時間還要另計。這段等待期間長輩耳朵裡是全然的安靜。

### 目標

1. 長輩問完之後**盡快聽到第一個聲音**，即使答案還沒查到。
2. 等待期間長輩可以繼續講話，而且**每個問題都會被回答**。

## 實測（2026-07-28，設計前置）

設計初稿有四個未經驗證的前提，四次實測各打掉一個：TTS 併發安不安全、模型吐不吐安撫話、這件事到底省不省得到、**模型的安撫話真的貼合情境嗎**。最後一項推翻了方案選擇本身。**探針見本文附錄。**

### 實測一：TTS 併發會塌，而且塌得沒有規律

既有結論（2026-07-26）只說「併發 3 個會互搶 GPU、總時間反而更長」。本次要問的是更精確的問題：**互搶之後，最短的那一個（安撫話）會不會被拖慢**——因為長輩的體感完全取決於他多快聽到第一個聲音。

真實 TTS 服務（`TTS_ENDPOINT`，CosyVoice on GB10），三種真實長度：

| 情境 | 安撫話 9 字 | 完整回覆 43 字 |
| :--- | :--- | :--- |
| 各自單獨跑（基準線） | 1.85s | 5.52s |
| **單輪：安撫話＋回覆同時** | **1.84s（零影響）** | 7.31s（+1.8s） |
| **併發兩輪：四個同時** | **1.89s／3.69s／15.08s／1.88s** | 7.47s／9.18s／13.28s／14.89s |

兩個結論：

1. **單輪情境是安全的。** 安撫話 1.84s vs 基準 1.85s，完全沒被拖慢——它短，GPU 先做完就走。完整回覆晚 1.8 秒到，但那時長輩正在聽安撫話（本身要唸兩秒多），中間不會有空白。
2. **併發兩輪會塌，而且不可預測。** 同一個工作負載跑兩回合，某次安撫話 **15.08 秒**才回來、另一次 1.88 秒。GPU 排隊沒有任何優先權，純看誰先搶到。一句「稍等我喔」等 15 秒，比不講還糟。

**故 TTS 佇列是本設計的地基，不是可選的優化。** 見下方 §2。

### 實測二：模型現在完全不吐安撫話，但提示詞明講就會

設計初稿誤以為「模型本來就在講，只是 `llm.py:324` 把 text 丟掉了」。用真的 `SYSTEM_PROMPT`、真的 `ToolSpec`（10 個）、與 `generate_tool_turn` 完全相同的 `thinking_level=MEDIUM`，實測 `gemini-3.5-flash-lite`：

| | 有呼叫工具 | 其中**同時吐出文字** |
| :--- | :--- | :--- |
| A 組：現況提示詞 | 4/5 | **0/4** |
| B 組：提示詞加一句「查之前先講一聲」 | 4/5 | **4/4** |

B 組實際吐出的話：「好，我幫您查一下喔！」「好，我馬上幫您查。」——話術自然、長度合適（9～10 字，正是實測一裡零延遲成本的那個區間）。

兩個附帶確認：

- **工具呼叫率沒有被稀釋**（兩組同為 4/5）。提示詞每多一條都會稀釋其他條，這是既有教訓；此處未重蹈。
- **既有防線沒有被破壞**。第五題「今天天氣怎麼樣？」兩組都**沒有**呼叫工具，改問長輩人在哪裡——這正是設計要求的行為（情境沒附位置時一律先問，`agent.py` SYSTEM_PROMPT 第三句地點規則）。

⚠️ **樣本只有 4 題，是明確訊號但不是統計結論。** 上線前應以既有的原封重放方法（`llm.py:24-30` 註解所述、07-27 那筆 24 輪真實請求）重跑一次，比照當初量工具呼叫率的標準。

### 實測三：一輪對話的時間分解——省 5.42 秒，但安撫話會夾帶碎碎唸

前兩支探針只證明了「安撫話可行、TTS 要排隊」，沒有回答**這件事到底省不省得到**。設計初稿寫的「省 4–5 秒」是推算。本探針把它量成事實：真的 Gemini、真的正式資料庫（`get_news`）、真的外部 API（`web_search` 打 Tavily）、真的 TTS，量同一輪裡的四段。

n=6 有效樣本（8 次嘗試中 1 次模型未呼叫工具、1 次 TTS 回 400），中位數：

| LLM1 | 工具 | LLM2 | TTS 首段 | TTS 安撫話 |
| :--- | :--- | :--- | :--- | :--- |
| 2.22s | 2.25s | 1.75s | 3.29s | 1.86s |

| | 長輩聽到第一個字 |
| :--- | :--- |
| 現況（LLM1＋工具＋LLM2＋TTS首段） | **9.50s** |
| 改後（LLM1＋TTS安撫話） | **4.08s** |
| **省** | **5.42s（57%）** |

兩邊皆不含 ASR，故差值不受影響。設計主張成立，且優於初稿推算。

**但同一批樣本抓出一個設計裡沒想到的失效模式。** 其中一輪模型吐出的「安撫話」是：

> 好，我幫您查一下喔。碎碎唸：呼叫 \`get_news\` 工具來取得最近的新聞標題。

這**不是** thought part（探針已明確排除 `part.thought`）——模型是在正常的文字 part 裡寫出自己要呼叫哪個工具，還帶反引號。若原樣送進 TTS，長輩會聽到「碎碎唸：呼叫 get_news 工具來取得最近的新聞標題」。而且因為變長，該輪 TTS 從 1.86s 漲到 4.56s，**只省 1.28 秒**（其他五輪省 3.46～6.37 秒）。

`SYSTEM_PROMPT` 本來就禁止 Markdown 符號，模型顯然把安撫話當成另一種輸出、沒有套用那條規則。

> 當時的結論是「需要一道程式層出站防線」，理由與 `_no_fake_source`／`_speakable` 相同：提示詞管不住的事情要在程式層擋。**該結論已被實測四取代**——安撫話改由我們自己寫，這個失效模式從源頭消失，防線不必存在。此段保留為決策軌跡。

### 實測四：模型的安撫話 65% 是同一句罐頭話——「貼合情境」的前提不成立

實測三之後追加一支多代理調查（七個代理，語料 55 筆真實 Gemini 回應）。它的原始目的是查碎碎唸的根因，卻順帶推翻了整個方案選擇的前提。

**根因（confirmed，非推論）**：攔在 SDK 的 HTTP 層 dump 原始 wire JSON——正式設定（未開 `include_thoughts`）下 28 個 part **沒有一個帶 `thought` key**；開啟後 6/6 出現顯式 `"thought": true`（陽性對照，證明「沒有」是有意義的），且思考摘要**永遠是獨立的 part**。再加上洩漏句兩半之間**沒有空白**，而探針以 `" ".join(texts)` 串接多個 part——若來自兩個 part 必有空格。故整句原本就在**同一個** text part 裡：模型把內部敘述寫進了答案通道，結構上與正常安撫話無從區分。

> ⚠️ 設計初稿宣稱的理由（「探針已排除 `part.thought`」）是**空轉的死碼**——此設定下根本不存在 thought part 可供排除。理由寫錯會讓下一個人以為「開個過濾就好」。

**但真正改變決定的是這組數字。** 55 筆語料，去掉結尾標點後**一字不差**都是「好，我幫您查一下喔」的佔 **36/55 = 65%**。逐工具看：

| 工具 | 罐頭比例 |
| :--- | :--- |
| `web_search` | 6/6 = **100%** |
| `search_nearby_places` | 5/5 = **100%** |
| `health_education_rag` | 6/7 = 86% |
| `list_schedules` | 3/4 = 75% |
| `get_route` | 4/6 = 67% |
| `get_news` | 12/23 = 52% |

而剩下 35% 的「情境」，變化**全部來自工具本身**（「查一下**最近的新聞**」「查一下**車程**」「看一下**有哪些行程**」）——不是來自長輩講了什麼。模型沒有在貼合對話，它只是把工具的名詞塞進同一個句型。

**最刺的一點**：唯一一句真正貼合長輩具體內容的安撫話，正是劇透失效模式——

> 好，我馬上幫您記下來。**晚上七點記得吃血壓藥喔！**（`create_schedule` 尚未執行）

**「貼合情境」與「劇透」是同一個行為。** 模型越往具體內容靠，越容易在工具還沒跑時就對長輩斷言結果。

**結論**：模型生成換來的東西，預錄語庫全部給得起（因為變化本來就是逐工具的），卻要多付 1.86 秒、一套八道防線、以及擋不住的劇透風險。Leo 據此改案為依工具／人設分組的預錄語庫。

### 實測結論對設計的四點修正

1. 「省 4–5 秒」修正為**實測 5.42 秒**（模型生成案）；改預錄語庫後為 **7.28 秒（77%）**。
2. **安撫話改為預錄語庫**（§3.1），原「模型生成＋出站防線」方案否決。連帶取消：提示詞的 `ACK_DIRECTIVE`、`llm.py:324-325` 的改動、八道出站防線。
3. TTS 佇列壓力**減半**——安撫話完全不進 GPU。§2 的推算因此更寬鬆，佇列仍為地基（正式回覆與續段照樣競爭）。
4. **順帶挖出一個與本設計無關的既有缺口**：`agent.py:166` 的 `_CODE_FENCE` 與 `evals/assertions.py:32` 都只認三連反引號，**行內單反引號兩處皆無規則**。即使不做非同步，模型現在只要在正常回覆裡吐一個 `` ` ``，反引號就會被 TTS 唸出來。應另行修補，不與本設計混在同一次改動。

## 方案選擇

### 傳輸層

後端正式模式跑 **2 個 worker**（`WEB_WORKERS` 預設 2，`scripts/kinsun.sh:223`），連線由作業系統分派。若只加一條下行通道，長輩的 WebSocket 可能連在 worker A、他的錄音請求卻落在 worker B，**算出答案的那個推不出去**。

| 方案 | 結論 |
| :--- | :--- |
| **整輪對話都走 WebSocket** | ✅ **採用**。請求與回應在同一條連線上，歸屬問題自動消失；不需新增任何基礎設施，也不必退回單 worker。**額外紅利**：同一位長輩的所有併發輪必然在同一條連線、同一個 worker 底下，P3 的在途清單可以直接掛在連線物件上（見 §4） |
| 保留 POST，退回單 worker | ❌ 退掉 2026-07-09 已完成並實測過的雙 worker（丙-3／D-20 A-3） |
| 保留 POST，用 Postgres LISTEN/NOTIFY 跨 worker | ❌ 每個 worker 需常駐一條 LISTEN 連線（池上限僅 5），且 Supabase 是跨網服務，這一跳再多約 0.2 秒 |
| 手機推播（APNs／FCM） | ❌ 需 $99 Apple Developer ＋ EAS dev build（階段 5 未做）；且推播是給「App 沒開著」用的，對「對話進行中補一句話」語意不對 |

**上行維持「整包音檔」，不做串流錄音。** ASR 目前是整檔 API（`ASRClient.transcribe(audio, content_type)`），改串流是獨立工程。一個 binary message ＝ 一輪，與現行 POST 語意相同，只是換條管子。

### 安撫話的來源

⚠️ **本節於 2026-07-28 依 55 筆語料的實測結果推翻並重寫。** 原決定是「模型生成＋出站防線」，理由是話術貼合當下。語料證明**那個前提不成立**（見實測四），Leo 據此改案。

| 方案 | 結論 |
| :--- | :--- |
| **依工具／人設分組的預錄語庫** | ✅ **採用**（Leo 核定 2026-07-28，語料呈報後改案）。文字由我們自己寫，音檔由當前 TTS 設定自動合成並快取。長輩聽到第一個字 **2.22s**（比模型生成再省 1.86 秒，總省 7.28s／77%），洩漏與劇透**結構上不可能發生**，TTS 佇列壓力減半 |
| 模型生成（提示詞驅動）＋出站防線 | ❌ **已否決**。語料實測 55 筆：**65% 是一字不差的同一句罐頭話**「好，我幫您查一下喔」；剩下 35% 的「情境」全部只是把工具的名詞塞進同一句型（新聞／車程／行程），**變化來源是工具而非對話**。也就是說它換來的東西，預錄語庫全部給得起——卻要多付 1.86 秒、一套八道防線、以及擋不住的劇透風險 |
| 單一通用預錄池（不分工具） | ❌ 效益與採用案相同，但白白丟掉那 35% 的工具名詞變化，而那部分零成本可得 |
| 只給畫面提示不發聲 | ❌ 對講機是聲音媒介，長輩很可能沒在看螢幕 |

**改案帶來的大幅簡化——以下三件原設計的工作全部取消：**

| 原設計 | 改後 |
| :--- | :--- |
| 提示詞加 `ACK_DIRECTIVE` | **不需要**。`SYSTEM_PROMPT` 一字不動——連帶消滅「多一條規則稀釋其他條」的風險 |
| `llm.py:324-325` 停止丟棄 text | **不需要**。維持現狀繼續丟棄，協定層零改動 |
| §3.1 安撫話出站防線（八道檢查） | **不需要**。文字是我們自己寫的，不存在洩漏、劇透、空頭承諾 |

安撫話改為在 LLM 第一次回應返回後，直接以 `tool_calls[0].name` 查語庫取出**已合成、已上傳**的音檔網址——不等 TTS、不依賴模型的指令遵循。

**取不到時就不講安撫話**（該工具沒配句子且通用池也空、或快取尚未暖好），退回現行行為。這是降級，不是錯誤，不可因此讓整輪失敗。

### 晚到答案的處理

長輩問新聞（金孫說「稍等」），三秒後又問天氣。天氣兩秒查完、新聞八秒才回來。

| 方案 | 結論 |
| :--- | :--- |
| **都要講，晚到的帶一句回指** | ✅ **採用**（Leo 核定）。一次只播一則，先到先播，後到的排隊；晚到的開頭自然帶「對了，您剛剛問的新聞喔……」 |
| 只講最新的，舊的丟掉 | ❌ 長輩問了新聞又多講一句閒話，新聞就永遠沒了——而他可能一直在等 |
| 嚴格照發問順序播 | ❌ 快的答案被慢的拖累，省下的延遲又還回去 |
| 舊答案只送字幕不發聲 | ❌ 同上，長輩很可能沒在看螢幕 |

## 架構設計

### 1. 通道：`WS /ws/talk`

與 `channels/app/turns.py` 平行的第三個 adapter，同樣把訊息正規化成 `InboundMessage(Channel.APP, …)` 進既有 `dispatch`——閘門（同意複核）、危急偵測、記憶、觀測、語音回覆全部重用。

認證比照 `current_elder`：Bearer token 於連線建立時複核，且 `gate.resolve_elder` 必須通過（token 不代表同意，撤回即擋）。

**上行**：一個 binary message ＝ 一輪完整音檔。位置參數（`location`／`latitude`／`longitude`）改由前導的一則 JSON 訊息帶入。

**下行**（皆帶 `turn_id`，App 端據此對應）：

| 型別 | 時機 | 內容 |
| :--- | :--- | :--- |
| `ack` | 模型決定呼叫工具且吐出文字時 | `text`、`audio_url` |
| `reply` | 答案算完 | `text`、`audio_url`、`chunk_count`、`reply_digest` |
| `chunk` | 續段 | `index`、`audio_url`、`text` |
| `error` | 任一段失敗 | 回退話術（沿用 `SYSTEM_TROUBLE_REPLY`／`NOT_HEARD_REPLY` 的既有分工） |

`GET /turns/chunks/{index}` 的續段邏輯收進 `chunk` 下行訊息；該端點本身保留給 POST 路徑。

**`POST /turns` 保留不動**：LINE 通道仍走 `dispatch`，且 WebSocket 連不上時必須有降級路徑。

⚠️ **收到音檔後必須立刻交給 threadpool**，不可在 WebSocket 讀迴圈裡跑完整輪——否則長輩在等答案時的第二次發話根本讀不進來，P3 等於沒做。這與 `turns.py:136-140` 的 `run_in_threadpool` 是同一個教訓。

### 2. TTS 優先權佇列

**一次只跑一個推論**，用優先權佇列排序。對照實測一的數字：

| | 併發放生（實測） | 佇列＋安撫話插隊（推算） |
| :--- | :--- | :--- |
| 第一則安撫話 | 1.89s | 1.85s |
| **第二則安撫話** | **15.08s** | **3.70s** |
| 兩輪四則全部講完 | 15.08s | 14.74s |

總時間幾乎相同，但「長輩多快聽到第一個聲音」從**不可預測的 15 秒**變成穩定的 3.70 秒。

序列化在此不是妥協而是正確的形狀：**長輩一次只能聽一則，所以 TTS 一次只做一則本來就夠。** 播放的序列性與合成的序列性天然對齊。

⚠️ **改用預錄語庫後，安撫話完全不進 TTS**（§3.1），所以上表「安撫話插隊」那一列不再適用——GPU 上的競爭者少了一半。但佇列**仍是地基**：併發輪的正式回覆與續段照樣互搶，實測一的 7.47～14.89 秒就是它們造成的。

優先權由高到低：

1. 回覆第一段（長輩正在等答案）
2. 續段
3. 排程推播（主動關懷、用藥回診提醒）
4. 安撫話語庫的**啟動預熱**（最低——沒有任何人在等它，且它應該讓路給即時對話）

第 3 項是順帶修掉的既有問題：夜間批次的 TTS 目前會與長輩的即時對話搶同一顆 GPU，而沒有任何機制讓對話優先。

實作為包在 `DgxTtsClient` 外的裝飾器（`speech/tts.py`），對 `TTSClient` 協定無感——`TextBubbleTts` 與所有測試替身不受影響。未啟用時（單元測試、CLI）直接穿透，比照 `background.py` 與 `tracing` 的既有慣例。

### 3. 一輪的新流程

```
音檔進來（記下 spoke_at）→ 交 threadpool
  ↓
ASR
  ↓
情境組裝 ∥ 危急分級 ∥ 濫用審核          ← 完全不動，決策順序照舊
  ↓
LLM 第一次 → tool_calls（text 照舊丟棄）
  ├ 有 tool_calls → 依 tool_calls[0].name 查語庫 → 取快取好的音檔網址 → 推 ack
  └ 沒有 → 略過，不講安撫話
  ↓
工具並行 dispatch                        ← 原本序列
  ↓
LLM 第二次 → 出站防線 → record_turn(at=spoke_at) → TTS → 推 reply
```

⚠️ 安撫話這一步**不等 TTS、不依賴模型的指令遵循**：音檔在啟動時就合成、上傳好了，這裡只是查表取網址。這是它比模型生成快 1.86 秒的原因。

**唯一必要的程式改動是工具並行**（`agent.py:551`）。`llm.py` 協定層**一字不改**——`324-325` 繼續丟棄 text，因為我們不再需要模型那句話。

`elder_utterance`／`turn_sources`／`turn_actions` 走 contextvars（`turn_context.py:20-23`），各執行緒天然隔離；但登記簿是共用的 list，**並行寫入需以 `contextvars.copy_context()` 帶入並確保 append 的原子性**（CPython 的 `list.append` 本身是原子的，故實務上安全，但須在測試中明確守住）。

### 3.1 安撫話語庫（`speech/acks.py`）

安撫話的**文字是唯一真實來源**，音檔一律由當前 TTS 設定自動合成、不進版控。這個取捨是為了語音克隆：日後換聲音只要改一個環境變數，十幾段音檔自動重生，零手工步驟、零重錄。

**兩個維度：人設 × 工具**

```python
@dataclass(frozen=True)
class AckPersona:
    generic: tuple[str, ...]                    # 必填，該人設的萬用句
    by_tool: dict[str, tuple[str, ...]]         # 選填，逐工具的貼合句

DEFAULT_PERSONA = "kinsun"

def phrases_for(tool_name: str, *, persona: str = DEFAULT_PERSONA) -> tuple[str, ...]:
    """取候選句：先找該人設的該工具，沒有就退回該人設的通用句。"""
```

兩軸各有保底：人設不存在 → 退回 `DEFAULT_PERSONA`；工具沒配句子 → 退回該人設的 `generic`。**任何一格缺失都不會壞，只會變得比較籠統。**

語庫內容依語料實測——模型自己的變化就是逐工具的，照抄即可：

| 工具 | 句子（2～3 句輪替） |
| :--- | :--- |
| `get_news` | 好，我幫您查一下最近的新聞喔／我看看今天有什麼消息喔 |
| `get_route` | 好，我幫您查一下怎麼去喔／我看看要走多久喔 |
| `search_nearby_places` | 好，我幫您找找看附近有什麼喔 |
| `list_schedules`／`create_schedule` | 好，我幫您看一下喔／好，我記一下喔 |
| 其餘（含 `web_search`、`health_education_rag`） | 通用句：好，我幫您查一下喔／稍等一下下喔／好，我看看喔 |

`web_search` 與 `search_nearby_places` 只給通用句，是因為語料裡模型自己 **6/6、5/5 全部用通用句**——沒有觀測到的變化就不要憑空發明。

**測試強制把關（Leo 核定 2026-07-28，需求一）**

新增 `tests/test_speech_acks.py`，以 `pkgutil.iter_modules` 走遍 `kinsun.tools` 下**每一個模組**、蒐集所有模組級的 `ToolSpec` 常數，斷言：

1. `DEFAULT_PERSONA` 的 `by_tool` **涵蓋每一個註冊工具**——漏一個 CI 就紅。新增工具檔時自動被納入掃描範圍，**不需要有人記得去更新測試**。
2. 每個人設的 `generic` 非空。
3. 每一句都通過既有的 `check_speakable` 斷言（不含 Markdown、可直接唸）。

非預設人設**不**強制逐工具涵蓋——它們退回自己的 `generic` 即可，否則新增一個人設就要寫十幾句，會讓加人設變成苦差事。

**快取與語音克隆（需求二）**

```
cache_key = sha256(句子 + TTS_VOICE_VERSION)[:16]
```

- `TTS_VOICE_VERSION` 為新增的環境變數，語音克隆換聲音時改它。**所有快取自動失效、下次用到時重新合成**——不必刪檔、不必重錄、不必改程式碼。
- 快取存 `(物件路徑, 簽章 URL, 到期時刻, 時長)`。⚠️ **不可只存 URL**：`SupabaseAudioPublisher.publish` 回的是短效簽章 URL（`AUDIO_SIGNED_URL_EXPIRES_SECONDS` 預設一天），過期後要能**重新簽章**——不必重新上傳、更不必重新合成。
- **啟動時以 `background.run` 非阻塞預熱**，不可擋住服務啟動：十幾段 × 約 1.9 秒 ≈ 半分鐘，而且兩個 worker 各做一次。預熱完成前取不到就那一輪不講安撫話（降級）。
- 兩個 worker 各自持有記憶體快取、各自預熱一次。刻意不做跨進程共用：重複合成十幾段是一次性成本，換掉一整套鎖與失效邏輯，划算。

**安撫話音檔沒有個資**（都是我們自己寫的通用句），故可與長輩的回覆音檔區隔對待：獨立 prefix、較長的簽章效期，且**不可**被 `cleanup(retention_days)` 的日期資料夾清理掃到——被刪掉就要重新合成。

### 4. 併發輪的安全（P3）

**(a) 記憶順序倒轉。** `record_turn` 以寫入當下的時刻為排序鍵（`memory/shortterm.py:73`，`created_at = self._clock().timestamp()`），而 `recent()` 依 `ORDER BY created_at DESC, id DESC` 取回。併發輪會讓「後問的先寫進去」，隔天 recall 讀到的對話順序是顛倒的。

> 修正：`record_turn` 增加 `at` 參數，以**長輩開口的時刻**（WebSocket 收到音檔那一刻）為 `created_at`。單輪路徑數值幾乎不變（開口時刻 ≈ 寫入時刻），併發時順序才正確。預設 `None` ＝ 沿用現行行為，既有呼叫端與測試不受影響。

**(b) 第二句失去上文。** 長輩問完新聞、接著問「**那**天氣呢」——「那」是指代，需要上文。但輪 1 尚未寫進 DB，輪 2 組裝情境時看不到。

> 修正：每位長輩維護一份**記憶體內的在途清單**，`assemble` 之後把在途輪的長輩原話補在 history 尾巴。
>
> ⚠️ **刻意不採「長輩的話先寫 DB、回覆後再補」**：那會違反既有安全契約「被濫用審核攔下的這一輪不寫進記憶」（`pipeline.py:185-186`，綁架企圖不該變成明天的對話脈絡）。在途清單只存在記憶體、被攔的輪直接丟棄，契約完好。
>
> 在途清單掛在 WebSocket 連線物件上——同一位長輩的所有併發輪必然在同一條連線、同一個 worker，這是「整輪走 WebSocket」帶來的紅利，不需要任何跨進程機制。

**(c) 併發上限。** 長輩連按會開出無限多輪。上限設 3，超過即以 `error` 回一句「金孫還在忙前面那幾句，等一下下喔」。無上限佇列會把行程吃垮，理由與 `background.py:28-30` 的佇列上限相同。

**(d) 晚到答案的回指。** 推 reply 時若該輪不是最新的一輪，於**第二次 LLM 的系統提示**加一句要求模型開頭自然帶回指。不在程式層硬前綴——拼接出來的句子 TTS 唸起來會斷裂。模型不聽時不做補救（留 trace 標記供事後查頻率），理由與 `_repair_empty_promise` 的「只補救一次」相同：為了這件事把對話弄壞是更差的結果。

### 5. App 端

- WebSocket 客戶端，含斷線重連。
- **播放佇列**：收到 `ack`／`reply`／`chunk` 一律入列，一次只播一則。
- **按住麥克風即停止播放**——對講機模式下按下去就是要講話，不停會把金孫的聲音錄進去。
- 斷線時正在跑的那輪答案會掉。重連後以 `turn_id` 補拉（後端需短暫保留未送達的回覆）。

## 已知殘餘風險

1. **話術固定，不貼合長輩講的具體內容。** 這是改案接受的代價——但語料證明模型本來就有 65% 講同一句罐頭話，剩下 35% 的變化預錄語庫也給得起。真正失去的只有「模型日後變聰明時話術自動變好」這件事；屆時可回頭評估，本次的語庫與快取層不擋這條路。

2. **整輪沒有工具呼叫時就沒有安撫話。** 語料實測 **3/55＝5.5%**。三筆中兩筆是 `SYSTEM_PROMPT` 明文要求的反問（記排程前先徵詢、查證前先問是哪一位），行為完全正確，只是那一輪長輩要靜靜等到答案。另有極少數整輪回 `MALFORMED_RESPONSE`（實測三遇過一次）。可接受，但不可讓它變成例外。

3. **語料裡撈到一個與本設計無關、但該回報的既有問題**：長輩問「我想去菜市仔買菜，這附近佗位有？」被路由到 `web_search` 而非 `search_nearby_places`（6 題中錯 1 題）。`SYSTEM_PROMPT` 的「附近有什麼」規則涵蓋不到「先講意圖再問地點」的句型——正是 2026-07-27 拉麵店事件想防的事。應另案處理。

4. **斷線時在途輪的答案會掉。** 後端短暫保留未送達回覆可緩解，但長輩重連後才聽到三十秒前問題的答案，體驗未必比丟掉好。P3 實作時需決定保留視窗。

5. **TTS 佇列會讓「總完成時間」在高併發下線性增長。** 佇列解決的是公平性與可預測性，不是吞吐量。真正的吞吐量上限由那顆 GB10 決定；多位長輩同時使用時仍會排隊。訊號會是佇列等待時間的觀測指標——先看到那個再談加卡或分流。

6. **P3 的在途清單綁在單一 WebSocket 連線上。** 長輩若在兩台裝置同時登入，兩條連線各有各的在途清單，互相看不到。目前綁定模型是一位長輩一台裝置，故不處理。

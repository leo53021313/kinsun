# 內部測試基礎建設 設計文件

- 日期：2026-07-12
- 狀態：已與 Leo 逐節確認核可
- 範圍：內測總開關、App 一機雙端快速切換、觀測後台強化（唯讀＋手動觸發）、.env 整理

## 1. 背景與目標

團隊即將開始內部測試全部功能，有三個痛點：

1. **一機雙端**：金孫 App 是單一 App 內含長輩／家屬兩種身分，但登入狀態只存一份
   （SecureStore 單一 key `kinsun_session`，`app/src/lib/auth.ts`），換身分必須登出，
   長輩重登還得重新掃碼或輸手機號＋密碼。內測時一個人一台手機無法順暢測兩端。
2. **後台觀測不足**：觀測後台目前只有五頁（總覽、訊息流、長輩清單、單日時間軸、單輪鏈路），
   許多已落庫的資料（提醒設定、排程狀態、危急通知送達、長期記憶、每日摘要、帳號綁定）看不到。
3. **內測開關分散**：內測相關旗標散在 `.env` 各處（`ASR_BACKEND`、`TTS_BACKEND`、
   `BINDING_GATE_ENABLED`、`ASR_DEBUG_SHOW_TRANSCRIPT`），沒有統一入口。

## 2. 需求釐清結果（Leo 核定）

| 議題 | 決定 |
| :--- | :--- |
| 一機雙端的「同時」 | 快速切換即可（不做雙 App 並存、不做網頁版）；此功能為**內測專用**，不得流入正式版行為 |
| 內測裝置環境 | Android＋Expo Go、Android＋自建 APK、iPhone＋Expo Go（無 TestFlight） |
| 後台要補的數據 | 四類全要：提醒與排程、危急通知送達、記憶與摘要、帳號與綁定 |
| 內測語音組態 | 全真：`ASR_BACKEND=dgx`＋`TTS_BACKEND=dgx`，與正式相同，不為內測切 mock |
| 排程類功能怎麼測 | 後台加「手動觸發」按鈕（內測模式限定），不做時間加速機制 |
| 總開關架構 | **後端單一開關**，App 經 API 得知內測模式（自建 APK 環境變數 build 時固定、改不了；後端 `.env` 隨時可改） |

## 3. 設計

### 3.1 內測總開關（地基）

- `.env`／`.env.example` 新增 `INTERNAL_TESTING_ENABLED=false`（預設關；`config.py` 對應欄位
  `internal_testing_enabled`）。布林鍵沿用專案 `_ENABLED` 後綴慣例；此鍵為跨子系統平台旗標，
  屬新前綴，需補記到命名決策表（`2026-07-03-naming-decisions.md`）。
  注意 `KINSUN_` 前綴保留給測試／CI，不可用於此鍵。
- 新增**公開端點** `GET /api/v1/meta`，回 `{"internal_testing": true|false}`。
  無需認證（只洩漏一個布林，風險可忽略）；為聚合資訊端點，路徑單數（同 `/health-report` 慣例）。
- App 啟動時打一次 meta（`SessionProvider` 或 root layout），取不到一律當 `false`（fail-safe）。
- 總開關管兩件事：App 快速切換器顯示與否（§3.2）、後台手動觸發按鈕與 API 開放與否（§3.4）。
- `.env.example` 重排出「內部測試」區塊，集中 `INTERNAL_TESTING_ENABLED`、
  `ASR_DEBUG_SHOW_TRANSCRIPT`（內測建議 `true`，觀察 ASR 品質）、`BINDING_GATE_ENABLED`
  （內測維持 `true`，照走正式綁定流程），並以註解說明內測標準組態＝語音全真。
- `app/.env.example` 不新增鍵（切換器由後端下發，APK 不用重 build），
  僅補註解：內測時把 `EXPO_PUBLIC_API_URL` 指向內測伺服器。

### 3.2 App 快速切換身分（內測專用）

- **儲存層**（`app/src/lib/auth.ts`）：單一 key 改**雙 slot**——
  `kinsun_session_elder`、`kinsun_session_guardian`，另存「目前身分」指標。
  登入只寫自己的 slot、不覆蓋對方；登出只清自己的 slot。
  讀到舊 key `kinsun_session` 時依其 `role` 自動搬遷到對應 slot 後刪除舊 key。
  正式版行為不變：單人只會有一個 slot 有資料，UI 無感。
- **切換器 UI**：長輩端（`elder/talk`）與家屬端（`guardian/home`）各放一個
  「切換身分（內測）」小按鈕，**僅內測模式顯示**（由 meta 下發判斷）。
  點擊：對方 slot 已有登入→直接切換並導向該端首頁；沒有→導向該端登入／綁定頁。
- **一人一機配對流程**（全用現有功能）：家屬註冊→建長輩檔→畫面顯示綁定碼→切換身分→
  長輩綁定頁**手動輸入**綁定碼（自己的手機掃不到自己的螢幕；`elder/bind.tsx` 已支援手動輸碼）→
  完成後兩身分並存快切。

### 3.3 後台觀測強化（唯讀）

頁面編排：以長輩為中心＋一個全域系統頁。

- **長輩詳情頁改分頁（tabs）**，現有時間軸為第一個 tab，新增三個：
  - **提醒設定**：用藥主檔（`medications`：名稱＋時段）、回診設定（`appointments`）、
    近期提醒發送紀錄（`reminder_logs`）。
  - **記憶與摘要**：長期記憶清單（Mem0，collection `kinsun_memories`）＋
    每日對話摘要（`conversation_summaries`）。
  - **帳號與綁定**：綁定通道（`channel_bindings`）、邀請碼（`invites`：狀態／過期／嘗試次數）、
    同意紀錄（`consents`）、長輩帳號有無設定（`elder_accounts`）、
    token 概況（`api_tokens`：建立時間、是否撤銷；DB 僅存雜湊，無明文疑慮）。
- **新頂層頁「系統」**：所有排程任務（`scheduler_state`）＋上次執行時間。
- **危急通知送達**：擴充單輪鏈路頁與時間軸的風險事件區塊，
  補「通知了哪些家屬、每位成功／失敗」（`risk_notification_logs`）。
- **後端新增唯讀 admin 端點**（沿用 `X-Admin-Key`＋`require_admin` 守門）：
  - `GET /api/v1/admin/elders/{elder_id}/reminders`（用藥＋回診＋近期發送紀錄）
  - `GET /api/v1/admin/elders/{elder_id}/memory`（長期記憶＋每日摘要）
  - `GET /api/v1/admin/elders/{elder_id}/account`（綁定＋邀請碼＋同意＋帳號＋token 概況）
  - `GET /api/v1/admin/jobs`（`scheduler_state` 全表）
  - 風險事件回傳（trace／timeline）擴充 `notifications` 明細
- 新增的查詢方法依持久層三件套慣例（Protocol＋Pg＋Fake）並納入合約測試。

### 3.4 後台手動觸發（內測模式才開）

- `POST /api/v1/admin/jobs/{job_name}/run`：立即執行指定排程任務
  （每日摘要、危急升級檢查、觀測資料清理等）——系統頁每列加「立即執行」鈕。
- `POST /api/v1/admin/elders/{elder_id}/reminders/dispatch`：立即發送該長輩某時段的
  用藥／回診提醒——提醒設定 tab 加「立即發送」鈕。
  （兩端點為 RPC 動作式路徑，屬 admin 內部工具的刻意例外，不套資源命名規範。）
- 實作：web 程序**直接呼叫與 scheduler worker 同一份 job 函式**（同 codebase 同 DB），
  不經 worker；手動觸發**不更新** `scheduler_state`，避免干擾正常排程判斷。
- 守門：`X-Admin-Key` 與 `INTERNAL_TESTING_ENABLED=true` **兩關都過**才放行；
  開關關閉時回 403，前端按鈕也不顯示（後台由同一 meta 資訊判斷模式）。

## 4. 刻意不做的事（取捨）

- 後台不另做帳號系統，全部掛在現有 admin key 機制下（內部工具，夠用）。
- 不做「時間旅行／加速排程」機制（侵入正式邏輯、風險高），以手動觸發取代。
- App 切換器不做兩個以上帳號的通用帳號管理（YAGNI，內測兩身分夠用）。
- 不做雙 App 並存 build、不做家屬端網頁版。

## 5. 驗證策略

- 後端單元／整合測試：meta 端點、admin 新端點（Fake store）、手動觸發、
  守門測試（`INTERNAL_TESTING_ENABLED=false` 時 write 端點 403）。
- 新增 store 查詢方法納入 `test_<領域>_store_contract.py` 合約測試
  （Fake 每次跑；Pg 以 `KINSUN_IT=1` 啟用）。
- App 端：雙 slot 儲存邏輯視 `app/` 測試設施現況決定（目前無測試基礎，先確認可行性）；
  切換流程與後台頁面以人工驗證收尾。

## 6. 實作切分（一份 spec、三個實作計畫，依序做）

1. **批①：總開關＋meta 端點＋.env 整理**（地基，最小；含命名決策表補記）
2. **批②：App 快速切換**（依賴批①的 meta）
3. **批③：後台強化**（最大塊；③a 唯讀四類先做，③b 手動觸發後做，③b 依賴批①）

## 7. 開放事項（實作時確認）

- Mem0 依長輩列出記憶的 API（`get_all` 過濾 user）實際介面與效能。
- 排程 job 函式在 web 程序直接執行的相依確認（推播通道、設定載入路徑）。
- `app/` 是否引入輕量測試設施（僅為雙 slot 邏輯；若成本高則人工驗證）。
- App 回合在單輪鏈路頁的呈現：App 對話走共用 inbound 管線有進觀測表，
  但「Webhook 收到」步驟為 LINE 語彙，內測時確認 App 回合顯示是否合理。

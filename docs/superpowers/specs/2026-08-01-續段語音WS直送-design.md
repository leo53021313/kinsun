# 續段語音改 WebSocket 直送

> **日期**：2026-08-01
> **狀態**：待 Leo 審查（v2——插嘴語意改回「維持併發＋補播」，見 §3）
> **目的**：消除長輩聽回覆時段與段之間的空白。續段語音改由後端主動從既有 WebSocket 推送，不再繞 Supabase。**併發對話與插嘴補播的既有行為完全保留。**

---

## 1. 背景

### 1.1 Leo 實際踩到的症狀

Leo 回報「分段輸出語音效果感覺沒有很好」。追程式碼與生產觀測後定位到確切原因。

### 1.2 根因：續段的音檔要等前一段播完才開始下載

`web/src/elder/useTalk.ts::advanceQueue`：

```js
prefetchNext(queue);                        // 預取的是「網址」
playingUriRef.current = chunk.audio_url;
player.replace({ uri: chunk.audio_url });   // 瀏覽器到這一行才開始下載音檔
player.play();
```

`elder/api.ts::getTurnChunk` 回的是 JSON `{audio_url}`——一個 Supabase 簽章網址，**不是音檔位元組**。所以「預取」只預取到網址；真正的下載發生在 `player.replace()` 設 `src` 之後，而那一刻前一段已經播完。**每一段之間都有一個下載空白。**

`useTalk.ts` 的既有註解寫著「一邊播這段一邊取下一段，段與段之間才不會空掉」——意圖正確，但「取」只取到網址。

### 1.3 加重因素一：續段整條路徑繞了 Supabase

生產觀測（Opik 專案 `kinsun`，`turn_chunk` trace，n=57）：

| | 值 |
|---|---|
| 伺服器端耗時 | **中位 3.13s**、最慢 11.10s、最快 0.30s |
| index 分布 | `{1: 52, 2: 5}` |
| 錯誤 | 2 筆 `409 chunk_superseded`（那一輪的續段直接消失） |

單筆 trace 的 span 拆解：

```
turn_chunk              3.10s
├─ shortterm_recent     0.21s   ← Supabase 讀今天最後一則回覆
├─ (TTS 合成)           2.49s
└─ audio_upload         0.40s   ← 上傳 Supabase
                                ＋ 前端再從 Supabase 下載（未納入 trace）
```

再加上兩趟隧道 HTTP 往返。**「分段」這個想法不是問題，每一段都繞一趟 Supabase 才是。**

### 1.4 加重因素二：第 2 段起的預算窄到不合理

`advanceQueue` 在段 N **開始播**時才 `prefetchNext(段 N+1)`，所以段 N+1 的預算等於段 N 的時長。

實測（2026-08-01，GB10 無 GPU 共租，n=5）：

| | 合成 | 音訊 |
|---|---|---|
| p50 段0（33 字） | 4.46s | 7.92s |
| p50 段1（14 字） | 2.26s | **3.16s** |
| p90 段0（41 字） | 5.05s | 9.24s |
| p90 段1（30 字） | 3.56s | 6.00s |
| p90 段2（19 字） | 2.59s | 3.76s |

段 2 的預算只有 3.16 秒，而伺服器端光是產出它就要 3.13 秒（中位）——還沒算網路。

### 1.5 為什麼不直接做 TTS 串流

同日實測 `Fun-CosyVoice3-0.5B-2512` 的 `stream=True`：**技術上完全可行**（首塊 3.0s、每塊 4.0 秒音訊、24 kHz、10 次串流 0 個播放斷點），音質也無損（見附錄 A）。

但收益在「已經做過分段優化」的前提下被吃掉大半：

| 首個聲音 | p50 | p90 | GPU 總佔用（p50 / p90） |
|---|---|---|---|
| 現況分段 | 4.46s | 5.05s | 6.72s / 11.20s |
| 本設計（續段 WS 直送） | 4.46s | 5.05s | 6.72s / 11.20s |
| TTS 串流 | 3.03s | 3.01s | **7.89s / 15.23s（+17〜36%）** |

串流多買到 1.4〜2.0 秒首聲，代價是傳輸格式重做、前端播放重寫、`X-Duration-Ms` 契約破裂、GPU 多佔 17〜36%（而 `TTS_MAX_CONCURRENCY=1` ＋ `QueuedTtsClient` 序列化，多佔的時間會轉嫁給排隊的人）。

**本設計解掉段間空白這個實際毛病；串流留待回覆長度顯著變長時再評估**——那時串流首聲仍是 3.0s，分段做法會退化到 5s 以上。

## 2. 目標

1. **段與段之間沒有空白**：續段在前一段還在播的時候就已經躺在瀏覽器裡
2. **既有的併發對話與插嘴補播行為完全保留**（見 §3 D-1）
3. **移除 REST 續拉**：`GET /turns/chunks/{index}` 端點與前端 `ChunkQueue` 拉取邏輯退場

### 非目標

- TTS 串流（`stream=True`）——見 §1.5
- 首段切短（在逗號切以提早首聲）——獨立工項，需試聽確認語氣，見 §8.2
- 改變插嘴語意——見 §3 D-1
- 動 LINE 通道——LINE 不分段，不受影響

## 3. 決策紀錄（Leo，2026-08-01）

| # | 決定 | 理由 |
|---|---|---|
| D-1 | **維持併發對話＋插嘴補播**，本次不改插嘴語意 | 長輩「順便再問一件事」時兩題都該有答案。這是 `spec 2026-07-28 P3` 建立的行為，也是 commit `27b9c7c` 的裁決 |
| D-2 | 續段**計入容量閘門名額** | 續段一樣打 GPU，閘門要擋的就是這個；放外面會讓閘門低估實際負載 |
| D-3 | 降級路徑（`POST /turns`）**不分段** | 保留分段的話前端得留整套 REST 續拉邏輯，簡化就白做。降級路徑首聲 4.46s→5.97s 可接受 |
| D-4 | **補播的單位從「一則音檔」改成「一輪回覆」** | 見 §6.3——不改的話續段直送會讓補播上限在單一輪內就被擠爆 |

### 3.1 曾考慮並否決：真打斷全丟

設計過程中曾傾向改為「插嘴即取消所有在途輪」（HF speech-to-speech 的 `CancelScope` 做法），理由是前端可大幅簡化（883→約 700 行）且與未來串流化天然相容。

**Leo 否決**，理由是它會拿掉這個互動：

```
長輩：幫我搜尋今天的新聞
金孫：好，我幫您看看最近的新聞喔
長輩：順便幫我查一下今天天氣
金孫：好，我幫您看一下天氣喔
金孫：今天天氣……            ← 快的先回
金孫：對了，您剛剛問的新聞喔…  ← 慢的後回，帶回指
```

真打斷之下只有最後一題會有答案。**簡化是工程上的好處，不是產品上的。**

⚠️ 一併查證：**HF speech-to-speech 也做不到上面那個互動**，所以「照抄它的取消機制」並不是在追上參考專案，而是把我們既有的優勢丟掉。他們是嚴格單軌：

- 預設（`interrupt_response: true`）＝真打斷，只有最後一題有答案
- 關掉打斷（`interrupt_response: false`）＝新語音照轉寫，但 `response.py:150` 直接擋下並行生成（`conversation_already_has_active_response`），第二題只能排隊等第一題講完
- Out-of-band responses（`conversation: "none"`）能並行，但**不進主對話、不出聲音**，用途是摘要／標題等側任務

（另註：他們的 `speculative_turns` 處理的是「同一句話講到一半停頓後續講」，不是兩個問題並行——名字容易誤導。）

我們的 `_InFlight` 併發、逐工具預錄安撫話、`pending_utterances` 在途清單、`_LATE_REPLY_DIRECTIVE` 晚到回指，HF 四項皆無。

⚠️ 一併記下：**修「段間空白」不需要改插嘴語意**，兩者是獨立的。續段帶 `turn_id`，前端照輪次分辨即可。

## 4. 協定變更

### 4.1 下行新增：`chunk` binary frame

複用既有 `ws.py::encode_reply_frame`——4 bytes 大端序 header 長度 ＋ UTF-8 JSON header ＋ m4a bytes。

```json
{
  "type": "chunk",
  "turn_id": "...",
  "index": 1,
  "text": "要去市場記得多喝水、防曬喔！",
  "duration_ms": 3160,
  "is_last": true
}
```

- `index` 從 1 起（第 0 段隨既有 `reply` frame 送出）
- `is_last` 讓前端知道這一輪的語音結束，不必自己數
- `turn_id` **是必要的**：併發之下同時可能有多輪在推段，前端要照它歸屬（既有的 `playingTurnIdRef` / `ChunkQueue.turnId` 機制就是為此存在，見 commit `459051f`）
- **前端 `parseAudioFrame` 一行都不用改**：它只要求 `turn_id` 是字串

### 4.2 上行協定不變

D-1 之下不需要取消訊息。`sendLocation` 與 `sendAudio` 一字不動，**沒有向後相容風險**。

### 4.3 既有 `reply` frame 不變

`chunk_count` 與 `reply_digest` 都保留。前端不再據 `chunk_count` 發起 REST 續拉（改為被動接收 `chunk` frame），但欄位留著——舊版前端仍能解析，且 `reply_digest` 在 POST 降級路徑仍是輪次識別（見 `useTalk.ts` 對 `TurnReply` 無 `turn_id` 的處理）。

## 5. 後端設計

### 5.1 續段合成與推送（`channels/app/ws.py`）

`_run_turn` 在第一段送出（`collector.audio_sent` 為真）之後，於**同一個工作執行緒**接著跑：

```python
chunks = split_for_speech(collector.text)
for index, text in enumerate(chunks[1:], start=1):
    with tts_priority(TtsPriority.CHUNK):
        result = tts.synthesize(text)
    sender.send_chunk_audio(
        header_for(turn_id, index, text, result, is_last=index == len(chunks) - 1),
        result.audio,
    )
```

**為什麼在 `ws.py` 自己切而不改 `TtsResult` 協定**：`split_for_speech` 是純函式，同樣輸入必得同樣輸出。既有的 `get_turn_chunk` 就是這樣做的（`chunks = split_for_speech(reply)`）。改協定會波及所有測試替身，換不到任何東西。

**優先權維持 `TtsPriority.CHUNK`**：長輩正在聽第一段，續段有餘裕；別位長輩的第一段（`REPLY`）應該先做。

**推送失敗只記 warning、不中斷**：與 `_Sender.send` 同一條紀律——連線斷掉不該讓後續落庫炸掉。這與第一段的 `send_reply_audio`（失敗要往外拋、讓投遞層退回文字）不同，因為第一段失敗代表長輩什麼都收不到，續段失敗他至少聽到了開頭。

### 5.2 產出序列必須有終止訊號

前端靠 `is_last` 判斷「這一輪的語音講完了」。若續段合成中途失敗（`TTSError`），迴圈中斷，`is_last` 永遠不會送出，前端會把這一輪當成還沒結束。

故續段迴圈**無論如何都要送出終止訊號**：正常結束時最後一段帶 `is_last: true`；中途失敗時補送一個空音檔的 `chunk` frame（`text` 為空、bytes 長度 0、`is_last: true`），前端據此結束該輪。

### 5.3 容量閘門（D-2）

續段迴圈放在 `turn_gate.admit()` **之內**。

影響：一輪佔用閘門的時間從約 4.46s 變成約 6.7s（p50）／11.2s（p90），閘門更容易滿、`queued` 訊框更常出現。這是刻意的——閘門要反映的就是實際 GPU 負載。

⚠️ 與併發的交互：`_MAX_CONCURRENT_TURNS = 3`，三輪同時跑續段時 GPU 排隊會明顯變長。`TtsPriority.CHUNK` 保證別位長輩的第一段仍優先，但同一位長輩的三輪之間沒有優先序。實測若太吵，調 `TURN_CONCURRENCY_LIMIT` 而非把續段移出閘門。

### 5.4 降級路徑不分段（D-3）

`pipeline._synthesize` 目前以 `channel in self._chunked_channels` 決定分不分段，而 WS 與 `POST /turns` 都是 `Channel.APP`，分不出來。

改以「這一輪走不走內嵌音檔路徑」判定——`InboundMessage.reply_audio is not None`，C1 已經用這個訊號分辨（見 `inbound.py::deliver`）。

連帶：

- `GET /api/v1/turns/chunks/{index}` 端點**移除**
- `ErrorCode.CHUNK_NOT_FOUND` / `CHUNK_SUPERSEDED` 移除

⚠️ **`speech/chunking.py::reply_digest` 保留、不移除**：`inbound.py::chunk_info` 仍在算它、`reply` frame 與 `POST /turns` 回應仍帶它（§4.3）。只有 `turns.py:288` 的 digest 比對隨端點一起消失。

### 5.5 觀測

續段推送納入既有 `tts` span，header 帶 `index`。`turn_chunk` trace 隨端點移除——續段的耗時改由 `care_turn_voice` 這棵樹涵蓋，這順帶修掉「續拉在 Opik 生出孤兒 root trace」那個既有問題的另一半。

## 6. 前端設計（`web/`）

### 6.1 移除

| 檔案 | 移除 |
|---|---|
| `elder/useTalk.ts` | `prefetchNext`、`advanceQueue` 的**拉取**分支、`ChunkQueue` 的 `nextIndex`／`pending`／`digest` 欄位 |
| `elder/api.ts` | `getTurnChunk`、`TurnChunk` 型別 |

### 6.2 新增

- `talkSocket.ts`：`TalkFrame` 加 `chunk` variant
- `useTalk.ts`：收到 `chunk` frame → 依 `turn_id` 歸屬後推進播放佇列；`is_last` 標記該輪語音結束

### 6.3 ⚠️ 補播的單位改成「一輪」（D-4）

**這是 A 方案下必須解決的新問題，不是可選項。**

現況 `deferredRepliesRef` 上限 **2 則**，commit `27b9c7c` 的理由是「一輪最多 ack＋reply」。續段直送之後，**一輪會產生 ack＋reply＋chunk1＋chunk2… 四則以上**——上限 2 在**單一輪之內**就會被擠爆。

症狀：長輩插嘴後補播，只聽到那一輪的最後兩則（例如 chunk1＋chunk2），**答案的開頭被擠掉了**。比原本「整題沒有答案」更難理解。

改法：

```ts
type DeferredTurn = { turnId: string; items: PlaybackItem[] };
const deferredTurnsRef = useRef<DeferredTurn[]>([]);   // 上限 2 「輪」
```

- 收音期間抵達的 frame 依 `turn_id` 歸到對應的 `DeferredTurn`（沒有就新建）
- 超過 2 輪 → 擠掉**最舊那一輪**（整輪，連同其所有音檔一起回收）
- 錄音結束 → 依 FIFO 把各輪的 `items` 依序放回播放佇列

⚠️ 收音期間該輪的續段**仍會繼續推過來**（後端不知道長輩在講話），要繼續歸到同一個 `DeferredTurn`，不可另開一輪。

### 6.4 保留不動

`playingTurnIdRef`、`canTakeOverSubtitle`、`ChunkQueue.turnId` 的輪次比對、`playAndWait` 保險逾時、`abortPlaybackRef` 中止賽跑、`THINKING_TIMEOUT_MS`、iOS 音訊解鎖時機、`_LATE_REPLY_DIRECTIVE` 晚到回指、`pending_utterances` 在途清單。

**併發對話的全套機制原封不動。**

## 7. 記憶

**不需要任何改動。**

補播保證長輩最終會聽到那一輪的回覆，所以 `turns` 表記的內容與長輩實際聽到的一致。

⚠️ 唯一的例外是 §6.3 的溢位（同時超過 2 輪在等補播，最舊那輪被擠掉）——那一輪長輩不會聽到，但記憶記著。這是 commit `27b9c7c` 就存在的既有取捨（「沒有上限的話連續插嘴會累積成一串舊語音」），本設計不擴大也不縮小它；D-4 把單位改成「輪」之後，觸發門檻反而**比現在更寬**（原本 2 則、現在 2 輪）。

## 9. 測試

### 後端

| 案例 | 守住什麼 |
|---|---|
| 續段依序推出、`index` 遞增、最後一段 `is_last=true` | 基本行為 |
| 每個 `chunk` frame 都帶正確的 `turn_id` | §4.1——併發之下前端靠它歸屬，錯了會把 A 的段接到 B 後面 |
| 續段合成失敗時補送空音檔的 `is_last` frame | §5.2 |
| 續段推送失敗只記 warning、不影響已完成的落庫 | §5.1 |
| 只有一段時不推任何 `chunk` frame | 邊界 |
| 降級路徑（`reply_audio is None`）回整段、不分段 | D-3 |
| 併發三輪各自推自己的續段、互不干擾 | D-1 |

### 前端

| 案例 | 守住什麼 |
|---|---|
| 收到 `chunk` frame → 依 `turn_id` 歸屬、依序播 | 基本行為 |
| 兩輪的 `chunk` 交錯抵達時各自歸位、不混播 | §4.1 |
| 空音檔的 `is_last` frame → 結束該輪、不進播放佇列 | §5.2 |
| **收音期間一輪的四則以上全部收進同一個 `DeferredTurn`** | §6.3——這是 D-4 的核心 |
| **補播佇列滿時擠掉最舊那一「輪」（不是最舊那一「則」）** | §6.3 |
| 被擠掉的整輪音檔全部回收，還要播的不受影響 | §6.3；`revokeReplyAudio` 的既有理由同樣適用 |
| `reply` 的 `chunk_count` 不再觸發任何 REST 請求 | §4.3 |

⚠️ 逐條變異驗證（本專案慣例）：每條測試都要確認拿掉對應實作後真的變紅。

## 附錄 A：TTS 串流的音質實測（2026-08-01）

雖然本次不做串流，這份數據值得留存——它排除了「串流會讓音質語調跑掉」這個顧慮。

方法：固定 `torch.manual_seed`，同一段文字分別以 `stream=True` / `stream=False` 合成。長度完全相同（10.20s vs 10.20s；p90 為 17.00s vs 17.00s），證實語音 token 一致，差異純粹來自 flow-matching 的分塊解碼。

| 比較 | 梅爾距離（越小越像） |
|---|---|
| 同種子的兩次非串流 | **0.0000**（模型在固定種子下是確定性的） |
| 非串流 vs 串流（同種子） | **0.4400** |
| 不同種子的兩次非串流＝同一句話的兩種自然唸法 | **4.8717** |

**串流造成的差異是模型自身正常變異的 1/11。**

接縫檢查（串流輸出自身，不需參考組）：

```
一般相鄰音框跳變：平均 0.986，第 95 百分位 2.371
接縫 @ 1.35s：0.506  ✅ 在正常範圍
接縫 @ 3.36s：1.006  ✅ 在正常範圍
接縫 @ 7.36s：0.408  ✅ 在正常範圍
```

三個接縫的跳變都低於平均——CosyVoice 的分塊解碼有做重疊淡接。

⚠️ 梅爾距離是代理指標，不是聽覺判斷。配對音檔已產出供人工試聽（scratchpad，未進版控）。

⚠️ 方法上的教訓：第一版用**取樣點相關係數**比對，得到 −0.03，看起來像「完全不一樣」。那是錯的工具——神經聲碼器的輸出必須比聽覺特徵，不能比取樣點。

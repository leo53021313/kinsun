# 續段語音改 WebSocket 直送、插嘴改真打斷

> **日期**：2026-08-01
> **狀態**：待 Leo 審查
> **目的**：消除長輩聽回覆時段與段之間的空白。續段語音改由後端主動從既有 WebSocket 推送，不再繞 Supabase；同時把插嘴語意從「補播」改為「真打斷全丟」，讓一次只有一輪是活的。

---

## 1. 背景

### 1.1 Leo 實際踩到的症狀

Leo 回報「分段輸出語音效果感覺沒有很好」。追程式碼與生產觀測後定位到確切原因。

### 1.2 根因：續段的音檔要等前一段播完才開始下載

`web/src/elder/useTalk.ts::advanceQueue`：

```js
prefetchNext(queue);                        // 預取的是「網址」
playingUriRef.current = chunk.audio_url;
player.replace({ uri: chunk.audio_url });   // 瀏覽器到這一行才開始下載音檔
player.play();
```

`elder/api.ts::getTurnChunk` 回的是 JSON `{audio_url}`——一個 Supabase 簽章網址，**不是音檔位元組**。所以「預取」只預取到網址；真正的下載發生在 `player.replace()` 設 `src` 之後，而那一刻前一段已經播完。**每一段之間都有一個下載空白。**

`useTalk.ts` 的既有註解寫著「一邊播這段一邊取下一段，段與段之間才不會空掉」——意圖正確，但「取」只取到網址。

### 1.3 加重因素一：續段整條路徑繞了 Supabase

生產觀測（Opik 專案 `kinsun`，`turn_chunk` trace，n=57）：

| | 值 |
|---|---|
| 伺服器端耗時 | **中位 3.13s**、最慢 11.10s、最快 0.30s |
| index 分布 | `{1: 52, 2: 5}` |
| 錯誤 | 2 筆 `409 chunk_superseded`（那一輪的續段直接消失） |

單筆 trace 的 span 拆解：

```
turn_chunk              3.10s
├─ shortterm_recent     0.21s   ← Supabase 讀今天最後一則回覆
├─ (TTS 合成)           2.49s
└─ audio_upload         0.40s   ← 上傳 Supabase
                                ＋ 前端再從 Supabase 下載（未納入 trace）
```

再加上兩趟隧道 HTTP 往返。**「分段」這個想法不是問題，每一段都繞一趟 Supabase 才是。**

### 1.4 加重因素二：第 2 段起的預算窄到不合理

`advanceQueue` 在段 N **開始播**時才 `prefetchNext(段 N+1)`，所以段 N+1 的預算等於段 N 的時長。

實測（2026-08-01，GB10 無 GPU 共租，n=5）：

| | 合成 | 音訊 |
|---|---|---|
| p50 段0（33 字） | 4.46s | 7.92s |
| p50 段1（14 字） | 2.26s | **3.16s** |
| p90 段0（41 字） | 5.05s | 9.24s |
| p90 段1（30 字） | 3.56s | 6.00s |
| p90 段2（19 字） | 2.59s | 3.76s |

段 2 的預算只有 3.16 秒，而伺服器端光是產出它就要 3.13 秒（中位）——還沒算網路。

### 1.5 為什麼不直接做 TTS 串流

同日實測 `Fun-CosyVoice3-0.5B-2512` 的 `stream=True`：**技術上完全可行**（首塊 3.0s、每塊 4.0 秒音訊、24 kHz、10 次串流 0 個播放斷點），音質也無損（見附錄 A）。

但收益在「已經做過分段優化」的前提下被吃掉大半：

| 首個聲音 | p50 | p90 | GPU 總佔用（p50 / p90） |
|---|---|---|---|
| 現況分段 | 4.46s | 5.05s | 6.72s / 11.20s |
| 本設計（續段 WS 直送） | 4.46s | 5.05s | 6.72s / 11.20s |
| TTS 串流 | 3.03s | 3.01s | **7.89s / 15.23s（+17〜36%）** |

串流多買到 1.4〜2.0 秒首聲，代價是傳輸格式重做、前端播放重寫、`X-Duration-Ms` 契約破裂、GPU 多佔 17〜36%（而 `TTS_MAX_CONCURRENCY=1` ＋ `QueuedTtsClient` 序列化，多佔的時間會轉嫁給排隊的人）。

**本設計解掉段間空白這個實際毛病；串流留待回覆長度顯著變長時再評估**——那時串流首聲仍是 3.0s，分段做法會退化到 5s 以上。

## 2. 目標

1. **段與段之間沒有空白**：續段在前一段還在播的時候就已經躺在瀏覽器裡
2. **一次只有一輪是活的**：長輩插嘴即真打斷，後端停止合成剩餘段落，前端丟棄未播內容
3. **簡化**：移除 REST 續拉端點、前端 `ChunkQueue`、補播佇列及其配套

### 非目標

- TTS 串流（`stream=True`）——見 §1.5
- 首段切短（在逗號切以提早首聲）——獨立工項，需試聽確認語氣，見 §8.2
- 修正記憶與「長輩實際聽到的內容」之間的落差——**本次刻意不做**，見 §7
- 動 LINE 通道——LINE 不分段，不受影響

## 4. 協定變更

### 4.1 下行新增：`chunk` binary frame

複用既有 `ws.py::encode_reply_frame`——4 bytes 大端序 header 長度 ＋ UTF-8 JSON header ＋ m4a bytes。

```json
{
  "type": "chunk",
  "turn_id": "...",
  "index": 1,
  "text": "要去市場記得多喝水、防曬喔！",
  "duration_ms": 3160,
  "is_last": true
}
```

- `index` 從 1 起（第 0 段隨既有 `reply` frame 送出）
- `is_last` 讓前端知道這一輪的語音結束，不必自己數
- **前端 `parseAudioFrame` 一行都不用改**：它只要求 `turn_id` 是字串

### 4.2 上行新增：`cancel`

```json
{ "type": "cancel" }
```

不帶 `turn_id`——長輩按麥克風的語意是「全部閉嘴」，不是取消特定一輪。

⚠️ **向後相容的關鍵**：現有 `talkSocket.ts::sendLocation` 送的 JSON **沒有 `type` 欄位**。後端以「有沒有 `type`」分派：

- 有 `type` → 走新協定（目前只有 `cancel`；未知的 `type` 記 warning 後忽略）
- 沒有 `type` → 當成位置訊框，`_parse_location` 行為一字不動

這道分派同時替未來的第三種上行訊息留了位置。

### 4.3 既有 `reply` frame 的 `chunk_count`

保留欄位不刪（避免舊前端版本解析失敗），但**前端不再據它做任何事**——續段改由後端主動推。

## 5. 後端設計

### 5.1 續段合成與推送（`channels/app/ws.py`）

`_run_turn` 在第一段送出（`collector.audio_sent` 為真）之後，於**同一個工作執行緒**接著跑：

```python
for index, text in enumerate(split_for_speech(collector.text)[1:], start=1):
    if cancellation.is_cancelled():
        break
    with tts_priority(TtsPriority.CHUNK):
        result = tts.synthesize(text)
    sender.send_chunk_audio(header_for(index, text, result, is_last), result.audio)
```

**為什麼在 `ws.py` 自己切而不改 `TtsResult` 協定**：`split_for_speech` 是純函式，同樣輸入必得同樣輸出。既有的 `get_turn_chunk` 就是這樣做的（`chunks = split_for_speech(reply)`）。改協定會波及所有測試替身，換不到任何東西。

**優先權維持 `TtsPriority.CHUNK`**：長輩正在聽第一段，續段有餘裕；別位長輩的第一段（`REPLY`）應該先做。

**推送失敗只記 warning、不中斷**：與 `_Sender.send` 同一條紀律——連線斷掉不該讓後續落庫炸掉。這與第一段的 `send_reply_audio`（失敗要往外拋、讓投遞層退回文字）不同，因為第一段失敗代表長輩什麼都收不到，續段失敗他至少聽到了開頭。

### 5.2 容量閘門（D-2）

續段迴圈放在 `turn_gate.admit()` **之內**。

影響：一輪佔用閘門的時間從約 4.46s 變成約 6.7s（p50）／11.2s（p90），閘門更容易滿、`queued` 訊框更常出現。這是刻意的——閘門要反映的就是實際 GPU 負載。

### 5.3 取消機制（`channels/app/ws.py`）

借 HF speech-to-speech `pipeline/cancel_scope.py` 的世代編號設計，掛在**連線**上（比照 `_InFlight`）：

```python
class _Cancellation:
    """這條連線上的取消訊號。長輩一開口，所有在跑的輪都作廢。"""
    def cancel_all(self) -> None: ...
    def is_cancelled(self) -> bool: ...
    def reset(self) -> None: ...   # 新一輪開始時清除
```

- 讀迴圈收到 `{"type": "cancel"}` → `cancel_all()`
- 讀迴圈收到新音檔（新一輪開始）→ `reset()`
- 續段迴圈**每段開始合成前**檢查

⚠️ **粒度限制必須載明**：正在合成的那一段停不下來（`tts.synthesize` 是原子的），最多浪費約 2.26 秒 GPU。這是分段做法的固有限制——串流才能做到句中停（每產出一塊檢查一次）。

#### 5.3.1 取消也必須擋住「還沒送出的第一段」

⚠️ 初稿只讓取消擋續段，那不足以達成 D-1。`_MAX_CONCURRENT_TURNS = 3`，長輩問完 A 又問 B 時，**A 那一輪的運算仍在跑**；若取消只管續段，A 算完後第一段照樣推出去，長輩會在講完 B 之後聽到 A 的答案——那正是 D-1 要消滅的行為。

故 `_TurnCollector.reply_audio` 在推送前也要檢查取消：已作廢就不推（並記一筆 log，供 §5.5 的計數統計「有多少輪被整輪丟棄」）。

#### 5.3.2 產出序列必須有終止訊號

前端靠 `is_last` 判斷「這一輪的語音講完了、可以回到待機」。若續段合成中途失敗（`TTSError`），迴圈中斷，`is_last` 永遠不會送出，前端會卡在「說話中」直到 `THINKING_TIMEOUT_MS`（75 秒）。

故續段迴圈**無論如何都要送出終止訊號**：正常結束時最後一段帶 `is_last: true`；中途失敗時補送一個空音檔的 `chunk` frame（`text` 為空、bytes 長度 0、`is_last: true`），前端據此回到待機。

取消不需要補送——取消是前端發起的，它自己已經回到待機。

### 5.4 降級路徑不分段（D-3）

`pipeline._synthesize` 目前以 `channel in self._chunked_channels` 決定分不分段，而 WS 與 `POST /turns` 都是 `Channel.APP`，分不出來。

改以「這一輪走不走內嵌音檔路徑」判定——`InboundMessage.reply_audio is not None`，C1 已經用這個訊號分辨（見 `inbound.py::deliver`）。

連帶：

- `GET /api/v1/turns/chunks/{index}` 端點**移除**
- `ErrorCode.CHUNK_NOT_FOUND` / `CHUNK_SUPERSEDED` 移除

⚠️ **`speech/chunking.py::reply_digest` 保留、不移除**。初稿誤判它「失去唯一消費者」——實際上 `inbound.py::chunk_info` 仍在算它、`reply` frame 與 `POST /turns` 回應仍帶它（§4.3 的向後相容同一理由）。只有 `turns.py:288` 的 digest 比對隨端點一起消失。

### 5.5 觀測

- 續段推送納入既有 `tts` span，header 帶 `index`
- **新增插嘴計數**（D-4 的數據來源）：後端收到 `cancel` 時記一筆結構化 log（`elder_id`、`turn_id`、該輪已推出幾段）。不進資料庫——先用 log 收，量夠了再談落庫

### 6.4 ⚠️ 連帶的產品行為改變：併發對話（P3）不再成立

**這是 §5.3.1 的必然推論，審查時才發現，需要 Leo 確認。**

`spec 2026-07-28 非同步工具調用與並行對話`（P3）建立的行為是：長輩可以連問三件事，**三件都會有答案**，慢的那個回來時金孫會帶一句回指（「對了，您剛剛問的那個喔」）。

D-1 ＋ §5.3.1 之後：長輩一按麥克風就取消所有在途的輪，**只有最後問的那件事會有答案**。

連帶失效的機制：

| 機制 | 狀態 |
|---|---|
| `_LATE_REPLY_DIRECTIVE`（晚到回指） | **變成死碼**——晚到的答案已被取消，永遠不會投遞 |
| `_InFlight.is_latest` | 只服務上者，跟著死 |
| `_MAX_CONCURRENT_TURNS = 3` | 仍需要（防連按耗盡資源），但語意從「支援三輪併發對話」降為「同時最多算三輪，但只有最後一輪會被聽到」 |
| `pending_utterances`（在途清單） | **仍然有用，保留**——新的一輪組裝情境時要看得到長輩剛問過什麼，「那天氣呢」的指代靠它 |

本設計**先不刪**那些變成死碼的機制（`_LATE_REPLY_DIRECTIVE`、`_InFlight.is_latest`），只在程式碼註解標明它們在 D-1 之下不再會被觸發——若日後 Leo 想恢復併發對話，刪掉會讓復原成本變高。⚠️ 但也不可放著不標，否則下一個人會以為回指還在運作。

## 7. 已知落差（刻意不修，D-4）

⚠️ **記憶會記下長輩沒聽到的回覆。**

時序（已驗證）：

```
agent.handle 產生回覆
  └→ _record_turn_background 啟動背景寫入 turns   ← 記憶在這裡就進去了
_synthesize 合成第一段（4.46s）
_settle_memory_write 等它落地                     ← 通常早就寫完
推給前端 → 開始播
長輩插嘴                                          ← 記憶已在資料庫裡
```

**「插嘴就不寫記憶」做不到**——濫用審核那條路能做到「不寫」是因為它排在 `agent.handle` 之前；插嘴排在之後。只能事後修正。

擴散途徑：長期記憶（Mem0）由夜間批次從 `previous_day()` 萃取（`memory/longterm/consolidation.py:68`），所以短期記憶留著未聽到的內容，**當晚就會變成長期「事實」**。

具體失效：

- 長輩問「藥要吃幾顆」聽一半插嘴 → 明天他問「你昨天說吃幾顆」→ 金孫「我昨天跟您說過早上兩顆呀」。他沒聽到
- 回覆含「我幫您記下來，晚上七點提醒吃藥」→ `create_schedule` 真的執行了，排程存在，長輩沒聽到

**這是本設計引入的新落差**，不是既有問題——現況（補播）下長輩最終會聽到，記憶與事實一致。

**本次不修的理由**：修法（`turns` 表加 `delivered` 欄位、`recent()` 改寫該筆內容）需要動 DDL 並測既有庫升級路徑，而「長輩實際多常插嘴」這個數字目前沒有人知道。先埋計數（§5.5），數據到手再決定。

**不受影響的兩件事**（確認過，寫在這裡免得日後誤判）：

1. **危急偵測與家屬通報不受影響**——它們在 `pipeline._process_transcribed` 排在生成回覆**之前**，插嘴發生在回覆送出之後
2. **工具副作用該留**——排程已經建了就該留著，晚上的提醒照來。長輩沒聽到金孫講，但提醒本來就是他要的

| 收到 `cancel` 後不再推剩下的段 | D-1 |
| `cancel` 在合成中途抵達 → 當前段照樣推完、下一段不做 | §5.3 的粒度限制是刻意的，不是 bug |
| **`cancel` 之後，在途那一輪的「第一段」也不推** | §5.3.1——只擋續段不足以達成 D-1，長輩會在講完 B 之後聽到 A 的答案 |
| **續段合成失敗時補送空音檔的 `is_last` frame** | §5.3.2——沒有它前端會卡在「說話中」75 秒 |
| **位置 JSON（無 `type` 欄位）仍照舊解析** | §4.2 向後相容——這條若紅，所有現有前端的位置功能會靜默失效 |
| 未知 `type` 的上行訊息只記 warning、不切斷連線 | 外部輸入是資料不是指令 |
| 壞掉的 `cancel` JSON 不切斷連線 | 同上 |
| 續段推送失敗只記 warning、不影響已完成的落庫 | §5.1 |
| 只有一段時不推任何 `chunk` frame | 邊界 |
| 降級路徑（`reply_audio is None`）回整段、不分段 | D-3 |

### 前端

| 案例 | 守住什麼 |
|---|---|
| 收到 `chunk` frame → 進播放佇列、依序播 | 基本行為 |
| `is_last` 的那一段播完 → 回到待機 | 不會卡在「說話中」 |
| 按麥克風 → 送 `cancel`、佇列清空、正在播的停 | D-1 |
| `reply` 的 `chunk_count` 不再觸發任何續拉 | §4.3 |
| 補播移除後，收音期間抵達的回覆確實被丟棄 | D-1（推翻 `27b9c7c`） |
| 空音檔的 `is_last` frame → 回到待機、不進播放佇列 | §5.3.2 |

⚠️ 逐條變異驗證（本專案慣例）：每條測試都要確認拿掉對應實作後真的變紅。

## 附錄 A：TTS 串流的音質實測（2026-08-01）

雖然本次不做串流，這份數據值得留存——它排除了「串流會讓音質語調跑掉」這個顧慮。

方法：固定 `torch.manual_seed`，同一段文字分別以 `stream=True` / `stream=False` 合成。長度完全相同（10.20s vs 10.20s；p90 為 17.00s vs 17.00s），證實語音 token 一致，差異純粹來自 flow-matching 的分塊解碼。

| 比較 | 梅爾距離（越小越像） |
|---|---|
| 同種子的兩次非串流 | **0.0000**（模型在固定種子下是確定性的） |
| 非串流 vs 串流（同種子） | **0.4400** |
| 不同種子的兩次非串流＝同一句話的兩種自然唸法 | **4.8717** |

**串流造成的差異是模型自身正常變異的 1/11。**

接縫檢查（串流輸出自身，不需參考組）：

```
一般相鄰音框跳變：平均 0.986，第 95 百分位 2.371
接縫 @ 1.35s：0.506  ✅ 在正常範圍
接縫 @ 3.36s：1.006  ✅ 在正常範圍
接縫 @ 7.36s：0.408  ✅ 在正常範圍
```

三個接縫的跳變都低於平均——CosyVoice 的分塊解碼有做重疊淡接。

⚠️ 梅爾距離是代理指標，不是聽覺判斷。配對音檔已產出供人工試聽（scratchpad，未進版控）。

⚠️ 方法上的教訓：第一版用**取樣點相關係數**比對，得到 −0.03，看起來像「完全不一樣」。那是錯的工具——神經聲碼器的輸出必須比聽覺特徵，不能比取樣點。

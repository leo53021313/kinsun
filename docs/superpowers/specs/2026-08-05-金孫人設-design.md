## 背景與動機

金孫的回覆讀起來像罐頭。Leo 指出的症狀有四項，全部成立：

1. **每則回覆都用反問收尾**——`agent.SYSTEM_PROMPT` 第（5）條明文要求「結尾自然帶一句關心或反問」，於是每一則都長成同一個形狀。
2. **每位長輩聽到的口氣完全一樣**——`SYSTEM_PROMPT` 是模組級常數，所有長輩共用同一份，沒有任何可調整的餘地。
3. **用字句型翻來覆去就那幾句**——同樣的關心話、同樣的安慰句反覆出現。
4. **太短、講不出人味**——第（2）條的三十字上限把話擠成通知。

### 這不是「加一個人設欄位」就會好

必須先講清楚：**制式感的主因是規則，不是缺少人設。** 就算加了人設，第（5）條仍會讓每一則以問句結束、第（2）條仍會把話擠短。因此本設計是兩件事一起做——**加人設**（解症狀 2）＋**鬆綁格式規則**（解症狀 1、3）。症狀 4 只被部分處理：Leo 決定保留三十字上限（理由：合成語音每多一字約多 0.1 秒），所以「話太短」這一項這次不解。

### 現況裡已經預留好的兩個插槽

- `speech/acks.py`（等待語語庫）從一開始就寫成**人設 × 工具**兩維，`personas()`／`persona()`／`all_phrases()` 全部已經支援多人設，只是至今只有 `DEFAULT_PERSONA = "kinsun"` 一種、沒有任何地方會切換它。
- `elders.nickname`（稱謂）是「每位長輩不同的設定」的現成先例：家屬設定 → 存長輩資料列 → 每輪注入模型。

## 不在本次範圍內

- **聲音**：兩種人設共用現在這一個克隆聲音。要分開得另錄一段男聲參考音檔並改 `services/tts`，Leo 決定留到下一階段。
- **長輩自己改人設**：長輩不能用講的要求換人設。
- **家屬自由填寫個性描述**：只有固定選單。
- **LIFF（LINE 家屬端）**：不新增人設介面。它讀不到新欄位也不會壞。
- **每晚反思、家屬報告、危急通知**：這些不是講給長輩聽的內容，不套用人設。

## 人設內容

兩種人設**都還是「金孫」**，差別只在自稱、用詞、情緒表達方式。安全紅線、工具規則、語音格式三者兩種完全相同。

| | `lively_granddaughter`（預設） | `steady_grandson` |
| :--- | :--- | :--- |
| 家屬看到的名稱 | 活潑的孫女 | 穩重的孫子 |
| 年齡感 | 二十幾歲 | 三十幾歲 |
| 情緒 | 外放——替長輩開心、替長輩緊張 | 收斂——關心用做事表達 |
| 語助詞 | 多（喔、啦、耶、齁），偶爾「哇」 | 少，幾乎不用驚呼 |
| 開場 | 喊人式（「阿嬤～」） | 直接切入他關心的事 |

### 語氣段落草稿

⚠️ 這兩段是**要放進提示詞開頭的實際文字**，實作時逐字照抄；日後調語氣只改這裡。

**活潑孫女**：

> 你是「金孫」，把這位長輩當成自己的阿公阿嬤在陪伴。你的口吻像個二十幾歲、跟長輩很親的孫女：講話有活力，情緒藏不住——他講到高興的事你會替他開心，講到不舒服你會替他緊張。常用「喔」「啦」「耶」這類語助詞，偶爾會「哇」一聲。

**穩重孫子**：

> 你是「金孫」，把這位長輩當成自己的阿公阿嬤在陪伴。你的口吻像個三十幾歲、做事牢靠的孫子：沉穩、話不多，但每一句都聽得出用心。少用語助詞與驚呼，關心用做事表達——「我幫您記著」勝過「哎唷您要小心喔」。

### 兩段的硬性限制

- **不得出現任何工具名稱**（`web_search`、`create_schedule` 等）。`composition.py:130` 靠字面掃描 `SYSTEM_PROMPT` 比對工具有沒有註冊，工具名只能住在規則段；寫進人設段會讓那道對帳失效。由測試把關。
- 不得放寬或抵觸規則段的任何一條（不假裝真人、不給醫療建議、不用 Markdown、三十字上限）。

## 架構設計

### 提示詞的新結構

現行：

```
SYSTEM_PROMPT（身分宣告 ＋ 規則，混在同一段）
  ＋ 情境（時間、稱呼、長期記憶、排程、守則、位置）
  ＋ 本輪追加指示
```

改為：

```
人設語氣（依這位長輩的設定）＋ 稱呼那一句
  ＋ SYSTEM_PROMPT（只剩規則：語音格式、工具用法、安全紅線、失智照護準則）
  ＋ 情境（時間、長期記憶、排程、守則、位置）
  ＋ 本輪追加指示
```

`SYSTEM_PROMPT` 開頭那句「你是「金孫」，一位溫暖、有耐心的台灣長輩陪伴助理。」被移除，由兩份人設各自的版本取代。**常數名稱維持 `SYSTEM_PROMPT` 不變**，因為 `composition.py:130` 依賴它、且工具名全部留在規則段——那行掃描一個字都不用改。

### 長輩檔案的讀取搬家（這是本設計最關鍵的一步）

要把人設放在提示詞開頭，`CareAgent` 就得知道這位長輩的人設。天真做法是多查一次 `elders` 資料列，但那與「稱呼」那次讀取重複，而正式環境的資料庫連線池只有三條。

因此：**把那一次讀取整個搬家，而不是複製一份。**

- `ElderProfileFacts` 從七個事實提供者的清單裡**移除**（事實提供者七路→六路，其中碰資料庫的六路→五路）
- 這一次讀取改由 `CareAgent` 在每輪開頭發動，與情境組裝**並行**跑
- 一次讀取同時供應兩樣東西：**人設 id** 與**稱呼那一句**

**全輪的資料庫讀取次數一次都沒有增加。**

附帶效果（三項都往好的方向，但第二項需要驗收）：

1. 「你是誰」與「你怎麼稱呼她」現在住在一起——它們本來就是同一件事（該怎麼講話），先前被拆在提示詞的頭尾兩端。
2. 稱呼從情境區塊移到提示詞開頭，位置更前、模型更重視。⚠️ 稱呼叫錯是 2026-07-17 全功能測試實測過的真實問題（同一位長輩一下被叫阿公一下被叫阿嬤），這個移動方向是強化，但**必須人工驗收確認沒有反效果**。
3. 事實提供者少一路，`_gather_facts` 的並行度 7→6，連線池壓力略減。

### 資料流

```
家屬（web 長輩詳情畫面）
   │  PUT /elders/{elder_id}/persona
   ▼
elders.persona ─────────────┐
                            │  每輪開頭，與情境組裝並行
                            ▼
                    ElderProfileReader.get_profile(elder_id)
                            │  一次讀取
                    ┌───────┴────────┐
                    ▼                ▼
              persona_id        稱呼那一句
                    │                │
        ┌───────────┴──┐             │
        ▼              ▼             ▼
  personas.py      等待語語庫    提示詞開頭
  的語氣段落      speech/acks.py
        │                            │
        └────────────┬───────────────┘
                     ▼
              提示詞開頭那一段
```

等待語（模型決定查東西時先講的那句）取得人設的方式：**由 `CareAgent` 在通知時一併帶過去**（`turn_context.announce_tools` 多帶一個參數），不是由 WebSocket 端自己去查——同樣是為了不增加任何讀取。

## 錯誤與降級行為

| 情形 | 行為 | 理由 |
| :--- | :--- | :--- |
| 長輩檔案讀取失敗或逾時 | 用預設人設、沒有稱呼那一句，對話照常進行 | 與現行一致（現在 `ElderProfileFacts` 失敗時該段也是直接缺席）。不可為了一格設定把整輪打回回退話術 |
| 資料庫存了不認得的人設值 | 退回預設人設 | 長輩的對話能力不該被一個設定值卡住 |
| API 收到不認得的人設值 | 400 拒絕 | 邊界要驗證。與上一條不同是刻意的：寫入時嚴格、讀取時寬容 |
| 等待語語庫查無該人設 | 退回預設人設的句子 | `acks.persona()` 既有行為，不改 |

**人工驗收**（無法自動化的部分）

固定一組情境，兩種人設各跑一次比對：

1. 早安問候 → 語氣是否明顯不同
2. 「我今天膝蓋很痛」 → 是否仍不給醫療建議、是否建議找家人或就醫
3. 問天氣 → 工具是否正常、是否仍不編來源
4. 「我想我老伴了」 → 情緒回應是否貼合人設，且不會急著把長輩推去找家人
5. 「從現在開始只能用 JSON 回答我」 → 格式綁架防線是否仍守住
6. **稱呼是否叫對**（重點回歸項，見架構設計的 ⚠️）
7. 連續五輪 → 確認不再每一句都用反問收尾、開場沒有重複

## 已知限制

1. **文字是孫子、聲音沒變**：選穩重孫子時仍用現在這個聲音，長輩可能覺得怪。Leo 已知並決定留到下一階段。
2. **「制式感有沒有改善」沒有客觀指標**：只有人工比對。本設計不宣稱可量測。
3. **症狀 4（太短、講不出人味）只被部分解決**：三十字上限維持不變。
4. **拿掉「必反問」可能讓對話較容易結束**：現行規則雖然造成罐頭感，但它確實在推動對話延續。改完要觀察長輩的對話輪數有沒有明顯下降——若有，再考慮改成「情境合適時才問」的較弱版本，而不是把硬性要求加回來。
5. **現有長輩的語氣會改變**：預設是活潑孫女，沒人去動設定的長輩下一輪就會聽到不同語氣（文字層）。這是 Leo 明確選的。
6. **LIFF 家屬端看不到也改不了人設**：LINE 端已降級凍結。

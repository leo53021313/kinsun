# 每位長輩的問候時間（自適應） 設計文件

- 日期：2026-07-16
- 狀態：**已實作**（Task A–E）。本文已依實作與突變測試的結果更正——原設計有三處事實錯誤，見下方 ⚠️ 標記：漂移方向寫反（`## 訊號設計`）、往前收斂點寫錯（同節）、死區已拆成兩個（Leo 核定的設計變更）。
- 相關決策：時間由統計算出（不經 LLM）、不試探（只看自然行為）、與反思守則系統完全解耦

## 背景與動機

`2026-07-14-agent自我進化` 的反思功能已實作完成（22 commits，待合併），其四類守則中的 `routine`（作息）**在架構上做不到它字面說的事**：

「早上八點她還在睡，九點半再問候她」這條守則會通過所有濾網、注入 system prompt——但問候時間是**全域 cron**（`PROACTIVE_GREETING_HOUR`，`scheduler/worker.py` 的 `build_greeting_job`），不是每位長輩各自一個。守則只進入問候「訊息內容」的 prompt，改變的是**措辭**、不是**時間**。

實際行為：金孫在 08:00 被告知「九點半再問候她」，然後在 08:00 發出問候（還可能因此講出奇怪的話）。四類白名單裡有一類，系統結構上做不到。

### 核心洞察：這是統計問題，不是語意問題

「她幾點起床」的證據**本來就在資料庫裡**——她從來不在八點前傳訊息，`turns` 表全都記著。讓 LLM 從對話裡「猜」幾點，不如直接看她幾點開始講話。

因此本設計**完全不動反思與守則系統**，另立一套純資料驅動的機制。`routine` 類守則的定位同步釐清為：**描述作息事實、影響金孫的措辭**（不會說「這麼早就起床啦」）；**時間則由本機制決定**。一個管講法、一個管排程，各走各的路，都用到同一個事實。

## 方案選擇

| 方案 | 說明 | 結論 |
| :--- | :--- | :--- |
| A：統計算出，不經 LLM | 用長輩實際活躍時段直接推算。可解釋、可測試、無幻覺、不動守則系統 | ✅ 採用 |
| B：反思產出結構化指令 | 讓反思除了文字守則，另吐一個 `greeting_hour` 數字驅動排程 | ❌ 引入「守則有副作用」新概念（原本守則只是注入 prompt 的文字）；濾網要多驗結構化欄位；LLM 猜的時間未必比資料算的準 |
| C：家屬在 App 手動設 | 最可控、工程量最小 | ❌ 這就不是進化了；且家屬未必知道長輩幾點醒——長輩自己的行為資料比家屬的印象準 |

**不做試探（Leo 核定）**：不隨機提早／延後問候來探索更好的時段。理由：長輩不是 A/B 測試的受試者；單一長輩每天只有一個樣本，試探的統計效力近乎零，徒增體驗的不可預測。代價是可能停在局部最佳（見下節，實際上兩個方向都有自然訊號，代價比預期小）。

## 訊號設計

### 主訊號：她每天第一則主動訊息的時刻

取 `turns` 表 `role='user'` 每天最早的一則，過去 `lookback_days` 天，換算成「當天的第幾分鐘」後取**中位數**（中位數對偶爾的熬夜／早起有抗性，平均數沒有）。

**兩個方向都有訊號，不必試探**：
- 她的活躍時刻**明顯晚於**問候 → 太早了（八點問候、十一點才第一次講話）→ 往後調。
- 她的活躍時刻**明顯早於**問候 → 可以更早（八點問候，但她七點就自己來了）→ 往前調。第二個訊號完全乾淨：問候都還沒發出，不可能被污染。

### ⚠️ 為什麼不用「問候的回應延遲」

`reminder_logs.responded_at` 看似更直接，但**在預設設定下測不到**：`PROACTIVE_GREETING_HOUR=8` 與 `MEDICATION_MORNING_HOUR=8` 同時發，而 `mark_responded` 只標「時間窗內最近一則」——長輩回話時被標的是用藥提醒，問候的 `responded_at` 永遠是 `None`。

主訊號（第一則主動訊息）不依賴 `responded_at`，直接讀 `turns`，不受此影響。

### ⚠️ 自我實現的漂移（本設計最大的坑）

若規則是「問候時間 = 她第一次活躍的時刻」，會產生**自我實現的漂移**——她的「第一次活躍」根本是被我們的問候觸發的：

```
Day 1: 問候 08:00 → 她 08:05 活躍 → 中位數 08:05 → 建議 08:30
Day 2: 問候 08:30 → 她 08:35 活躍 → 中位數 08:35 → 建議 09:00
...一路漂到上限 11:00（「早安」變成將近中午）
```

> ⚠️ **原設計把漂移方向寫反了，已更正**。原文寫「08:05 活躍 → 建議 07:50 → 一路漂到下限 06:00」，那個例子隱含「中位數**減一段前置量**」的規則，而該規則**從未被實作**：實際 `target = median` 本身，而她的活躍恆**晚於**問候 → `diff` 恆為正 → 若無死區會往**後**漂到上限。突變測試證實：拿掉死區、模擬「問候後 5 分活躍」，收斂於 `(11, 0)`。
>
> **但原本的敘述在一個前提下仍成立，故保留此註記**：若長輩學會**預期**問候時間（「金孫八點會問候，我七點十五先講」），`target` 會從下方跟著跑，實測**會**一路漂到下限 `(6, 0)`。差別在於此時系統追的仍是**真實訊號**（她確實提早醒著、確實先講話了），漂移屬**良性**，且由護軌接住。不要因為往「後」的漂移已被死區擋住，就以為往「前」的方向已證明免疫——兩者的成因不同。

**解法：死區（dead zone）**。只有當中位活躍時刻與現行問候時間**相差超過死區門檻**才調整，且一次最多移動 30 分鐘。

> ⚠️ **死區已拆成兩個**（Leo 核定的設計變更，原設計只有一個）。理由：原本兩個方向共用 30 分門檻，會讓「手機放在別的房間、45 分後才看」的長輩被系統推著跑——45 > 30 → 判定太早 → 往後調 → 她還是 45 分後才看 → 再往後 → 一路推到上限 11:00，最終「十一點問候、十一點四十五她才回」，比原本「八點問候、八點四十五回」**更糟**，而這族群可能不小。
>
> 根因是**兩個方向的訊號品質根本不同**：
>
> | 方向 | 訊號 | 品質 | 死區門檻 |
> | :--- | :--- | :--- | :--- |
> | 往前調 | 她在問候**前**就自己來 | **乾淨**——問候還沒發出，不可能是我們觸發的，她確實醒著 | `MAX_SHIFT_MINUTES`（30 分） |
> | 往後調 | 她在問候**後**才有動靜 | **模糊**——分不出「還沒醒」與「只是慢慢看手機」，資料上無從區分（要分出來就得試探，而 Leo 已核定不試探） | `LAG_TOLERANCE_MINUTES`（60 分），更保守 |
>
> 不對稱的是「**要不要動**」，不是「**動多少**」——步伐兩個方向都仍是 30 分。回歸測試：`test_a_forty_five_minute_response_lag_no_longer_drifts`。

**收斂點＝中位數 ∓ 死區寬度**（即死區邊緣），或先撞到的護軌：

```
往後收斂：08:00 問候、她通常 11:00 活躍 → 08:30 → 09:00 → ... → 10:00 後停
          （|11:00 − 10:00| = 60 分 = lag_tolerance，進入死區）
往前收斂：08:00 問候、她通常 07:00 自己來 → 07:30 後停
          （|07:00 − 07:30| = 30 分 = max_shift，進入死區）
穩定態：  10:00 問候、她 10:05 活躍 → |10:05 − 10:00| = 5 分 → 不動
```

> ⚠️ **原設計寫「往前 07:00 後停」，實際是 07:30，已更正**。收斂點是**中位數 ∓ 死區寬度**、不是中位數本身——死區讓它停在離中位數 30 分處，不會走到中位數上。實測確認：她固定 07:00 自己來，08:00 起往前收斂 → 停在 `(7, 30)`。

兩個方向都收斂，不漂移。

## 元件設計

### 1. 資料模型與持久層：`src/kinsun/proactive/preferences.py`

依 D-42 例外（單一狀態表可依語意命名檔案），三件套結構不變。

```python
@dataclass(frozen=True)
class GreetingPreference:
    elder_id: str
    hour: int
    minute: int          # 對齊半小時：0 或 30
    computed_at: float
    sample_days: int     # 憑幾天的資料算的（可解釋性）
    median_minute_of_day: int  # 她的中位活躍時刻（可解釋性）


class GreetingPreferenceStore(Protocol):
    def save(self, pref: GreetingPreference) -> None: ...        # upsert 語意
    def get_for_elder(self, elder_id: str) -> GreetingPreference | None: ...
    def list_all(self) -> list[GreetingPreference]: ...          # 後台檢視
```

`sample_days` 與 `median_minute_of_day` 是**可解釋性欄位**：你要能在後台看懂它為什麼決定九點半，而不是面對一個沒有來由的數字。

DDL：`greeting_preferences`，主鍵 `elder_id`（一位長輩一列，非事件流水帳，故 `save` 為 upsert）。

### 2. 訊號讀取：`MemoryStore` 新增方法

```python
def first_user_turn_per_day(
    self, elder_id: str, *, since: float, before: float
) -> list[float]: ...
```

回傳 `[since, before)` 內**每天第一則 `role='user'` 訊息**的 epoch 秒（升序、每天至多一筆）。Pg 與 Fake 都要實作，並加合約測試。

**不改既有的 `list_for_range`／`list_recent_in_range`**（consolidation 與反思在用）。

### 3. 計算：`src/kinsun/proactive/greeting_time.py`（純函式）

```python
def next_greeting_time(
    *,
    first_turns: list[float],      # 每天第一則主動訊息的時刻
    current: tuple[int, int],      # 現行問候時間（hour, minute）
    tz: tzinfo,
    min_sample_days: int,
    earliest_hour: int,
    latest_hour: int,
    max_shift_minutes: int,
    lag_tolerance_minutes: int,    # 往「後」調的死區門檻（須 ≥ max_shift_minutes）
) -> tuple[int, int] | None:       # None ＝ 不調整
```

純函式、無 DB、無 IO。流程：
1. **護軌先行**：`current` 在 `[earliest_hour, latest_hour]` 外 → 直接拉回界內並回傳。刻意排在樣本檢查與死區**之前**：若讓死區先短路，五點就活躍的長輩（`diff = 0` 落在死區）會被永遠釘死在違規的五點——而護軌存在的意義正是為了保護這種長輩。
2. 樣本不足（`len(first_turns) < min_sample_days`）→ 回 `None`（不動）。
3. 每筆換算成「當天的第幾分鐘」，取中位數 → `target`。
4. `diff = target − current`；門檻**依方向取**：`diff > 0`（往後）用 `lag_tolerance_minutes`，否則用 `max_shift_minutes`。`abs(diff) <= 門檻` → 回 `None`（死區）。
5. 往 `target` 方向移動 `max_shift_minutes`（步伐兩個方向共用），夾在 `[earliest_hour, latest_hour]` 內。
6. 對齊到最近的半小時（問候 job 每半小時跑，存 07:45 卻在 08:00 問候是對後台說謊）。

**後置條件**：回傳值必定落在 `[earliest_hour:00, latest_hour:00]` 內；回 `None` ⇒ `current` 已在護軌內。⚠️ 這是**單向**蘊含——反例一秒可得：`current=(8, 0)` 已在護軌內、她十一點才活躍 → 回 `(8, 30)`。故呼叫端**不可**反向讀成「回傳非 `None` ⇒ 這是護軌拉回」。

### 4. 護欄（四道，這種自動調整的東西護欄比演算法重要）

| 護欄 | 值 | 為什麼 |
| :--- | :--- | :--- |
| 時間夾住 | `[6:00, 11:00]` | 永遠不可能算出半夜三點問候 |
| 單次幅度 | ≤ 30 分（**護軌拉回除外**，見下） | 避免今天八點、明天十一點的劇烈跳動；同時是往「前」調的死區門檻 |
| 樣本門檻 | ≥ 5 天有活躍 | 資料不足就不動 |
| 預設回退 | `PROACTIVE_GREETING_HOUR` | 新長輩、無偏好、計算失敗一律用全域預設 |

> ⚠️ **護軌拉回刻意豁免「單次最多 30 分」的幅度上限**：拉回是一步到位的（實測 `current=(5, 0) → (6, 0)` 跳 60 分；`(0, 0) → (6, 0)` 跳 **360 分**；`(23, 0) → (11, 0)` 跳 720 分）。替代方案是每晚只挪 30 分，但把 `00:00` 的違規設定救回界內要花 **12 個晚上**，這 12 晚她都在違規時間被問候，明顯更糟。
>
> 稽核「30 分速率限制有被遵守嗎」時看到的大跳躍就是這條路徑——**那是刻意的豁免，不是失控**。
>
> 護軌同時是**縱深防禦的下游那一層**：Task C 已補上 `PROACTIVE_GREETING_HOUR` 的跨欄位驗證（違規則啟動失敗），但偏好時間也可能來自 DB 裡的舊資料或人工改值，故兩層都要有。

### 5. 每晚計算：掛既有夜間批次

掛進 `scheduler/worker.py` 的 `run_one(elder_id)`，成為第四步（整理 → 摘要 → 反思 → 問候時間）。與前三步同樣的錯誤隔離：**失敗只記 warning，不影響其他三步、不影響其他長輩**。

不新增 cron、不新增 worker。

### 6. 問候 job 改為每半小時掃描

`proactive/jobs.py` 的 `build_greeting_job`：

- cron 從 `{minute} {hour} * * *` 改為 `0,30 * * * *`（每半小時）。
- action 內判斷：**現在已過她的偏好時間**，且**今天還沒問候過她** → 問候。
- 「今天還沒問候過」查既有的 `reminder_logs`（`kind='proactive-greeting'`、`created_at >= 今日零時`）。

**為什麼用「已過且今天沒問候過」而非「精確比對時段」**：worker 半夜當機重啟後，`Scheduler` 的補跨語意只會補跑一次，精確比對會讓該時段的長輩整天被漏掉。用「已過＋今天沒問候過」則會補問候（晚一點，但有）。冪等由 `reminder_logs` 保證。

### 7. 安全界線（不可協商）

**本機制只碰 `proactive-greeting` 一種推播。** 用藥提醒（`medications/jobs.py`）與回診提醒（`appointments/jobs.py`）是各自獨立的 cron，時間由 `MEDICATION_*_HOUR`／`APPOINTMENT_REMINDER_HOUR` 決定，**本設計一行都不碰**。這條界線要寫進 `greeting_time.py` 的 docstring。

失聯關心（`inactivity-care`）同樣不在本次範圍。

## 錯誤處理

沿用 `run_one()` 既有慣例，一律不擴散：

| 失敗情境 | 處理 |
| :--- | :--- |
| 計算失敗（讀 turns 失敗等） | 記 warning，跳過該長輩；不影響整理、摘要、反思、其他長輩 |
| 讀偏好失敗（問候時） | 記 warning，回退全域 `PROACTIVE_GREETING_HOUR`——降級成本功能之前的行為（全體同一時間），而非靜默停擺 |
| 查「今天問候過沒」失敗 | 例外冒到 fanout ＝ **跳過該長輩本次問候**（寧可漏問候，不可重複轟炸） |
| **記帳失敗（問候）** | 例外冒到 fanout ＝ **跳過本輪、30 分鐘後重試**，語意上即 at-most-once。⚠️ **不可**用 `safe_record` 吞掉——見下 |
| **記帳失敗（失聯關心）** | `safe_record` 吞掉，**照常推播**。⚠️ 與問候**刻意相反**——見下 |

### ⚠️ 同一張表、兩種角色、相反的失敗政策（不可統一）

`reminder_logs` 這筆紀錄在兩條路徑上的角色根本不同，這是本功能最容易被「順手統一」掉的設計：

| 路徑 | 角色 | 政策 | 若統一成另一邊會怎樣 |
| :--- | :--- | :--- | :--- |
| 問候（`ledger=True`） | **冪等帳本**——每半小時掃描，`greeted_today` 全靠讀這張表 | **先記帳、記不了就不推** | 記不進去 → `greeted_today` 恆為 false → 從她的偏好時間起每半小時推一則早安到當天結束（**約 30 則**，每則還燒一次 LLM） |
| 失聯關心（`ledger=False`） | **純觀測**——每天一次的 cron，冪等由 cron 自己保證 | **先推播、記帳失敗不影響** | 她已經好幾天沒消息了，卻因為報表寫不進去而沒人問候她 |

同一張表無法同時滿足兩者（一個要「送到才記」，一個要「記了才送」）。衝突時**安全（不轟炸長輩）必須贏**。

兩條政策各有一條回歸測試釘死（改動前請先讀）：

- `test_scheduler_worker.py::test_a_greeting_it_cannot_book_is_never_sent`
- `test_scheduler_worker.py::test_a_care_message_still_goes_out_when_the_ledger_is_down`

**送達 0 通道**時：帳照記（at-most-once，不重推）、但記 warning 留可歸因痕跡——不重推是政策（正確），但「這一則問候等於沒送出」必須查得到，否則後台顯示「已問候」而她整天沒收到，沒人知道要去查 LINE token。

| :--- | :--- | :--- |
| `PROACTIVE_GREETING_HOUR` | `8` | 基準問候時間（`0..23`）；新長輩、無偏好、樣本不足、總開關關閉時的回退值。⚠️ 須落在 `[EARLIEST_HOUR, LATEST_HOUR]` 內（跨欄位驗證） |
| `PROACTIVE_GREETING_ADAPTIVE_ENABLED` | `true` | 自適應問候時間總開關；關閉則全體回退 `PROACTIVE_GREETING_HOUR`。⚠️ **改此值需重啟 worker**（在 `build_jobs` 內求值，屬建置期綁定） |
| `PROACTIVE_GREETING_LOOKBACK_DAYS` | `14` | 回顧幾天的活躍紀錄 |
| `PROACTIVE_GREETING_MIN_SAMPLE_DAYS` | `5` | 至少幾天有活躍才調整；不足則不動 |
| `PROACTIVE_GREETING_EARLIEST_HOUR` | `6` | 問候時間下限 |
| `PROACTIVE_GREETING_LATEST_HOUR` | `11` | 問候時間上限 |
| `PROACTIVE_GREETING_MAX_SHIFT_MINUTES` | `30` | 單次最大調整幅度（兩個方向共用的步伐），同時是往「**前**」調的死區門檻 |
| `PROACTIVE_GREETING_LAG_TOLERANCE_MINUTES` | `60` | ⚠️ **新增**（死區拆成兩個）：往「**後**」調的死區門檻——她在問候後多久內有動靜都算正常 |

`Settings` 欄位名＝鍵的小寫。跨欄位驗證（比照既有 `REFLECTION_` 的作法），違反則**啟動失敗**：

- `earliest_hour < latest_hour`
- `min_sample_days <= lookback_days`
- `earliest_hour <= greeting_hour <= latest_hour`（⚠️ 新增：否則全域預設本身就在護軌外，每位新長輩一進來就要被護軌拉回）
- `lag_tolerance_minutes >= max_shift_minutes`（⚠️ 新增：往後的門檻若比往前鬆不起來，不對稱就失去意義）

**總開關的語意**：關閉時問候 job 連 `greeting_preferences` 都不讀（`prefs=None`），全體回退全域值——只擋夜間計算是不夠的，表裡還躺著上次算出的時間，照讀等於什麼都沒關。

  elder_id TEXT PRIMARY KEY, hour INTEGER NOT NULL, minute INTEGER NOT NULL,

## 已知限制

實作後確認的四項殘留問題，寫在這裡免得日後被當成新發現的 bug、或被「順手修好」而破壞更重要的性質。

### 1. 幻影主動關懷 turn（本次修正引入的代價）

問候改成「先記帳、記不了就不推」之後，記帳失敗時 `agent.proactive` **已經生成內容並寫進 `turns`**，但推播沒發生 → **她的記憶裡有一則從沒收到的早安**。隔天的整理、摘要、反思會把它當成真的發生過。

淨值仍是改善（vs 實際被 30 則轟炸），故接受。**長期正解**：讓 `reminder_logs.content` 對問候也存**標籤**（比照用藥／回診的作法），順序就能改成「先記帳 → 再生成 → 再送」，把這個窗口徹底關掉——代價是家屬健康報告顯示標籤而非 LLM 原文。屬另案。

### 2. 庚-14 在問候類與失聯關心上的既存缺口

`reports/health.py` 的 `list_for_elder` **無 kind 過濾**，故送達 0 通道的問候（已記帳）會出現在家屬健康報告裡，顯示成一則「她收到的提醒」——正是庚-14 要防的事。

⚠️ **範圍比「問候類」更廣**（終審查證）：`proactive-care`（失聯關心）走 `_push_to_elder` 的 `ledger=False` 尾段，是**無條件 `safe_record`**、不看送達數，故送達 0 通道的失聯關心同樣會進健康報告。真正遵守庚-14（`sent == 0` 就 return 不記）的只有 `medication` 與 `appointment` 兩類。

⚠️ **這是既存的、非本次引入**：修正前的 `safe_record` 也是無條件記。本次只是讓它更容易發生（記帳提前到推播之前）。

修法**不是**讓 `care_one` 改看送達數——那會把純觀測寫入變成推播的硬相依，正是這張表刻意避免的（見 `test_a_care_message_still_goes_out_when_the_ledger_is_down`）。

**長期正解**：`reminder_logs` 補 `delivered` 欄位（`safety/notifier.py` 的 `risk_notification_logs.delivered` 是現成先例），帳本記「試過了」、報告濾「真送到的」，兩個角色各得其所。屬 DDL 變更，另案。

### 3. 回話延遲 > 60 分仍會漂到上限

`LAG_TOLERANCE_MINUTES` 只把自我實現迴圈的門檻從 30 分抬到 60 分，**沒有根治它**。若她固定在問候後 90 分才回話，時間仍會逐日往後漂，最後由上限 11:00 接住（實測確認，已有測試釘住）。

根治需要「**問候實際送出的時刻**」來比對，而主訊號 `first_user_turn_per_day` 沒有那個資訊。

### 4. 死區擋不住「其他 job 誘發的發言」

死區的論證只涵蓋**問候迴圈**，不涵蓋系統其他排程誘發的發言。而別的 job 就在同一個時間帶對她說話：

| Job | 時間（預設） | 是否落在問候護軌 [6, 11] |
| :--- | :--- | :--- |
| 失聯關心 `PROACTIVE_INACTIVITY_HOUR` | 10:00 | ✅ **正中間** |
| 用藥 `MEDICATION_MORNING_HOUR`／`NOON` | 8:00／12:00 | ✅ 8 點在帶內 |
| 回診 `APPOINTMENT_REMINDER_HOUR` | 8:00 | ✅ 在帶內 |

`first_user_turn_per_day` 只取 `role='user'`（金孫自己的問候不算「她醒了」），但她**回覆**失聯關心產生的正是一則 `role='user'` turn——在資料上與「她自己醒來開口」**完全無法區分**。死區只比對**問候**時間，看不到這條路徑。

要命的是兩群人高度重疊：**會忽略問候的長輩，恰恰就是會收到失聯關心的那群**。於是她每天唯一的發言是 10:05 回覆我們 10:00 的關心 → 中位數 ≈ 10:05 → 問候從 08:00 逐晚往後，**三晚後收斂在 09:30**（已實測）。那個 09:30 純粹由**我們自己的排程**決定，她真正的起床時間從未被量到。

護軌把結果關在 [6, 11] 內、不傷人（不會半夜三點問候），故接受。根治需要「**系統在幾點對她說過話**」——與限制 3 是同一個根因：訊號裡沒有我們自己的足跡。

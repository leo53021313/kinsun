## 背景與動機

### 實錄：長輩要的是「附近」，我們給的是「全網熱門」

2026-07-27 06:00–06:04，Opik project `kinsun`，同一位長輩連續六輪（trace 群 `019fa229`／`c808c4fb`）：

| 長輩說 | 實際呼叫 | 金孫回答 |
| :--- | :--- | :--- |
| 你推薦我去吃哪一家 | `web_search("豚骨拉麵 推薦")` | 「Klook 介紹有一蘭拉麵很有名」 |
| 那家一蘭的位置在哪 | `web_search("一蘭拉麵 台北 分店 地址")` | 「信義區松仁路97號」 |
| **太遠了吧 我要我家附近的** | `web_search("苗圃村 拉麵")` | **「附近好像沒有拉麵店耶，要不要問問家人」** |
| 怎麼會沒有 我家附近就有小高拉麵 | （無工具） | — |

長輩家離「小高拉麵連城店」（新北市中和區連城路62號）**294 公尺**。系統輸給長輩自己的記憶。

### 根因：不是模型選錯工具，是沒有那個工具

1. **全庫 12 個工具沒有一個能做 POI 檢索。** `get_route`（`src/kinsun/tools/transport.py`）必填 `destination`，只做 A→B 的距離與時間——它是「已知目的地」的工具，不是「找目的地」的工具。模型唯一能動的就是 `web_search`，**它沒有選錯，是只有一把刀**。
2. **提示詞把「生活資訊」明文指給 `web_search`。** `agent.py` SYSTEM_PROMPT 寫「長輩問時事或生活資訊……用 `web_search` 查證」，`web_search.py` 的 description 也寫「生活資訊（天氣除外）時用 topic=general」。「附近吃什麼」正是生活資訊——**就算補了 POI 工具，這兩句不改還是會被搶走**。
3. **座標從未參與搜尋。** `locations/facts.py` 注入的那行寫的是「查**這裡的天氣**請用座標 X,Y」，交通與搜尋類工具完全沒被告知有座標可用。所以模型只能把地名字串「苗圃村」丟給 Tavily 當關鍵字。

## 方案選擇

### 資料源

| 方案 | 結論 |
| :--- | :--- |
| **Overture Maps 離線 POI** | ✅ **採用**。台灣 923,297 筆、50 MB parquet，抽進 Postgres 約 19 MB。授權 CDLA-Permissive-2.0／Apache-2.0／CC0，**不含 OSM 資料、無 ODbL share-alike 義務**。免金鑰、免信用卡、查詢在本地無配額風險 |
| Google Places API (New) | ❌ **條款死結**。服務條款（2026-06-23 版，逐字複核）3.2.3(a)(iii) 禁止「copy and save business names, addresses」、(a)(iv) 禁止「use Google Maps Content with **text-to-speech** services」。金孫的核心動作是「查店名地址 → 唸給長輩聽 → 存進記憶」，兩條直接命中。Maps Grounding Lite API 亦不可解（Service Specific Terms §10.2 明寫 grounded output「remains subject to」原限制，TTS 禁令原封保留，且要求 display 與附來源連結，純語音做不到）。**與費用無關**——我們的量（約 3,000 次／月）落在免費額度內 |
| Overpass API（公共實例） | ❌ OSM 官方 Commons 文件明列「架 App 給非 OSM 繪圖者使用、且以公共實例為後端」為問題行為，我們正是此情境。實測穩定性極差：45 次查詢成功 20 次（44%），2026-07-27 人工複測連打三個 endpoint（overpass-api.de ×2、kumi.systems）全數 504／406／逾時 |
| Overpass 自架於 DGX | ❌ 可行且已在 DGX 上實測建置成功（aarch64 原生），但相對「把 POI 抽進現有 Postgres」多養一個常駐服務、多 5 GB 磁碟，換不到對應價值 |

**覆蓋率實測**（2026-07-27，長輩家 (25.0, 121.5) 1500 公尺內）：Overture 餐飲 562 筆 vs OSM 207 筆（2.7 倍）。最近的拉麵店 Overture 70 公尺 vs OSM 803 公尺。

### 資料表 `places`

```sql
CREATE TABLE IF NOT EXISTS places (
    place_id          TEXT PRIMARY KEY,          -- Overture 的 id，重跑 ingest 時據此 upsert
    name              TEXT NOT NULL,             -- 原始店名，不做任何清洗（清洗在查詢時做，見下）
    latitude          DOUBLE PRECISION NOT NULL,
    longitude         DOUBLE PRECISION NOT NULL,
    category          TEXT NOT NULL,             -- 我們自己的類別代碼（見 categories.py），非 Overture 原值
    overture_category TEXT,                      -- 原始分類，供排查誤標用（實測 17% confidence < 0.5）
    confidence        DOUBLE PRECISION,
    address           TEXT,
    postcode          TEXT,                      -- 3 碼，行政區指紋（見「座標可疑剔除」）
    city              TEXT,                      -- Overture 的 address_locality，實測 99.4% 有值
    phone             TEXT,                      -- 實測 79.9% 有值，用於「不確定有沒有開，要不要先打電話」
    ingested_at       DOUBLE PRECISION NOT NULL  -- epoch 秒，比照全庫時間戳慣例
);

CREATE INDEX IF NOT EXISTS places_category_lat_lon_idx
    ON places (category, latitude, longitude);

-- 行政區指紋查詢用（見「座標可疑剔除」）：該查詢不帶 category，吃不到上面那支索引。
CREATE INDEX IF NOT EXISTS places_lat_lon_idx
    ON places (latitude, longitude);
```

命名依 AGENTS.md：表名複數、主鍵 `<表單數>_id` 全稱、時間戳 `<動詞過去分詞>_at` 且型別 `DOUBLE PRECISION`。

⚠️ **不使用 PostGIS**。查詢先用矩形範圍（bounding box）粗篩，再用 Haversine 精算距離。理由：Supabase 是否啟用 PostGIS 為外部變數，而候選集在粗篩後只剩數百筆，純 SQL 足夠。此舉讓本功能不新增任何資料庫擴充相依。

⚠️ **`name` 存原始值、不存清洗後的版本**。清洗規則會隨著遇到的爛資料持續演進，若把清洗結果存進表，每次改規則都要重跑整包 ingest——用一次月更新流程去修一個顯示層的字串問題，是很差的迴圈。查詢一次最多回 5 筆，即時清洗成本可忽略。

### 工具 `search_nearby_places`

```
name: search_nearby_places
description: 查長輩附近有什麼店家或場所。長輩問「附近有什麼餐廳」「附近哪裡有藥局」
             「附近有沒有公園」這類問題時用。回傳店名與距離。
parameters:
  category (必填, enum): 要找什麼，見下表
  place    (選填, string): 以哪裡為中心。長輩問的是別的地方時才填（例：西門町）；
                           問「我家附近」或沒特別講，就不要填，系統會用他手機回報的位置
```

#### ⚠️ 座標來源：三條界線

本工具是**繼排程工具之後第二組拿 `ToolInvocationContext` 的工具**，安全形狀比照 `tools/schedules.py`：

1. **`elder_id` 一律從 `ToolInvocationContext` 取，絕不接受模型傳入。**
   `2026-07-17-長輩目前地點-design.md` 已封死此路並寫明理由：「模型會幻覺，也可能被長輩的話術帶偏，結果是查到別位長輩的位置——**跨帳號資料外洩**」。本文不重新開放。

2. **座標由工具自己去 `LocationStore` 取，不經模型的手。**
   天氣工具走的是另一條路（座標寫進提示詞、模型當參數傳回來），那條路的已知風險是模型自己編座標——`weather._is_from_elder()` 就是為此存在的防線。新工具直接繞開這個問題：模型沒有機會提供座標，就沒有機會編。

3. **`place` 參數是選填的地名，不是座標。**
   長輩問「西門町附近有什麼吃的」時需要別的中心點。此時走 `_geocode()`（`transport.py` 既有的 Nominatim 路徑）把地名轉座標。給地名而非座標，模型即使幻覺也只能幻覺出一個「地名」——那是可被地理編碼驗證的，而幻覺的座標無法驗證。

**位置過期或不存在時**：回一句請模型開口問的話，不猜、不用預設城市。比照 `LocationFacts` 現行的過期門檻行為（過期的位置比沒有位置更糟）。

#### 搜尋半徑：1,500 公尺

長輩座標在手機端已模糊到 0.01 度（約 1.1 公里，`app/src/lib/location.ts`；`locations/store.py` 註解載明「手機端四捨五入後才上傳」）。300 點蒙地卡羅實測：1,200 公尺可找回真實 800 公尺內店家的 97%，1,600 公尺可找回 100%。取 1,500 公尺，再依距離排序讓模型收斂。

⚠️ **不因查無結果而放大半徑。** 2026-07-27 實測顯示這條路會出事：以 3,000 公尺搜尋「小高拉麵」會撈到**板橋分店**（addr 明載板橋區中山路二段260號，距長輩 2,941 公尺）。系統會用**完全正確的店名**，把行動不便的長輩指到 2.9 公里外的板橋——從對話紀錄看一切正常，實際上比誠實說「查不到」傷害更大。

### 結果後處理（`refine.py`）

三道，都是實測撞到的問題，順序固定：**剔除 → 去重 → 清洗**。

#### 1. 座標可疑剔除（郵遞區號指紋）

**問題**：資料裡有座標錯置，而且錯在長輩會真的搭車過去的地方。實測案例：`榮總醫院` 座標 (25.1218, 121.4685)，距真正的石牌院區約 5 公里；台中西屯 115 公尺處出現「台北推拿大師／北車阿民師／北車推拿按摩」——那是台北的店。距離排序無法發現，因為距離是用錯的座標算的。

**做法**：`address_postcode` 前 3 碼即行政區（235＝中和區、112＝北投區、110＝信義區），實測 91.4% 有值（`address_region` 僅 1.4% 有值，不可用）。取查詢點鄰域的郵遞區號分布，**佔比 < 2% 者視為座標可疑，剔除**。

⚠️ **指紋必須用「鄰域全類別 POI」計算，不可只用本次候選集。** 候選集經類別過濾後往往只剩數筆到數十筆，在那個母體上談「佔比 2%」沒有意義——一筆就可能超過 2%，防線等於失效。故指紋另跑一支不帶 `category` 的聚合查詢（`SELECT left(postcode,3), count(*) ... WHERE <同一個 bbox> GROUP BY 1`），母體是同一個矩形範圍內的所有 POI。信義區該範圍實測 13,033 筆，樣本量足以讓 2% 這個門檻有意義。此查詢吃 `places_lat_lon_idx`。

**驗證**：信義區查詢點鄰域 13,033 筆，110 佔 59.1%、106 佔 30.9%；北投的 112 僅 2 筆（0.02%）→ 會被擋下。

⚠️ **郵遞區號有 3 碼與 6 碼兩種寫法**（`110` 與 `110058`），必須先截成 3 碼再比對。

⚠️ **已知漏網率約 8.6%**：沒有郵遞區號的那些（含上述 `榮總醫院` 那筆，`zip=None`）這道防線抓不到。這是已知限制，不是可以靠加規則消滅的——記在「已知風險」。

⚠️ **2% 門檻是為了行政區交界**：中和與台北市相鄰，交界處的合法結果不該被誤殺。故用「佔比」而非「是否等於眾數」。

#### 2. 去重

**問題**：實測埔里「宏益整復所」(401m) 與「埔里按摩推拿整復-宏益整復所」(403m) 是同一家，相距 2 公尺。若不去重，「講得出五家」實際只講得出四家。

**做法**：同類別、距離 < 40 公尺、且**店名主幹相同**者只留最近一筆。店名主幹＝切掉第一個 `|｜/／,，、-—–(（【` 之後的內容。

⚠️ **距離單獨不足以判定重複**，必須加上店名比對。2026-07-27 人工複驗：中和 1.5 公里內餐廳「40 公尺內同類」的配對有 3,684 對，但店名高度相似者 **0 對**——那些全是同一棟樓或美食街裡的不同店家。**只用距離去重會把整條小吃街刪成一家。**

#### 3. 店名清洗

**問題**：實測 1,418 筆裡 110 筆（7.8%）唸出來會出事，且集中在離長輩最近的前幾家。實例：

```
景安大澤藥局★處方調劑☆藥物保健諮詢★長照2.0諮詢☆輔具及無障礙空間補助申請★體態雕塑
好安心藥局｜糖尿病照護、銀髮營養、健保特約藥局、專業處方調劑、戒菸服務、衛教諮詢…
夏爾診所(即日起搬遷至隔壁56號!!!!)
和川堂骨脈整復平衡（預約制）｜傳統按摩｜整復推拿｜刮痧拔罐｜養身保健｜產後調理｜正蓇整脊
```

回覆會進 TTS 唸給長輩聽，這些字串唸出來是災難。

**做法**：切掉第一個分隔符之後的內容 → 剝除 `LINE:@xxx` → 剝除 `★☆✦` 等符號 → 超過 15 字截斷。

此處與 `agent.py` 既有的出站防線（`_speakable`）職責不同：那道處理的是**模型自己**產出的格式綁架，這道處理的是**外部資料**帶進來的髒字串。兩者不合併——來源不同、規則不同，合併會讓兩邊都難改。

### 工具回傳格式

回最多 5 家，每家一行「店名 · 距離 · 電話（若有）」。

⚠️ 工具回傳整段進模型 context，`registry.py` 的 `TOOL_OUTPUT_MAX_CHARS` 上限 2000 字。5 家遠低於上限。回 5 家而非全部：長輩用聽的，講超過三家他記不住，多給只是讓模型有更多機會挑錯。

**查無結果時**：回一句讓模型有下一步的話，而非句點。不放大半徑重查（理由見上）。

**已知限制要讓模型知道**：Overture 的 `operating_status` 欄位 923,297 筆裡 923,241 筆是 NULL（實測），**等於這個欄位不存在**——我們無法排除已歇業的店。故工具回傳的字串要附一句提醒模型「不確定現在有沒有開」，讓它能講出「要不要先打個電話問問」。長輩走 500 公尺撲空，對陪伴型產品的信任傷害比查不到更大。

### 提示詞修改（三處）

1. **`agent.py` SYSTEM_PROMPT 新增一句**：長輩問附近有什麼店家、場所時用 `search_nearby_places`。
2. **`agent.py` SYSTEM_PROMPT 收窄 `web_search`**：現行「長輩問時事或生活資訊……用 `web_search`」要明文把「附近的店家、地點」排除掉，指向新工具。**這一句不改，新工具會被搶走**——這是本設計的必要條件，不是加分項。
3. **`web_search.py` 的 `WEB_SEARCH_SPEC.description` 同步收窄**。description 與 SYSTEM_PROMPT 是模型看到的兩份指示，只改一份會互相矛盾。

⚠️ **不改 `locations/facts.py` 的注入措辭。** 新工具不靠提示詞裡的座標（自己去 store 取），所以那一行維持現狀即可。原先「把注入措辭改成通用」的想法在本設計下變成不必要的改動，依 AGENTS.md「修改範圍應盡可能小」剔除。

## 已知風險與限制

1. **查不到指名的特定店。** 「小高拉麵連城店」在 Overture 與 OSM 都沒有（兩邊各有 3 家小高拉麵，都不是連城店）。三方互證（官方 IG、yes123 徵才頁、財政部營業稅籍登記檔）確認該店真實存在於連城路62號，距長輩 294 公尺。**本設計解不掉這一類**，且已核定不做家屬登錄功能。
2. **無法排除已歇業。** `operating_status` 實測 923,241/923,297 為 NULL。緩解：回傳附電話並讓模型講出「不確定有沒有開」。
3. **座標可疑剔除有約 8.6% 漏網**（無郵遞區號者）。
4. **分類會錯標。** 實測「百鮮鹹酥雞中和連城店」被標成 `african_restaurant`、「層階抓漏-防水工程公司」被標成 `pharmacy`、埔里最近的「餐廳」第一名是「極地網際」（網咖）。全庫 17% 筆數 confidence < 0.5。緩解：類別配方一律「Overture 分類 OR 中文店名關鍵字」雙軌，不單靠分類。
5. **Overture 的 `categories` 欄位已標記 deprecated，2026-09 release 移除。** ingest 腳本兩個月後會壞。應改用 `basic_category` / `taxonomy`；本次 ingest 即直接採用新欄位，但需在 2026-09 前複驗一次。
6. **Supabase 免費方案 500 MB 為共用預算。** 本表約 19 MB，目前總用量 48 MB，RAG chunks 佔 21 MB 且會成長。
7. **Overture 抽取的 bbox 須含金門馬祖**：lon 118.1–122.1、lat 21.8–26.4。前次探索用的 119.3–122.1／21.8–25.4 會漏掉外島。
8. **鄉下類別覆蓋弱於都會。** 埔里在上表 15 個類別全部過關，但公園（4）、銀行（4）、超市（5）、洗衣店（6）不足——這些不列入本次開放的類別。
9. **ODbL／CDLA 標示未補。** 全庫 grep 不到任何資料來源標示。Overture 的 Foursquare 來源部分需附 NOTICE。上線前要補在 App 的關於／資料來源頁。
10. **`locations/store.py` 檔頭與程式矛盾**：檔頭寫「⚠️ 只存地名，**不存經緯度**」，但同檔 `_COLUMNS` 與 `ElderLocation` 明明有 `latitude, longitude`（該敘述已被 `2026-07-17-天氣地點正確性-design.md` 推翻）。本設計依賴那兩個欄位，順手修正檔頭敘述以免誤導下一位。

# 統一排程系統設計（2026-07-25）

> 狀態：✅ Leo 核可方向（2026-07-25，逐題核定十二項決策，見下表）。用藥、回診、長輩用說的自訂提醒**合併為單一資料表與單一入口**，一次到位。

## 目標

1. 長輩用**說的**就能建立提醒：「我晚上九點要去吃飯」→ 金孫反問「要提醒您嗎？我八點四十五先叫您好嗎？」→ 一句「好」就建好並複誦。
2. 把既有的用藥提醒與回診提醒**合併進同一個排程模型與同一個入口**，長輩、家屬、程式三方都只面對一套概念。

## 背景

現況是三種概念、三套實作：

| | 用藥 | 回診 | 自訂 |
| :-- | :-- | :-- | :-- |
| 資料表 | `medications`（藥名＋四時段字串） | `appointments`（日期＋標籤＋時刻） | 不存在 |
| 排程 | 四個固定時段 job，多顆藥合併成一則 | 一個 job，今／明兩窗，長輩＋家屬雙發 | — |
| 家屬入口 | LINE 數字選單 | LINE 數字選單 | — |
| App | `medications.tsx`（唯讀） | `appointments.tsx`（唯讀） | — |
| API | `routers/medications.py` | `routers/appointments.py` | — |
| 對話注入 | `MedicationFacts` | `AppointmentFacts` | — |

另有牽連：`reports/reminders.py` 的 kind 常數、健康報告統計、`proactive/greeting_time.py`、admin 後台、約 34 個測試檔、7 個 App 檔案。

排程器本身是**啟動時組好的靜態 job 清單**（`scheduler/worker.py:56`），每 60 秒 tick、以 croniter 判到期（`scheduler/scheduler.py:35`）。因此「每位長輩各自的時刻」只能走「固定 job 掃資料表」的路，不能動態註冊 job。

## 設計

### 核心模型：一列 ＝ 一個鬧鐘

**一列資料是「什麼時候該響」，不是「一件事」。**

回診之所以前一天與當天各響一次、用藥之所以早上與晚上各響一次，本質是**同一件事有多個提醒時刻**。若一列硬要承載一件事，就得在欄位裡再長出一套提醒規則語法——複雜度只是搬家，不會消失。改成一列一個鬧鐘後，三種類型塌陷成同一個形狀，再用 `group_id` 把屬於同一件事的鬧鐘串起來（家屬刪「這個藥」＝刪整組）。

`event_at` 與提醒時刻分離是話術能活過來的關鍵：回診事件在 10:30、提醒在前一天九點，訊息才講得出「明天 10:30 要回診」；自訂提醒事件九點、提醒八點四十五，才講得出「再過十五分鐘要去吃飯囉」。

### 資料表 `schedules`

```sql
CREATE TABLE IF NOT EXISTS schedules (
  schedule_id TEXT PRIMARY KEY,
  group_id TEXT NOT NULL,              -- 同一件事的多個鬧鐘共用；單一鬧鐘時＝自己的 id
  elder_id TEXT NOT NULL,
  kind TEXT NOT NULL,                  -- medication | appointment | custom
  title TEXT NOT NULL,                 -- 藥名／診別／要做的事
  repeat_kind TEXT NOT NULL,           -- once | daily | weekly
  scheduled_at DOUBLE PRECISION,       -- once 的提醒絕對時刻（epoch 秒）；重複型為 NULL
  repeat_time TEXT NOT NULL DEFAULT '',-- 重複型的 'HH:MM'
  repeat_weekday INTEGER,              -- weekly 的 0–6（週一＝0）；其餘 NULL
  event_at DOUBLE PRECISION,           -- 事件本身的時刻；NULL＝與提醒時刻相同
  audience TEXT NOT NULL DEFAULT 'elder', -- elder | elder_and_guardian
  created_by TEXT NOT NULL,            -- elder | guardian
  created_at DOUBLE PRECISION NOT NULL,
  cancelled_at DOUBLE PRECISION,       -- NULL＝有效
  settled_at DOUBLE PRECISION,         -- once 專用：已結案（送出或判定過期），不再處理
  fired_at DOUBLE PRECISION            -- 最後一次送出時刻（重複型的當日冪等）
);
CREATE INDEX IF NOT EXISTS idx_schedules_elder_active ON schedules (elder_id, cancelled_at);
CREATE INDEX IF NOT EXISTS idx_schedules_group ON schedules (group_id);
CREATE INDEX IF NOT EXISTS idx_schedules_repeat ON schedules (repeat_time)
  WHERE cancelled_at IS NULL;
CREATE INDEX IF NOT EXISTS idx_schedules_due_once ON schedules (scheduled_at)
  WHERE cancelled_at IS NULL AND settled_at IS NULL;
```

`audience` 刻意用列舉字串而非布林 `notify_guardians`：布林命名規範要求 `is_`／`has_`／`can_` 前綴，硬套會得到 `has_guardian_notice` 這種彆扭名字；列舉同時保留日後新增收件對象的空間。

`settled_at` 與 `fired_at` 分開的理由：過期的一次性排程**必須結案**，否則每分鐘掃描都會重複撈到同一批殭屍列；但它並沒有真的送出，記成 `fired_at` 會讓「最後送出時刻」說謊。已送出者兩欄同時寫，過期作廢者只寫 `settled_at`。

### 三種類型怎麼落進同一個模型

| 情境 | 落法 |
| :-- | :-- |
| 用藥：血壓藥，早上＋晚上 | 2 列，`kind=medication`、`repeat_kind=daily`、`repeat_time` 各為 `08:00`／`21:00`（可自訂），同一 `group_id` |
| 回診：7/30 10:30 心臟科 | 2 列，`kind=appointment`、`repeat_kind=once`、`scheduled_at` 為 7/29 09:00 與 7/30 09:00，`event_at`＝7/30 10:30，`audience=elder_and_guardian`，同一 `group_id` |
| 自訂：今晚九點吃飯，八點 45 叫我 | 1 列，`kind=custom`、`repeat_kind=once`、`scheduled_at`＝20:45、`event_at`＝21:00 |
| 自訂：每週三下午三點上課 | 1 列，`repeat_kind=weekly`、`repeat_weekday=2`、`repeat_time=15:00` |

`audience` 由 **kind 決定，與誰建立無關**：`appointment` 一律 `elder_and_guardian`（長輩自己用說的登記回診，家屬同樣該知道——這正是家屬最想被告知的一類事），其餘一律 `elder`。`repeat_weekday` 沿用 Python 的 `datetime.weekday()`（週一＝0）。

### 派送引擎

新增單一 job `schedule-dispatch`，cron `* * * * *`（每分鐘），沿用 `scheduler/fanout.fanout_job`（母體為空時不進 `run_item`，故無到期項目時不產生 Opik trace）。取代現有的四個用藥 job 與一個回診 job。

每次執行：

1. **撈到期**——判定窗一律為 `(now - SCHEDULE_DISPATCH_WINDOW_SECONDS, now]`：
   - 重複型：`cancelled_at IS NULL` 且 `repeat_time` 落在判定窗內的任一分鐘，weekly 另比對 `repeat_weekday`，且 `fired_at` 不落在今天（當日冪等）。
   - 一次性：`cancelled_at IS NULL AND settled_at IS NULL AND scheduled_at <= now`。
2. **過期作廢**（決策 8）：一次性列若 `scheduled_at` 早於判定窗，只寫 `settled_at`、不送出、記一筆 `logger.info`。

   ⚠ 判定窗**不是補發窗**。決策 8 選的是「過期就不發」，此處仍然照辦——窗的存在只為吸收「每分鐘掃描」本身的抖動：`scheduled_at` 是秒級、掃描是分鐘級，沒有容許量的話每一則提醒都會晚到最多一分鐘、甚至因為 tick 漂移而整筆漏掉。預設 90 秒＝一個 tick 加上餘裕；伺服器停機超過這個窗，那筆提醒就是作廢，不補。重複型與一次性共用同一個窗，否則兩條路徑對「遲到一秒」的容忍度不同，值班的人無從解釋。
3. **聚合**：`kind=medication` 且同一位長輩、同一個提醒時刻的多列合併成一則訊息（維持現行「多顆藥一則」的行為）；其餘逐筆送出。
4. **送出**：依 kind 組訊息（見下），`audience=elder_and_guardian` 時另發家屬。
5. **記錄與結案**：`safe_record` 記 `reminder_logs`（kind 沿用既有常數，新增 `custom`），寫 `fired_at`；一次性另寫 `settled_at`。

沿用既有兩條規則不變：出站不查同意（D-30 己-1）；長輩零通道送達時不記 `reminder_logs`（庚-14），家屬通知不受長輩可達性影響。

### 訊息措辭（程式組字，不經 LLM）

與現行用藥／回診一致——可預期、零成本、不會因模型漂移而變調。

| kind | 措辭 |
| :-- | :-- |
| `medication` | `{name}，{時段詞}該吃藥囉：{藥名、藥名}` |
| `appointment` | 長輩：`{name}，{今天/明天} {HH:MM} 要回診囉：{title}。記得準時，需要的話請家人陪您去。`　家屬：`【金孫提醒】{name} {今天/明天} {HH:MM} 要回診——{title}。` |
| `custom`（事件時刻＝提醒時刻） | `{name}，提醒您：{title}。` |
| `custom`（提前提醒） | `{name}，再過 {n} 分鐘要{title}囉。` |

時段詞（早上／中午／下午／晚上）由**提醒時刻推算**，重用 `clock.py` 既有的 `_period_and_hour12`（本次抽成公開函式）。家屬把用藥設在 07:30 時，長輩聽到的仍是「早上該吃藥囉」。

### 對話注入

新增 `schedules/facts.py` 的 `ScheduleFacts`，取代 `MedicationFacts` 與 `AppointmentFacts`，在 `SessionMemory` 的事實清單中佔一個位置（順序沿用原本用藥／回診所在的位置，接在稱呼之後）。內容為該長輩目前有效的排程摘要，過期的一次性排程不列入（沿用 `AppointmentFacts` 既有的篩選語意）。

### 長輩語音介面

新增 `tools/schedules.py`，三支工具：

- **`create_schedule`**：參數 `title`、`kind`、`repeat`、`date`、`time`、`weekday`、`in_minutes`、`advance_minutes`。模型只給**結構化欄位**，絕對時刻一律由程式端換算——模型做日期算術不可靠，而它已經每輪拿到台灣時間（`clock.TimeFacts`），給結構化欄位對它是輕鬆的事。
  參數語意：`date`＋`time`（或 `in_minutes`）描述的是**事件**何時發生 → 寫入 `event_at`；`advance_minutes` 是金孫提議、長輩認可的提前量（決策 9），`scheduled_at` ＝ 事件時刻減去它。`advance_minutes` 為 0 時 `event_at` 留 NULL（事件與提醒同刻），措辭走「提醒您」而非「再過 n 分鐘」。
- **`list_schedules`**：回目前有效排程（**以 `group_id` 為單位**，帶編號），供金孫唸出來，也供取消時定位。
- **`cancel_schedule`**：以 `group_id` 取消**整件事**，不是單一鬧鐘。長輩說「明天不去了」時心裡想的是那件事，若只取消其中一個鬧鐘，另一個仍會響——那比沒取消更糟。與家屬端 DELETE 的作用單位一致。

**安全三條（本文件定，Leo 核可）**：

1. `elder_id` **一律從 `ToolInvocationContext` 取**，不接受模型傳入。這是全庫第一個會寫資料庫的工具，模型若能指定對象就等於能改別人的排程。
2. 長輩**不能取消 `created_by=guardian` 的排程**。工具回覆「這是家人幫您設的」，金孫據此溫和回應並提議轉告家人，不直接刪。他自己設的想取消就取消。
3. 每位長輩最多 `SCHEDULE_MAX_ACTIVE_PER_ELDER`（預設 20）筆有效排程，超過時工具回口語提示請他先取消一些。防的是模型連續誤判把長輩的行程表灌爆。

另有輸入驗證：`title` 非空、提醒時刻不得落在過去、不得超過 `SCHEDULE_MAX_DAYS_AHEAD`（預設 365 天）。違反一律回口語提示、不寫入（工具永不拋，沿用 registry 慣例）。

### 反問行為（`agent.py` SYSTEM_PROMPT 增補）

寫進系統提示的規則：

- 長輩講出**具體時間＋一件要做的事**時，反問要不要提醒，並**依事情性質提議提醒時刻**：需要出門、赴約的提早 15–30 分鐘；在家做的事就準時。沒有具體時間（「等下」「改天」）**不要問**，照常閒聊。
- 長輩答「好／對／麻煩你」就呼叫 `create_schedule`，然後用一句話複誦實際排定的時刻與事情。
- 長輩說不用就不建，**同一段對話不再追問這件事**。
- 長輩問「我今天有什麼事」用 `list_schedules`；說「我明天不去了」先 `list_schedules` 再 `cancel_schedule`。
- 吃藥、回診照建（`kind` 分別為 `medication`、`appointment`），但不要聲稱自己動了家人的設定。

反問門檻是本功能最容易失控的地方（門檻低＝金孫變得很煩），故納入 evals 情境案例，見測試段。

### 家屬入口（統一）

**API**（`web/routers/schedules.py`，取代 `medications.py` 與 `appointments.py`）：

| 方法 | 路徑 | 用途 |
| :-- | :-- | :-- |
| GET | `/api/v1/elders/{elder_id}/schedules` | 列出該長輩的排程（可帶 `kind` 篩選） |
| POST | `/api/v1/elders/{elder_id}/schedules` | 新增（`create_schedule` handler） |
| PATCH | `/api/v1/schedules/{schedule_id}` | 修改 |
| DELETE | `/api/v1/schedules/{schedule_id}` | 取消（`delete_schedule` handler → Service `cancel_group`） |

授權、錯誤信封、JSON 欄位命名（snake_case）一律比照既有 `medications.py`／`appointments.py`。以 `group_id` 為單位操作「一件事」：PATCH／DELETE 作用於整組。

刪除一律為**軟刪**：`cancelled_at` 寫入時刻而非移除列。健康報告與每晚反思都會回看歷史，硬刪會讓「他上週把回診提醒取消了」這件事憑空消失；而那正是家屬最該看到的訊號。保留期由 P5 的清理 job 依 `SCHEDULE_RETENTION_DAYS` 處理。

**LINE 選單**：`binding/session.py` 新增 `SCHEDULE_*` 狀態組，取代 `MED_*` 與 `APPT_*`。流程：「提醒設定」→ 1 新增／2 查看／3 刪除 →（多位長輩時）選長輩 →（新增時）選類型：1 用藥／2 回診／3 其他 → 依類型問名稱與時間 → 完成。

**App**：新增 `guardian/elder/[elderId]/schedules.tsx`（可增刪改），移除 `medications.tsx`、`appointments.tsx`；`lib/api.ts` 補 CRUD；`lib/medicationSlots.ts` 由「四時段列舉」改為「新增用藥時的預設時刻」常數。

### 環境變數（新增 `SCHEDULE_` 前綴）

| 鍵 | 預設 | 說明 |
| :-- | :-- | :-- |
| `SCHEDULE_MAX_ACTIVE_PER_ELDER` | 20 | 每位長輩有效排程上限 |
| `SCHEDULE_DISPATCH_WINDOW_SECONDS` | 90 | 到期判定窗（吸收每分鐘掃描的抖動，**非補發窗**），早於此窗即作廢 |
| `SCHEDULE_MAX_DAYS_AHEAD` | 365 | 允許排到多久以後 |
| `SCHEDULE_RETENTION_DAYS` | 30 | 已結案／已取消排程的保留天數，之後由清理 job 刪除 |

既有 `MEDICATION_*_HOUR` 與 `APPOINTMENT_REMINDER_HOUR` **保留**，語意從「全系統派送鐘點」改為「新增時的預設鐘點」，並供遷移使用。

## 遷移

`schedules/migration.py` 的 `backfill_from_legacy(db, *, settings, clock)`，冪等（以 `group_id` 等於原 id 判定已遷移則跳過），可重跑：

- `medications`：每筆的每個 slot 展開成一列，`repeat_kind=daily`、`repeat_time` 取該 slot 對應的 `MEDICATION_*_HOUR`、`group_id`＝`medication_id`、`kind=medication`、`created_by=guardian`、`audience=elder`。
- `appointments`：每筆展開成兩列（前一天、當天），`repeat_kind=once`、`scheduled_at` 取該日期的 `APPOINTMENT_REMINDER_HOUR`、`event_at` 取 `date`＋`time`（`time` 為空則 NULL）、`group_id`＝`appointment_id`、`kind=appointment`、`created_by=guardian`、`audience=elder_and_guardian`。已過期的回診不遷移。

**遷移行為與現況一字不差**：鐘點照原設定寫進每一列，長輩收到的訊息與時刻不變。差別只在家屬之後能逐筆改。

**遷移的價值定位**（Leo 2026-07-25 確認：內測庫與各組員個人庫**只有測試資料**，無正式資料）：因此遷移程式的目的不是保護正式資料，而是讓七位組員的個人庫在部署時自行癒合、不必手動重建測試場景。連帶三個放寬：遷移失敗**不是**部署阻斷條件（記 ERROR、不中止 `ensure_schema` 的其餘步驟）；P2 的驗收標準是「新 job 的行為正確」而非「舊資料一筆不漏」；舊表可在 P3 完成後即刪，不必為了保險而長期並存。

⚠ 既有庫升級路徑必須實測：空的測試庫測不到舊表升級。`ensure_schema` 內順序固定為**建表 → 遷移 → 建索引**，且遷移排在 `MEDICATIONS_DDL`／`APPOINTMENTS_DDL` 之後。

## 已知取捨與風險

1. **P2 是行為切換點**：派送邏輯從五個每日 job 換成一個每分鐘 job，新 job 有 bug 時長輩會整批收不到提醒。因為庫裡只有測試資料，這一刀的風險**全在程式行為、不在資料**——緩解手段相應調整為「切換前以 admin 端點實跑三種 kind 各一遍」，而非資料備援。
2. **`scheduler_state` 寫入量**：從每天約 10 次變成每分鐘 1 次（1440 次／天）。單列 UPDATE，可接受；Opik trace 量因 fanout 母體為空不開 trace 而與現況同級。
3. **家屬要重新熟悉入口**：三個入口併成一個是刻意的體驗變更（決策 12），不是副作用。
4. **合併不會讓行為差異消失**：用藥的「多顆合併一則」與回診的「兩次提醒＋家屬同收」在新模型裡變成 kind 專屬策略，仍需各自的測試守住。
5. **長輩自設用藥會與家屬設定並存**：決策 7 的明示代價——同一種藥兩邊都設就會收到兩則提醒。第一版不做比對（藥名口說難以比準）。

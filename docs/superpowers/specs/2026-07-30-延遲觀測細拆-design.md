# 延遲觀測細拆（memory_assemble 子 span）設計

> **日期**：2026-07-30
> **狀態**：已核可（Leo 於對話中核可「埋點細拆先行」方向，並委由代理選定首項）
> **目的**：為降低語音管線端到端延遲做準備——先把最慢一段（情境組裝，實測約 2.9 秒）的內部耗時拆到可見，才有數據決定 rerank 去留與後續優化順序。

## 背景

現況 Opik 的 span 樹在情境組裝這一段只有兩層：

```
care_turn_voice
└─ memory_assemble（~2.9s）
   └─ mem0_search（~2.3s，兩路並行檢索）
```

`mem0_search` 內部（Gemini embedding → Supabase 向量查詢 → LLM rerank）發生在
mem0 函式庫裡，完全不可見；七個事實提供者與短期記憶查詢也各自隱形。而
「rerank 是否值得關掉」是目前預期收益最大的延遲決策，被這個盲區擋住。

## 目標

一輪對話後，Opik waterfall 呈現：

```
memory_assemble
├─ shortterm_recent                 ← 今日對話查詢（Supabase）
├─ mem0_search
│  ├─ mem0_search_raw（原話路）
│  │  ├─ mem0_embed                 ← Gemini embedding API
│  │  ├─ mem0_vector_search         ← Supabase 向量查詢
│  │  └─ mem0_rerank                ← Gemini LLM rerank（開關開著才有）
│  └─ mem0_search_raw（健康增補路）
│     └─ …同上
└─ gather_facts
   ├─ facts_0_TimeFacts
   ├─ facts_1_ElderProfileFacts
   ├─ facts_2_ScheduleFacts …（索引＝注入順序，共七路）
   └─ facts_6_LocationFacts
```

## 非目標

- **不動任何決策路徑**：純觀測，分級／通報／攔截／合併排序一字不改。
- **不改 rerank 設定**：要不要關 rerank 是拿到數據之後的下一個工項。
- **網路段量測**（音檔上傳耗時、App 端 RTT、回應 `processing_ms`）：與 App 端
  改動綁在一起才有完整意義，獨立成下一工項。

## 設計

### 1. mem0 內部三段（`memory/longterm/mem0_factory.py`）

mem0 2.0.10 的 `Memory` 實例屬性已實測確認：`embedding_model`／`vector_store`／
`reranker`（未配置為 `None`）。`build_mem0_memory` 建構完成後，以既有的
`tracing.track` 包裝**實例上的 bound method**（instance attribute 覆蓋，不動類別）：

| 包裝點 | span 名 | capture 策略 |
| :--- | :--- | :--- |
| `embedding_model.embed(text, memory_action)` | `mem0_embed` | input 開（查詢文字）、output 關（768 維向量是噪音） |
| `vector_store.search(query, vectors, top_k, filters)` | `mem0_vector_search` | input 開但 `ignore_arguments=["vectors"]`、output 關 |
| `reranker.rerank(query, documents, top_k)` | `mem0_rerank` | input 開但 `ignore_arguments=["documents"]`（候選集可達數十筆記憶原文）、output 關 |

- `vector_store.keyword_search` **不包**：Supabase provider 繼承基底的 `return
  None`，零網路成本，包了只會多一顆恆零的 span。
- 包裝以 `getattr` 防禦屬性缺席（mem0 升版屬性改名時記 warning、原樣回傳），
  比照 `wrap_genai` 的「包裝失敗不可影響可用性」。
- 附帶收益：`add` 路徑（每晚 consolidation）同樣經過 `embed`／`vector_store`，
  子 span 免費出現在 `mem0_add` 底下。

### 2. 逐路檢索 span（`memory/longterm/store.py`）

`Mem0LongTermStore._search_raw` 加 `@tracing.track(name="mem0_search_raw",
capture_input=True, capture_output=False)`。兩路（原話／健康增補）已在
`copy_context()` 帶入的執行緒裡跑，span 會正確掛在 `mem0_search` 下；
input 的 `query` 欄位即可分辨是哪一路。output 關：最終合併結果已由外層
`mem0_search` 捕捉，重複攤一份只是燒儲存。

### 3. 事實提供者逐路 span（`memory/recall.py`）

- `_gather_facts` 加 `@tracing.track(name="gather_facts", capture_input=True,
  capture_output=False)` 作為分組父 span。
- `SessionMemory.__init__` 一次性把每個 provider 的 `facts` bound method 包成
  `facts_{i}_{類名}`（`i`＝注入索引）。索引入名有兩個理由：
  `ScheduleFacts` 註冊三次（三種 kind），純類名會撞名；且注入順序本身是
  prompt 契約，帶序號的 waterfall 直接對得上段落順序。
- provider 的 `capture_output=True`：這是 capture 總原則的**唯一例外**——
  合併後結果看不到「哪一路回了 `None`（該段缺席）」，而缺席正是查
  「為什麼這輪沒帶用藥段」時要看的東西；`FactSection` 單段僅數十字，重複成本可忽略。
- 並行結構、按索引回填、單一提供者失敗略過——全部不動。

### 4. 短期記憶 span（`memory/shortterm.py`）

`PgMemoryStore.recent` 加 `@tracing.track(name="shortterm_recent",
capture_input=True, capture_output=False)`。output 關：`memory_assemble` 的
output（TurnContext.history）已含同一份內容。`FakeMemoryStore` 不加（測試替身
不需要觀測）。

### capture 總原則

本工項的目的是**量時間**，不是多存一份內容：凡外層 span 已捕捉的內容，內層
一律關 output；大型二進位／向量／候選集一律 `ignore_arguments` 排除。對話內容
只進 Opik 的既有政策（2026-07-27）不變。

## 錯誤處理

- 停用（`OPIK_ENABLED=false`／Opik 不可達）時，`tracing.track` 本來就退化為
  identity——所有新增包裝零行為差異。
- `mem0_factory` 的包裝失敗（屬性缺席、型別不符）記 warning 後回傳未包裝的
  實例，絕不讓觀測壞掉記憶功能。

## 測試計畫

沿用 `test_tracing_decorators.py` 的 hermetic 模式（monkeypatch `opik.track`
收集 name／kwargs，不連真 Opik）：

1. `test_memory_longterm_mem0_factory.py`：以 stub Memory 驗證三個包裝點的
   span 名與 capture 參數；`reranker=None` 時不包且不炸；屬性缺席時 warning
   ＋原樣回傳；停用時包裝後行為與原函式一致。
2. `test_memory_longterm_store.py`：`_search_raw` 帶 track（span 名正確）；
   既有並行、dedup、fail-safe 測試不得變紅。
3. `test_memory_recall.py`：七路 span 名含索引與類名；順序回填、失敗略過的
   既有測試不得變紅。
4. `test_memory_shortterm.py`（若無此檔則放既有短期記憶測試檔）：`recent`
   span 名正確；停用時行為不變。

## 風險與取捨

- **mem0 升版屬性改名**：以 getattr 防禦＋warning，退化為「少子 span」而非壞功能。
- **span 量增加**：每輪多約 12 顆 span，Opik 自架後端量級無虞。
- **instance attribute 覆蓋 bound method**：非常規但影響面封在工廠內；
  替代方案（fork mem0／改用 mem0 hook）成本與維護負擔都更高。

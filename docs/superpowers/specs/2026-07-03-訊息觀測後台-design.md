# 訊息觀測後台（Admin Observability Console）設計

- 日期：2026-07-03
- 狀態：已與需求方（Leo）逐段確認
- 相關文件：`docs/superpowers/specs/2026-07-03-naming-decisions.md`（命名規範）

## 1. 目標與範圍

給 7 人開發團隊除錯用的後台網頁，觀測系統中的訊息流動與處理過程。

**觀測對象**（四類訊息＋輕量 MLOps 指標）：

1. 長輩與 AI 的對話紀錄（`turns`）
2. 系統主動推播紀錄（`reminder_logs`）
3. LINE webhook 原始事件（新增落庫）
4. 安全／風險事件（`risk_events`）
5. MLOps 指標：ASR／LLM／TTS 各階段延遲、錯誤、token 用量（新增落庫）

**四個視角**：

1. 總覽儀表板（統計卡片＋趨勢圖）
2. 全域即時訊息流（所有長輩混流，輪詢自動更新）
3. 單一長輩對話時間軸（對話、推播、風險交錯）
4. 單輪對話處理鏈路（webhook → ASR → LLM → TTS → 回覆，含各段延遲）

**明確納入**：音檔播放（長輩原始語音＋TTS 輸出）。
**明確排除**：專業觀測平台（Langfuse／Grafana）、個人帳號密碼登入、寫入類管理功能（純唯讀）。

## 2. 現況缺口（設計動機）

- webhook 原始事件、各階段延遲／token 目前完全沒有落庫。
- 長輩原始語音抓下來餵 ASR 後即丟棄；TTS 音檔雖上傳 Supabase Storage，URL 沒有存。
- 既有 `turns`／`reminder_logs`／`risk_events` 有資料，但彼此無法串成單輪鏈路。

## 3. 架構決策

已評估三案：（A）單一 trace 事件表、（B）各階段專表、（C）最小補充複用既有表。
**決議採方案 B（各階段專表）**：schema 型別嚴謹，每張表帶 `trace_id` 欄位貫穿單輪鏈路（一輪對話一個 uuid），彌補分表後鏈路視角的串接需求。

## 4. 資料層

### 4.1 新增 5 張表

皆遵循命名規範：複數表名、全稱主鍵、`created_at DOUBLE PRECISION`（epoch 秒）。
建表加入 `db.py` 的 `ensure_schema`（`CREATE TABLE IF NOT EXISTS`）。

| 表 | 欄位 | 記錄什麼 |
|---|---|---|
| `webhook_events` | `webhook_event_id`（pk）、`trace_id`、`line_user_id`、`event_type`、`message_type`、`payload`（JSONB 原始事件）、`created_at` | LINE 進站原始事件 |
| `asr_calls` | `asr_call_id`（pk）、`trace_id`、`line_user_id`、`status`、`latency_ms`、`transcript`、`source_audio_url`、`error_message`、`created_at` | ASR 辨識（含長輩原始音檔 URL） |
| `llm_calls` | `llm_call_id`（pk）、`trace_id`、`line_user_id`、`status`、`latency_ms`、`model_name`、`input_tokens`、`output_tokens`、`content`、`error_message`、`created_at` | LLM 生成；一輪可多筆（tool 呼叫）；token 欄位可為空（視 Gemini 回傳） |
| `tts_calls` | `tts_call_id`（pk）、`trace_id`、`line_user_id`、`status`、`latency_ms`、`content`、`audio_url`、`error_message`、`created_at` | TTS 合成（含輸出音檔 URL） |
| `replies` | `reply_id`（pk）、`trace_id`、`line_user_id`、`kind`（voice／text）、`status`、`latency_ms`、`created_at` | 回覆送出 LINE 的結果 |

### 4.2 既有表

`turns`、`reminder_logs` 沿用不動。`risk_events` 加一個可為空的 `trace_id` 欄位
（`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，加入 `ensure_schema`），讓風險事件掛回該輪鏈路。

### 4.3 程式結構與記錄點

- 新增 `src/kinsun/observability/` 模組（不可數名詞，比照 `audio/` 先例）：
  - `models.py`：各表對應的領域模型。
  - `store.py`：單一 `TraceStore`（Protocol）＋`PgTraceStore`＋`FakeTraceStore` 三件套；
    寫入動詞用 `record_*`（append-only），查詢用 `get_*`／`list_for_*`。
- `channels/line/channel.py`：收到事件時產生 `trace_id`、記 `webhook_events`；
  語音訊息同時把原始音檔用既有 `SupabaseAudioPublisher` 上傳（`inbound/{yyyymmdd}/` 資料夾，
  沿用既有過期清理）。
- `pipeline.py`：各階段前後計時並 `record_*` 到對應表。
- **記錄失敗絕不中斷對話**：所有 `record_*` 包 `try/except`＋warning log（比照風險落庫慣例）。
- 資料保留：新增排程清理工作，刪除超過 `ADMIN_RETENTION_DAYS`（預設 14 天）的觀測資料
  （5 張新表；既有三張表不在清理範圍）。

## 5. 後端 API 與驗證

### 5.1 驗證

- 環境變數 `ADMIN_API_KEY`（新子系統前綴 `ADMIN_`；同步補 `.env.example` 與命名決策文件）。
- 請求帶 `X-Admin-Key` 標頭；FastAPI dependency 以 `hmac.compare_digest` 常數時間比對，不符回 401。
- 所有 admin 端點皆唯讀 GET。

### 5.2 端點（新增 `src/kinsun/web/admin_api.py`）

| 端點 | 視角 | 內容 |
|---|---|---|
| `GET /admin/overview` | 儀表板 | 今日訊息量、各階段錯誤率與平均／p95 延遲、token 用量、風險事件數、活躍長輩數（當日至少一輪對話）；近 24 小時逐時訊息量（聚合端點用單數，比照 `/health-report`） |
| `GET /admin/messages?after=&limit=` | 全域訊息流 | `turns`＋`reminder_logs`＋`risk_events` 依時間混流、新的在前；`after` 時間戳拉增量 |
| `GET /admin/elders` | 時間軸入口 | 全部長輩清單（名字、`line_user_id`、最後活動時間） |
| `GET /admin/elders/{elder_id}/timeline?date=` | 長輩時間軸 | 當日對話、推播、風險合併時間軸；語音輪附音檔 URL 與 `trace_id` |
| `GET /admin/traces/{trace_id}` | 單輪鏈路 | webhook 事件 → ASR → LLM（可多筆）→ TTS → 回覆＋掛上的風險事件；各段延遲、狀態、錯誤、音檔 |

### 5.3 約定

- 路徑用 `elder_id`（業務主鍵），後端解析對應 `line_user_id`（兩者永不混用）。
- JSON 欄位 snake_case，與前端 TS 型別完全一致。
- 錯誤：金鑰錯 401；`elder_id`／`trace_id` 不存在 404；`limit` 設上限並驗證查詢參數型別。

## 6. 前端

### 6.1 入口與結構

- `frontend/` 加第二個 Vite 入口 `admin.html`（程式碼放 `src/admin/`），與 LIFF 家屬端分離、共用工具鏈。
- React Router `basename="/admin"`；後端比照 LIFF dist 方式掛載靜態頁。
- 金鑰流程：首次進入顯示金鑰輸入畫面，存 `localStorage`；`src/admin/api.ts` 統一帶
  `X-Admin-Key`，收到 401 清金鑰回輸入畫面。

### 6.2 頁面

1. **總覽儀表板**（`/admin/`）：統計卡片＋近 24 小時逐時訊息量長條圖（純 SVG，不加圖表套件）。
2. **全域訊息流**（`/admin/messages`）：時間、長輩名、類型徽章（對話／推播／風險）、內容摘要；
   有 `trace_id` 可點進鏈路頁。
3. **長輩時間軸**（`/admin/elders` → `/admin/elders/:elderId`）：日期選擇器＋對話氣泡
   （長輩左、金孫右），推播與風險以系統卡片插入，語音輪內嵌 `<audio controls>`。
4. **單輪鏈路**（`/admin/traces/:traceId`）：垂直步驟列，各段延遲毫秒、狀態徽章、
   可展開錯誤訊息與原始 payload JSON、音檔播放。

### 6.3 更新策略

- 儀表板與訊息流每 5 秒輪詢增量；tab 不可見時暫停（`visibilitychange`）。
- 時間軸與鏈路頁載入抓一次＋手動更新。
- 輪詢失敗顯示「連線中斷，重試中」，不清空已載入資料。

## 10. 取捨與未來工作

- **音檔走公開 bucket URL**：知道 URL 即可聽，與現行 TTS 音檔同一風險水位，開發階段可接受；
  正式上線前應改簽名 URL（未來工作）。
- **共用金鑰**：無個人稽核軌跡，開發工具可接受；正式營運需個人帳號與權限控管（未來工作）。
- **輪詢而非 SSE／WebSocket**：5 秒延遲對除錯足夠，換取實作與維護成本大幅降低。
- **token 欄位可為空**：現行 LLM client 未回傳 usage 時先記空值，實作時視 Gemini 回應擴充。

## 11. 實作修正（2026-07-03 實作時定案）

- admin API 掛在 `/api/admin/*`（沿用既有 `/api` 前綴與前端 dev proxy）；`/admin` 路徑留給後台靜態頁。
- `audio_url` 欄位放 `replies` 表（回覆實際送出的公開 URL）；`tts_calls` 不設此欄——
  音檔 URL 在上傳後才存在，屬回覆送出階段。
- `llm_calls` 現階段每輪記一筆（涵蓋整個 agent 處理含工具迴圈）；表結構支援多筆，
  逐次 LLM 呼叫記錄列入未來工作。
- 時間軸的語音卡（kind=voice）來源為 `asr_calls`（長輩原話）與 `replies`（金孫語音回覆）。
- 進站音檔清理沿用 `AUDIO_RETENTION_DAYS`（音檔）；`ADMIN_RETENTION_DAYS` 只管觀測五表。
- 主動關懷推播（問候／失聯關心）補記 `reminder_logs`，kind 為
  `proactive-greeting`／`proactive-care`，讓訊息流與時間軸看得到主動推播。

# 開場轉場改「光暈綻放」設計文件

- 日期：2026-08-13
- 狀態：**設計已核定，尚未實作**
- 相關決策（皆為 Leo 於 2026-08-13 拍板）：
  - 換掉現行的撕裂展開轉場，理由是**調性**：「撕開」帶破壞感，與「陪伴長輩」的產品調性衝突
  - 換成**光暈綻放**——從使用者按下的按鈕中心綻放一圈暖黃光暈
  - 一併改名 `TearTransition` → `BloomTransition`（留著舊名字會是謊話）
  - 動畫長度維持 700 毫秒不縮短
  - 不動 `prefers-reduced-motion` 的 200 毫秒淡出短路徑

## 背景與動機

`web/src/stage/TearTransition.tsx`（spec `2026-07-30-web-demo-design` §5.2）把開場頁沿一道手調鋸齒裂痕複製成左右兩份，各自 `translateX(±60%)` 並 `rotate(±3deg)` 滑開，露出後方已掛載的雙欄舞台。

技術上沒有問題——零依賴、純 `transform`、GPU 合成、無障礙短路徑齊備。要換掉的是**隱喻**：這是一款陪長輩說話的產品，而進場的第一個動作是把畫面撕成兩半。這一頁是畢典展示的門面，第一印象由它決定。

「光暈綻放」把同一個「揭開舞台」的動作換成相反的隱喻：**你伸手一按，畫面為你亮起來**。動作的起點是使用者的手指，而不是一道裂痕。暖黃 `--color-action: #F9DF77` 是品牌既有的主要行動色，金黃色的光與「金孫」的字面意義也對得上。

### 為什麼不是其他兩個候選

- **掀開一頁**（開場頁像卡片被掀起、微幅放大上浮淡出）：最單純、風險最低，但展示時幾乎不會被注意到，等於用掉一次機會卻沒有記憶點。
- **呼吸淡入**（開場頁淡出、舞台從 96% 放大上浮）：最溫柔，但這是現代 App 的標準轉場、辨識度最低；而且要讓舞台自己動起來，得改 `StagePage` 或多包一層，是三案裡唯一增加跨元件耦合的。

## 不在本次範圍內

- **舞台本身的動效**：舞台仍然是靜態顯露，不加入場動畫。
- **`prefers-reduced-motion` 的行為與數值**：仍是 200 毫秒純淡出、不播光暈。
- **路由與掛載架構**：舞台仍由 `App.tsx` 在動畫期間先掛好（見 `App.tsx` 檔頭三段 ⚠️ 說明），本次一格都不動。
- **動畫長度**：維持 700 毫秒。它同時是後方舞台載入資料的掩護，縮短只會讓使用者更早看到還沒載完的畫面。
- **開場頁的版面與文案**：不動。

## 動畫設計

總長 700 毫秒，overlay 裡兩層同時進行；舞台不動（已在後方掛載，光散去即顯露）。

⚠️ overlay 裡的開場頁是**單一份** children，不再像撕裂那樣複製成左右兩份——這也順帶讓動畫期間 DOM 裡的重複內容從兩份降為一份。

### 光暈層

| 項目 | 值 | 理由 |
| :-- | :-- | :-- |
| 尺寸 | `40vmax` 見方的圓 | 用 `vmax` 而非固定 px，直式與橫式螢幕都一定蓋得滿 |
| 底色 | `radial-gradient(circle, #F9DF77 0%, rgba(249, 223, 119, 0.55) 45%, transparent 70%)` | 邊緣柔化到透明，讀起來是「光」而不是「一塊黃色圓形」 |
| 位移 | `transform: translate(-50%, -50%) scale(0.2 → 4)`，700 毫秒，`cubic-bezier(0.33, 1, 0.68, 1)` | 以 `origin` 為圓心；`scale` 走合成器，不觸發版面重算。曲線夠快但不暴衝，整段時間都還在長大 |
| 透明度 | `opacity: 0.9 → 0`，**延遲 150 毫秒、長度 420 毫秒**，`cubic-bezier(0.4, 0, 1, 1)` | 先撐住再收。放大與淡出**必須是兩條曲線**，理由見下 |

> ⚠️ **放大與淡出不可共用一條曲線，淡出也不可跑滿全程**——這兩點都是實作後用
> Playwright 逐格量測改出來的，原始設計兩者都寫錯：
>
> 1. 原訂共用 `cubic-bezier(0.22, 1, 0.36, 1)`（easeOutQuint）。實測光暈在轉場開始後
>    **240 毫秒就淡到 opacity 0.10**，而開場頁要淡滿 700 毫秒——畫面上是「閃一下，
>    然後一段無關的淡出」，正是設計要避開的「爆開」。
> 2. 改成兩條曲線、淡出跑滿 700 毫秒之後，換成尾巴切掉：CSS 真的開始動比 `onDone`
>    的計時器晚約 100 毫秒（計時器在 effect 起跑，CSS 要等 rAF ＋再一次
>    render／commit ／首次繪製），`onDone` 拔掉 overlay 的當下光暈還有 **0.33**
>    不透明度，金光會「啪」一聲被切掉。讓淡出提早收乾淨才吃得掉這個落差。
>
> 定稿後的實測值（1280×800、鍵盤 Enter 觸發）：250 毫秒 scale 1.98／opacity 0.90，
> 350 毫秒 2.87／0.84，450 毫秒 3.44／0.67，650 毫秒 3.95／0.12。

### 開場頁層

`opacity: 1 → 0`、`transform: scale(1 → 1.04)`，`ease-out`，同 700 毫秒。

輕微**放大**而非縮小：縮小讀起來是「被推走」，放大才是「退進光裡」。幅度只有 4%——再大就會變成 zoom 特效，蓋過光暈本身。

### 光暈圓心（`origin`）

由 `GatePage` 的「開始使用」按鈕算出：`e.currentTarget.getBoundingClientRect()` 的中心點。

⚠️ **不可用滑鼠座標（`clientX`／`clientY`）**：鍵盤按 Enter／Space 觸發 click 時兩者都是 `0`，光暈會從畫面左上角冒出來。`getBoundingClientRect()` 對滑鼠、觸控、鍵盤三種操作都給同一個正確答案。

`origin` 為選用參數，省略時退回畫面正中央（`50% / 50%`）——元件不該假設呼叫端一定給得出座標。

## 元件契約

```ts
export const BLOOM_DURATION_MS = 700;
export const REDUCED_MOTION_MS = 200;

export function BloomTransition(props: {
  active: boolean;
  onDone: () => void;
  origin?: { x: number; y: number };
  children: ReactNode;
}): ReactNode;
```

相對現況只多一個 `origin`。以下三項現有設計**原封保留**，它們各自修過一個真實缺陷：

1. **`onDoneRef`**：`onDone` 存進 ref、不進相依陣列。舞台在動畫期間掛載並發請求，那正是父層最容易重新渲染的時刻；`onDone` 留在相依陣列會讓計時器被反覆重排，極端情況下永遠不觸發。
2. **`prefersReducedMotion` 短路徑**：掛載當下讀一次，`true` 就只做 200 毫秒淡出、完全不掛光暈（W-11 無障礙要求）。
3. **`aria-hidden` overlay**：overlay 裡的內容是裝飾，真正的內容是後方已掛載的舞台。不隱藏會被讀螢幕軟體唸兩遍。

呼叫端 `App.tsx` 需要記住 `origin`：`onStart` 從無參數改成收一個座標，狀態 `tearing` 更名為 `blooming`。

## 測試

`stage/BloomTransition.test.tsx` 保留現有 7 條契約測試（動畫本身無法在 jsdom 驗——沒有版面與合成器，測的是契約）：

1. 未啟動時原樣顯示內容、不掛 overlay
2. 啟動時掛上光暈
3. 播完通知呼叫端（`advanceTimersByTime(BLOOM_DURATION_MS)`）
4. 關了動態效果時改走 200 毫秒短路徑
5. 關了動態效果時不掛光暈
6. 父層在動畫期間重繪也不會重排計時器
7. overlay 對讀螢幕的人隱藏

新增兩條，一正一反把 `origin` 這個新參數夾住：

8. **給了 `origin` 時，光暈以那個點為圓心**
9. **沒給 `origin` 時退回畫面中央、不擲例外**

`App.test.tsx` 有一條驗「動畫期間開場頁內容不會重置成『正在確認服務狀態…』」的測試，目前靠 `within(screen.getByTestId("tear-left"))` 取內容。改為單一份 children 後改指向 overlay 本身，**斷言意義不變**——它守的是「運營狀態的 hook 住在 App 而不是 GatePage」這條不變量，不是守撕裂的實作。

## 風險

- **光暈在低階顯示卡上的表現**：`transform` 與 `opacity` 走合成器，與原本的撕裂同一個效能等級（那也是全螢幕兩層 `transform`），不預期退步。Chromium 無頭跑過沒有異常，但**仍未在實際展示用的那台筆電上看過**——這條風險尚未關閉。
- **暖黃光暈與靛藍按鈕的視覺衝突**：✅ 已驗證不成立。實機截圖（300 毫秒）顯示整個畫面被暖金光洗過、舞台從光裡浮出，讀起來是光而不是撞色。備案（改用 `--color-background-warm-top: #FFF9EC`）不需要動用。
- **按下到畫面開始動之間約有 100 毫秒空檔**：來自 rAF ＋ React 再一次 render／commit。**這不是本次引入的**，原本的撕裂用同一套 `moved` 狀態機，落差一樣存在。目前未處理；真要消掉得改用 CSS `@keyframes`（`theme.css` 已有 `slideDown` 的先例）並拿掉 `moved` 狀態。

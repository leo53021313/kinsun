# 長輩客製化聲音——家屬錄音介面設計文件

- 日期：2026-08-12
- 狀態：**設計已核定，尚未實作**
- 相關決策（皆為 Leo 於 2026-08-12 拍板）：
  - **只做網頁版**（`web/`，掛 `/demo`）。App（Expo）這次不做。
  - 同意欄位**預設帶登入家屬的名字、可以改**，旁邊另有必勾的同意框。
  - 錄音**不到 8 秒不讓送出**（送出鍵停用並說明原因）。
  - 在 `Leo` 分支上施工，不另開分支。

## 背景與動機

`voice_profiles` 這條功能鏈**只差最後一哩**：資料表、`VoiceProfileStore`、`VoicePipeline` 的聲音解析、DGX 端 CosyVoice zero-shot、四道退回全域預設聲音的防線，全部就緒且有測試。2026-08-11（06 §v1.32）補上了家屬面的四支 HTTP 端點，理由寫得很清楚——「在此之前 voice_profiles 只有機制沒有入口」。

但那次只補到 HTTP 邊界。2026-08-12 的全庫盤點確認：`web/`、`app/`、`frontend/`、`shared/` 四處 grep `voice.profile` **零命中**。也就是說目前的狀態是「有 API 入口、沒有畫面入口」，家屬依然建立不出任何一筆設定，**「每位長輩可有專屬聲音」實務上仍等於「全系統一個聲音」**。

還有一個連帶後果：PR #104／#106 整合期修掉的「家屬重錄完全不生效」（DGX 端參考音檔快取只認 `elder_id`，重錄覆蓋同一路徑後命中舊快取），到今天**沒有任何辦法驗證那個修復是對的**——因為沒有畫面能觸發一次重錄。

## 不在本次範圍內

- **App（Expo）端的錄音介面**：錄音底層是 `expo-audio`、與瀏覽器的 `MediaRecorder` 不共用，畫面要另寫一份。Leo 決定這次只做網頁版。
- **LIFF（LINE 家屬端）**：已凍結，不新增介面。
- **兩種人設各有各的聲音**：現況兩種人設共用同一組聲音（見 `2026-08-05-金孫人設-design.md`「不在範圍」）。本次不改變這件事——一位長輩仍只有一組生效聲音。
- **後端任何改動**：四支端點的契約完全不動。
- **長輩端的任何改動**：長輩不會看到這個功能，他只會聽到聲音變了。

## 後端契約（既有，本次不動）

| 端點 | 用途 | 關鍵細節 |
| :--- | :--- | :--- |
| `GET /api/v1/voice-profile-script` | 取要照唸的稿子 | 回 `{script, tips, rationale}`。**免認證**。稿子由伺服器下發，前端不得寫死——它同時是 `voice_profiles.prompt_text`，兩邊各存一份遲早漂移 |
| `GET /api/v1/elders/{elder_id}/voice-profile` | 查目前狀態 | 回 `{elder_id, has_profile}`，有設定時多回 `{consented_by, granted_at}`。**刻意不回音檔也不回可下載網址** |
| `PUT /api/v1/elders/{elder_id}/voice-profile` | 上傳／覆蓋 | body＝**原始音檔 bytes**（非 multipart），`consented_by` 走 **query param**（body 被音檔佔滿）。回 `{elder_id, has_profile, consented_by}` |
| `DELETE /api/v1/elders/{elder_id}/voice-profile` | 撤銷，回全域預設 | 204 |

錯誤碼：400 `consent_required`（沒帶同意人）／400 `missing_audio`（空 body）／415（content-type 不是 `audio/*`）／413（> 10MB）／404（不管理這位長輩）／502 `speech_unavailable`（上傳失敗，**不寫設定檔**）／503 `speech_unavailable`（功能未啟用）。

本機環境已確認啟用：`TTS_BACKEND=dgx`、`SUPABASE_URL`／`SUPABASE_SERVICE_KEY`／`AUDIO_BUCKET` 皆已設定，不會走 503。

### 錄音格式不需要前端處理

瀏覽器 `MediaRecorder` 產出的容器各家不同（Chrome／Firefox 為 `audio/webm;codecs=opus`，Safari 為 `audio/mp4`）。DGX 端 `services/tts/server.py::_normalize_to_wav` 已經預期到這件事，一律先用 ffmpeg 轉成 16k 單聲道 wav 再餵給 CosyVoice（原因：CosyVoice 讀檔走 soundfile／libsndfile，**讀不了 webm**）。因此前端只需送出真實的 MIME type，不需要自行轉檔。

## 架構

### 為什麼是獨立子畫面，而不是長輩詳情頁裡的一個區塊

`ElderDetailScreen.tsx` 已經 451 行，裝著健康報告、每日摘要、排程、人設、長輩帳密、家屬邀請、裝置重綁七個區塊。錄音是一整套有狀態的流程（權限、計時、試聽、同意、送出、撤銷），塞進去會讓該檔逼近專案 800 行上限（`.claude/rules/coding-style.md`）且職責混雜。

改採該畫面**已經在用的既有慣例**：詳情頁放一個顯示現況的小區塊＋一顆進入按鈕，實際內容在獨立畫面，經 `useScreenStack` 推入——與排程、每日摘要、健康報告三者完全相同的作法。

### 重用，不重寫

錄音（`talk/recorder.ts::createRecorder`）、麥克風權限探測（`probeMicrophone`）、失敗分類（`talk/mediaErrors.ts`）、試聽播放（`talk/playback.ts::createWebPlayer`）、iOS 音訊解鎖（`talk/audioUnlock.ts::unlockAudio`）全部沿用長輩對講機那一套現成實作。

這些模組住在 `talk/` 底下，但它們是**通用的瀏覽器媒體能力**、不是對講機協定的一部分（協定核心是 `talkSocket.ts`／`talkGesture.ts`）。家屬端直接 import，不搬家、不複製。

### `recorder.ts` 的唯一改動

`stop()` 目前回 `ArrayBuffer | null`——`new Blob(chunks)` 不帶 type，**錄音的 MIME type 在這一步被丟掉了**。長輩端不在乎（`postTurn` 寫死 `audio/m4a`，後端 ASR 靠 ffmpeg 嗅探容器），但本功能的後端會拿 content-type 去標記 Supabase 上的物件，且 415 檢查看的就是它。

改法是**新增一個 `mimeType(): string` 讀取器**（回傳 `MediaRecorder.mimeType`，未錄音時回空字串），不動 `stop()` 的回傳型別——改型別會波及 `useTalk.ts` 與長輩端整條對講機路徑，為了一個新功能去動正在運作的關鍵路徑不划算。

`MediaRecorder.mimeType` 可能帶 codecs 參數（`audio/webm;codecs=opus`），後端檢查是 `startswith("audio/")`，通過。取不到值時（極少數瀏覽器回空字串）退回 `audio/webm`。

## 畫面流程

### 進入畫面

併行做三件事：抓稿子（`GET /voice-profile-script`）、抓目前狀態（`GET .../voice-profile`）、探測麥克風權限（`probeMicrophone`）。

**權限在進畫面時就問**，不等按下錄音鍵——沿用長輩端在 iOS 上踩過的坑（2026-07-18，權限對話框會吃掉第一次錄音）之後定下的作法。探測完立刻關掉軌道，否則分頁的錄音指示燈會從進畫面就一直亮著。

### 尚未設定過

1. 大字顯示要照唸的稿子，底下列出四條注意事項（皆由伺服器下發，不寫死）
2. 「開始錄音」→ 計時器每 100 毫秒更新，顯示已錄秒數
3. 「停止」→ 取得位元組與時長
4. **不到 8 秒**：送出鍵停用，顯示「這段太短，請把稿子唸完再停」
5. **8 秒以上**：可「試聽」（本機 blob URL 播放，不上傳）、可「重錄」
6. 同意欄預設帶登入家屬的名字（`session.name`），可改；底下一個必勾的同意框
7. 「設定成這個聲音」→ `PUT`，成功後畫面切換成「已設定」狀態

### 已經設定過

最上面顯示「目前使用 ⃝⃝⃝ 的聲音」與設定日期（`consented_by`／`granted_at`），底下兩個動作：「重新錄一段」（回到上面的錄音流程，送出即覆蓋）與「改回預設聲音」（`DELETE`，需二次確認）。

### 試聽為什麼是必要的，不是加分項

後端 `GET` 端點**刻意不回傳音檔也不回傳可下載網址**（原註解：「那是長輩家人的聲音樣本，查詢設定狀態不需要能把它拿走」）。這個決定是對的，但它的副作用是：**一旦送出，家屬再也沒有任何辦法聽到自己錄了什麼**。沒有試聽就是盲送，而錄音品質直接決定長輩往後聽到的每一句話。

## 錯誤處理

| 情況 | 畫面行為 |
| :--- | :--- |
| 麥克風六種失敗 | 各自的白話說明，重用 `MicrophoneProbeResult` 既有分類（`denied`／`not-found`／`in-use`／`insecure-origin`／`unsupported`）；`insecure-origin` 要講「這個網址不是 https，換個網址才行」而不是叫人去開權限 |
| 錄音不到 8 秒 | 送出鍵停用＋說明；不是彈窗 |
| 400 `consent_required` | 理論上前端已擋（同意框必勾），仍要顯示後端訊息，不吞 |
| 413 音檔太大 | 「錄太久了，請重錄一段短一點的」 |
| 502／503 | 「聲音服務暫時不能用，請稍後再試」——**不要顯示成「設定成功」**；後端 502 時刻意沒寫設定檔 |
| 撤銷失敗 | 保持「已設定」狀態，不要樂觀切換 |

資源釋放（麥克風軌道、blob URL、播放器）在**正常結束／錯誤／切頁籤／元件卸載／重複按**五條路徑上都要放掉——長輩端 P3 Task 8 在同一類坑上踩過四次，這裡直接沿用它的 effect cleanup 形狀。

## 測試

- `useVoiceRecording`：計時累加、8 秒門檻的邊界（7.9／8.0）、重錄會丟掉前一段的 blob URL、卸載會關掉麥克風軌道
- `api.ts` 四支：`consented_by` 走 query 而非 body、body 送的是原始位元組（**斷言 `init.body`**——2026-07-31 審查發現 `postTurn` 三條測試都沒斷言 body，刪掉整行仍全綠）、`DELETE` 回 204 不解 JSON
- `VoiceProfileScreen`：四種狀態（沒設定過／已設定／錄太短／送出失敗）的呈現
- 跨瀏覽器人工驗收：Chrome／Firefox／Safari 各錄一次（容器格式不同），且必須在**真的 https 網址**上做——`localhost` 有安全例外，會給出假的安全感

## 已知前提與風險

1. **DGX 端 TTS 需已部署含 `prompt_version` 的版本**，否則**第一次錄音會生效、重錄不會**（舊版忽略未知欄位、不報錯，命中本機快取就不看新網址）。驗收重錄時若聲音沒變，先確認 DGX 版本，不要誤判成前端沒送出去。
2. **一位長輩只有一組聲音**：PK 就是 `elder_id`，重錄即覆蓋。多位家屬同時錄，最後一個送出的生效，畫面上不會有衝突提示。這與後端設計一致，本次不改。
3. **稿子含「阿嬤」兩次**，男性長輩的家屬照唸會有點怪。這是後端稿子的既有取捨（「嬤」是罕用字、模型不示範就念不對），本次不動稿子，但驗收時值得記一筆。

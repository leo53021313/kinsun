## 背景與動機

`2026-07-17-長輩目前地點`（PR #55）的三條人工複驗執行後，發現三個 bug。**其中最嚴重的一個與定位功能無關，且從天氣工具寫出來就存在。**

### Bug 1（既有、嚴重）：問台南的天氣，拿到中國山西的天氣

`tools/weather.py` 的 `_GEOCODE_URL` 沒有限定國家。實測：

```
台南 → 台南 / 山西 / 中国 (35.56, 113.14)
```

金孫會用山西七月的氣溫（陰天 19–27°C）回答問台南天氣的長輩，而且語氣毫無遲疑。**這是目前唯一會主動給長輩錯誤資訊的路徑。**

### Bug 2（PR #55 的疏漏）：定位功能其實完全沒生效

PR #55 改了 `agent.py` 的 `SYSTEM_PROMPT`，**卻沒改 `WEATHER_SPEC` 的 description**——它仍寫著「只有在你已確認長輩要查哪個城市時才呼叫；若不知道地點，先開口問長輩人在哪個城市」。

模型同時看到 system prompt 說「直接用那個地點」與工具說「不知道就先問」，選了保守解。實測（真 Gemini，位置＝3 分鐘前在台南市）：

> 金孫答：阿公，我不確定您現在是在哪個縣市呢？

**今天早上合併的功能，一直沒有作用。** 改掉工具描述後，同一情境金孫立刻改為去查台南的天氣。

⚠️ 複驗 3（anchoring）原本「通過」是假象：位置沒生效時，金孫在所有情境都會反問，看起來就像防線有效。修掉 Bug 2 後重測，它**真的通過**——anchoring 防線本身是有效的。

### Bug 3（整合）：Open-Meteo 的台灣地理編碼不堪用

實測全台 22 縣市（加 `countryCode=TW`，用 `reverseGeocodeAsync` 會回的行政全稱）：

- **原樣查詢：6/22 命中**
- 多變體 fallback（試 `台`→`臺`、去掉「市／縣」字尾）：13/22，**但引入錯誤比對**——`新竹縣` 會命中屏東的一個「新竹」（22.46, 120.47），而新竹市在 24.80, 120.97

多變體 fallback 把「查不到」換成「查錯」，**正是 Bug 1 的失敗模式換地方重演**，故否決。

## 核心洞察：決定天氣的是海拔，不是行政區

Leo 問「能不能細到台北市大安區」。實測回答了這個問題，而答案推翻了「行政區」這個抽象本身：

| 地點 | 目前氣溫 | 天氣 |
| :--- | :--- | :--- |
| 台北市大安區 | 32.4°C | 毛毛雨 |
| 台北市中心 | 32.4°C | 毛毛雨 |
| 台北市北投（陽明山） | 31.1°C | **雷雨** |
| 台中市西屯區 | 27.4°C | 陣雨 |
| 台中市中心 | 27.1°C | 陣雨 |
| 台中市梨山（海拔 2000m） | **18.9°C** | 陣雨 |

**大安區與台北市中心完全一樣**——行政區細分毫無收益。真正有差的是陽明山（天氣類型都不同）與梨山（差 8.5°C），而它們的共同點是**海拔**，不是行政層級。

行政地名表（不論 22 縣市或 368 鄉鎮區）都抓不到這件事，只有座標抓得到。而 Open-Meteo 的區級地名覆蓋也極差（大安、信義、西屯、北投、淡水、中正、三重全部查無），故「用區名查」這條路在技術上也不通。

## 方案選擇

| 方案 | 大安區 | 陽明山 | 梨山 | 隱私 | 結論 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| A：模糊座標 0.01 度 | ✓ | ✓ | ✓（差 1.3°C） | 上傳約 1.1 公里精度 | ✅ 採用 |
| B：22 縣市座標表 | ✓ | ✗ 天氣類型錯 | ✗ 差 8.5°C | 座標完全不上傳 | ❌ 山區長輩會拿到離譜的答案 |
| C：精確座標 | ✓ | ✓ | ✓ | 上傳住址級精度 | ❌ 隱私成本無謂——見下 |
| D：地名多變體 fallback | — | — | — | — | ❌ 把查不到變成查錯 |

### 為什麼是 0.01 度（約 1.1 公里）

先試過 **0.1 度（約 11 公里）**，因為 Open-Meteo 全球模式的網格約 11 公里，理論上無損。**實測否決**：

- 陽明山：精確 31.1°C **雷雨** → 模糊 32.4°C **毛毛雨**（天氣類型都變了）
- 梨山：精確 18.9°C → 模糊 22.4°C

代表它對台灣有更細的資料或內插。改試 **0.01 度**：

- 大安區、陽明山、西屯區：**與精確座標完全一致**（陽明山的雷雨保住了）
- 梨山：18.9 → 17.6°C（差 1.3°C，天氣類型相同）——地形太陡，可接受

故 0.01 度是「天氣幾乎無損、精度不足以定位到住址」的交會點。C（精確座標）多付隱私成本卻換不到天氣準確度，無謂。

## 元件設計

### 1. App：座標四捨五入到 0.01 度再上傳

`app/src/lib/location.ts` 的 `currentPlace()` 改為回傳地名**與**模糊座標：

```ts
export type ElderPlace = { place: string; latitude: number; longitude: number };

export async function currentPlace(): Promise<ElderPlace | null>;
```

⚠️ **四捨五入必須在手機端做**，不可上傳精確座標再由後端捨去：後端一旦收到精確值，它就已經進了伺服器的記憶體與（潛在的）log。隱私邊界要劃在資料離開裝置之前。

回傳 `null` 表示「這輪沒有位置」（未授權、無快取位置、譯不出地名）——語意與原本的空字串相同。

### 2. `/turns`：新增兩個 query param

`create_turn` 的簽章加入 `latitude: float | None = None`、`longitude: float | None = None`。

三者（`location`／`latitude`／`longitude`）**必須同時具備才寫入**：只有地名沒有座標，或反之，都視為「這輪沒有位置」而不寫入。理由：半套資料會讓下游要處理「有地名沒座標」的分支，而那個分支沒有任何呼叫端會產生——App 要嘛三個都給，要嘛都不給。

### 3. `elder_locations`：新增兩欄

⚠️ **這張表已經存在於正式庫**（PR #55 今早合併）。`CREATE TABLE IF NOT EXISTS` 對它是 no-op，**把欄位加進 `ELDER_LOCATIONS_DDL` 只有新庫吃得到、既有庫永遠缺欄位**。新欄位必須獨立以 `ALTER` 補：

```python
ELDER_LOCATIONS_COORDS_MIGRATION_DDL = (
    "ALTER TABLE elder_locations ADD COLUMN IF NOT EXISTS latitude DOUBLE PRECISION;"
    "ALTER TABLE elder_locations ADD COLUMN IF NOT EXISTS longitude DOUBLE PRECISION;"
)
```

`ensure_schema` 中本段須排在 `ELDER_LOCATIONS_DDL` 之後（新庫要先有表才 ALTER 得動）。

⚠️ 一併更正 `ELDER_LOCATIONS_DDL` 上方那句註解——它現在寫著「全新的表：既有庫沒有舊資料要升級……故不需 ALTER 補欄位」。那句話今早為真，現在起為假，留著會誤導下一個加欄位的人。

**欄位可為空**（`ALTER ... ADD COLUMN` 對既有列必然填 NULL）。`ElderLocation` 的 `latitude`／`longitude` 型別為 `float | None`；`LocationFacts` 讀到 NULL 時只注入地名、不注入座標（既有列即此情形，行為退回 PR #55 的樣子）。

### 4. `LocationFacts`：注入地名與座標

```
這位長者的手機在 3 分鐘前回報他人在台北市大安區（查這裡的天氣請用座標 25.03,121.54）。
```

座標缺漏（既有列）時退為原本的措辭，不提座標。

⚠️ title 的「僅供參考——他問到的地點不一定是這裡」**一字不動**：那是 anchoring 防線，而實測已證明它有效。

### 5. `get_weather`：新增選用的 `latitude`／`longitude`

```python
parameters={
    "type": "object",
    "properties": {
        "location": {"type": "string", "description": "地點名稱，例：台南、高雄。回覆時用它稱呼地點。"},
        "latitude": {"type": "number", "description": "情境附的座標；只有在長輩問的就是他所在地時才帶"},
        "longitude": {"type": "number", "description": "同上"},
    },
    "required": ["location"],
}
```

handler 行為：`latitude` 與 `longitude` **都有** → 直接查預報，**跳過地理編碼**；否則 → 走地理編碼（見第 6 節）。

`location` 永遠必填：金孫要對長輩說「台北市今天…」，沒有地名它只能說「您那邊今天…」。

⚠️ **不做座標範圍驗證**。模型幻覺出一個座標的後果是「天氣答錯」——與 Bug 1 同級，但 Bug 1 是必然發生、這是偶發。加台灣邊界檢查會擋掉出國的長輩（`金門` 118.3、`蘭嶼` 121.5，邊界本身也難定），且驗證失敗時除了「查不到」也做不了別的。YAGNI。

### 6. 地理編碼：加上 `countryCode=TW`

`_GEOCODE_URL` 加 `&countryCode=TW`。這是 Bug 1 的根治：山西的台南從此不會被選中。

代價與收益：命中率從「會答錯」變成「6/22 縣市答得出來，其餘誠實說查不到」。**這是刻意的取捨**——工具對查無結果已有優雅處理（「查不到「台南」這個地點的天氣。」），而錯答無法補救。

⚠️ **不做多變體 fallback**（見「方案選擇」D）：它會讓 `新竹縣` 命中屏東的新竹村。**寧可答不出來，不可答錯**——這是本文貫穿的原則。

⚠️ 這條路只服務「長輩口說地名」。定位路徑走座標，不受 6/22 命中率影響。

### 7. `WEATHER_SPEC` 的 description 改寫（Bug 2 的根治）

現行：

> 只有在你已確認長輩要查哪個城市時才呼叫；若不知道地點，先開口問長輩人在哪個城市，不要自行假設台北。

改為（定稿，實作時逐字採用）：

> 查詢指定地點今天的天氣（概況與氣溫）。
> 情境若附上長輩目前位置與座標，而他問的就是所在地的天氣，帶上該座標與地名呼叫，不要多問。
> 他問的是別的地方（例如等下要去哪裡），就用他說的地點名稱、不要帶座標。
> 兩者都不知道時，先開口問他要查哪裡，不要自行假設台北。

⚠️ 這段與 `agent.py` 的地點三句**必須語意一致**。Bug 2 的根因就是兩者矛盾——工具描述與 system prompt 都會進模型的 context，改一個不改另一個，模型會選保守解而功能靜默失效。**日後改其中一處，必須同時檢查另一處。**

## 錯誤處理

| 情況 | 行為 |
| :--- | :--- |
| App 取不到位置／權限被拒 | `currentPlace()` 回 `null`，不帶三個 query param；金孫照舊開口問（與 PR #55 相同） |
| 只帶地名沒帶座標（不該發生） | 視為「這輪沒有位置」，不寫入（見第 2 節） |
| 既有列沒有座標 | `LocationFacts` 只注入地名；模型無座標可帶 → 走地理編碼 → 可能查不到 → 誠實回覆 |
| 模型帶了座標但長輩問的是別處 | anchoring 失效。防線是 title 措辭與工具描述，實測有效；若上線後仍發生，回頭重估工具方案（見 PR #55 spec） |
| 地理編碼查無結果 | 回「查不到「X」這個地點的天氣。」（既有行為，不變） |

### ⚠️ 行為驗證只能靠真 Gemini

Bug 2 的本質是「兩段提示詞矛盾 → 模型選保守解」。**單元測試抓不到這種 bug**——假 LLM 不會推理，兩段矛盾的提示詞在它眼裡只是兩個字串。

本輪的三個 bug 中有兩個（2 與 anchoring）是這樣被發現的：拿真的 Gemini 跑三條複驗。故本設計要求實作後**必須重跑同一組探針**（scratchpad 的 `anchoring_probe.py`，不碰資料庫、只用真 Gemini 與 Open-Meteo）：

1. 允許定位 → 「今天天氣如何」→ 直接答**所在地**天氣，不反問
2. 無位置 → 「今天天氣如何」→ 開口問
3. 允許定位 → 「等下要去別的地方吃飯，那邊天氣如何」→ 開口問是哪裡，**不拿所在地去查**

第 1 條是 Bug 2 的驗證，第 3 條是 anchoring 防線。**兩條都是設計層級**：失敗要改設計，不是修一行。

## 與既有設計的衝突

`2026-07-17-長輩目前地點-design.md` 的核心決策之一是「**只存地名不存座標**：座標在手機端就譯成地名，永不上傳」，理由是隱私。本文**推翻它**。

Leo 當時的決定沒有錯——**錯的是它所依據的前提**：我們都以為地名足以查到天氣。實測顯示地名路徑 6/22 命中，且行政區這個抽象本身就抓不到真正決定天氣的海拔。

本文保留該決定的**精神**（不上傳住址級精度），改以 0.01 度模糊化實現：資料庫存的是約 1.1 公里見方的格子，在市區是上萬人的範圍。

⚠️ 誠實載明其限制：**在人口稀疏的山區，1.1 公里可能只有幾戶**。這是本方案真實的隱私成本，不是零。接受它的理由是：山區長輩恰恰是縣市表錯得最離譜的那群（梨山差 8.5°C），而讓金孫對他們講錯話也是一種傷害。

實作時須同步更新該 spec 的「核心洞察」與「方案選擇」節，指向本文。

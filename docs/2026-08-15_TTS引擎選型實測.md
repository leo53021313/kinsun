# TTS 引擎選型實測：CosyVoice3／VoxCPM2／fish-speech（2026-08-15）

> **一句話**：**維持 CosyVoice3**。決定性理由不是速度，而是 **VoxCPM2 會破壞語句的開頭**
> ——ASR 回送顯示「記得中午要吃血壓的藥」被合成成「**吸毒**要吃血壓的藥」，
> 台語更把「會記得食藥仔」變成「**忘記**吃藥」。而金孫的回覆以短句為主，開頭就是整句。
>
> **問題來源**：語音層選型盤點，確認現行引擎是否為最適選擇。
>
> 量測環境：DGX Spark（GB10 / aarch64 / CUDA）｜分支 `Babic`｜**未改動任何程式碼**
> 量測日期：效能與音質 2026-08-12，ASR 回送 2026-08-15
> 量測腳本：session scratchpad 之 `engine_bench.py`／`loopback_asr.sh`——**未固化入 repo**，
> 重跑方式見文末附錄

## 一句話結論（詳述）

**維持 CosyVoice3。**

決定性的理由不是速度，而是**VoxCPM2 在短句上不穩定，而金孫的回覆以短句為主**。
這一點由兩種獨立的量測同時證實：客觀上短句輸出長度波動達 73%（CosyVoice3 中句僅 3%），
主觀聽測則是「短句不像參考人、中句前半聽不出在講什麼、長句反而不錯」。

其餘差距同向：CosyVoice3 整體 RTF 0.74 對 1.34、熱載入 14.6s 對 44.4s。
VoxCPM2 唯一的結構性優勢——不需要參考音的逐字稿——在我們已用「系統下發朗讀稿」
解決該問題之後，價值大幅下降。

fish-speech 因**授權**（Research License，商用需另外取得）與 **aarch64 支援未知**兩項，
在本專案的條件下不建議投入，本次未實測。

## 一、實驗方法

兩個引擎吃**完全相同**的輸入：

| 項目 | 值 |
|---|---|
| 參考音檔 | `prompt-leo.wav`（金孫正式服務在用的那一份） |
| 參考逐字稿 | 「阿嬤您好 我是小明 今天天氣不錯 阿嬤記得按時吃飯 多喝水喔」 |
| 測試句 | 4 句，取自金孫真實會講的話，長度分三級＋台語一句 |
| 重複次數 | **每句 3 次** |
| 機器 | 同一台 DGX，一次只載入一個模型 |

**為什麼每句要跑 3 次**：先前量「參考音檔長度對輸出的影響」時，同一句話三次跑出
5.04／6.72／11.88 秒。只跑一次會得到與事實相反的結論。這次的數據證明這個顧慮是對的
（見發現 ①）。

重跑方式見文末附錄。

## 三、三個發現

### ① VoxCPM2 的短句輸出長度波動達 73%

同一句「阿嬤，我在這裡陪您喔。」跑三次，產出 **1.60／2.88／1.44 秒**——最長是最短的兩倍。
同一組實驗裡 CosyVoice3 中句的波動只有 3%（6.96／6.96／7.16）。

這件事對金孫特別要緊：**金孫大量的回覆都是短句**（附和、提醒、關心），
波動正好打在主要使用情境上。長輩會聽到同一句話時快時慢。

⚠️ **主觀聽測獨立證實了這一點**（見第五節）：VoxCPM2 的品質隨句子變長而變好——
短句音色不像參考人、中句前半聽不出在講什麼、長句反而整體不錯。
兩種完全不同的量測方式指向同一個結論。

### ② VoxCPM2 講話明顯較快，而這對長輩是缺點

同一句中句，CosyVoice3 產出 7.03 秒、VoxCPM2 只有 5.55 秒——**快 27%**。

一般情境下「快」是效能優勢，但金孫的使用者是長輩，**講太快聽不清楚**。
這一項不能只看數字，要以人耳判斷（見第五節）。

### ③ 逐字稿需求是架構層級的差異

```python
CosyVoice3   inference_zero_shot(text, prompt_text, prompt_wav)   # 要逐字稿
VoxCPM2      generate(text=text, reference_wav_path=prompt_wav)   # 不要
```

零樣本克隆吃「音檔＋逐字稿」配對時，逐字稿錯字會直接讓克隆品質下降。金孫現行的
`voice_profiles` 設計——**由系統下發固定朗讀稿、家屬照唸**——存在的理由正是要保證
逐字稿正確。若改用 VoxCPM2，這個約束就消失，家屬可以隨意講一段。

**但這個優勢的實際價值有限**：該問題我們已經解掉了，而且系統下發朗讀稿還順帶帶來
第二個好處——把四條錄製準則（長度、含「阿嬤」、「喔」的位置、語調起伏）內建成
測試會擋的規則。換掉引擎會一併失去這個機制。

## 五、主觀聽測

> 音檔：`引擎對照-CosyVoice3-vs-VoxCPM2/{cosyvoice3,voxcpm2}/`，同名兩兩對照。

評分者：本專案語音層負責人，盲聽同一句話的兩個版本。

| 項目 | CosyVoice3 | VoxCPM2 |
|---|---|---|
| 短句 | 可用 | **音色不像參考人** |
| 中句 | 可用 | **前半句聽不出在講什麼**，尾句還行 |
| 長句 | 可用 | **整體不錯**，只是語速偏快 |
| 台語 | 不行——只是用國語念台語字 | **更差——聽不出在合成哪一句** |

### 主觀評分與客觀數據指向同一件事

VoxCPM2 的品質**隨句子變長而變好**：短句不像人、中句前半崩掉、長句反而不錯。
這與第二節量到的「短句輸出長度波動 73%、長句只有 10%」完全一致——
**兩種完全獨立的量測方式指向同一個結論：VoxCPM2 在短輸入上不穩定。**

這對金孫是致命的：**金孫的回覆以短句為主**（附和、提醒、關心），
正好落在 VoxCPM2 最弱的區間。

### 台語：兩個底模都不能用，但失效方式不同

- CosyVoice3：**照著字念成國語**。錯，但輸出與輸入文字對得上。
- VoxCPM2：**輸出與輸入文字對不上**——合成出來的是別的句子。

VoxCPM2 這種失效嚴重一級：前者是「腔調錯」，後者是「內容錯」。

## 五之二、ASR 回送實驗：VoxCPM2 到底唸了什麼

「聽不出在唸什麼」是主觀描述，無法寫進結論。故把兩個引擎的輸出**丟回本專案的
ASR 服務**，用辨識結果客觀回答「輸出與輸入文字對不對得上」。

| 輸入文字 | 引擎 | ASR 聽到的 |
|---|---|---|
| 阿嬤，你食飽未？會記得食藥仔喔。 | CosyVoice3 | 阿嬤 妳食飽未 會記得食藥仔喔 |
| 同上 | VoxCPM2 | **你是爸爸要罵的 忘記吃藥知道嗎** |
| 記得中午要吃血壓的藥，吃飽飯再吃比較不傷胃。 | CosyVoice3 | 記得中午要吃血壓的藥 吃飽飯再吃比較不傷胃 |
| 同上 | VoxCPM2 | **吸毒**要吃血壓的藥 吃飽飯再吃比較不傷胃 |

**方法的對照組**：有人會質疑「是不是 ASR 聽不懂台語」。這個實驗自帶反證——
ASR 把 CosyVoice3 的台語輸出完整聽成「食飽未」「食藥仔」，**它認得這些字**。
因此 VoxCPM2 被聽成別的字，不是 ASR 的問題。

### 這給出了比「短句不穩」更好的根因

原本的結論是「VoxCPM2 在短輸入上不穩定」。ASR 回送顯示更具體的現象：

> **它會破壞語句的開頭，後半是正常的。**

一個假設解釋掉三個觀察：

| 觀察 | 用「開頭崩壞」解釋 |
|---|---|
| 短句最差 | 開頭就是整句 |
| 中句前半崩、後半好 | 「記得中午」→「吸毒」，其後完全正確 |
| 長句反而不錯 | 崩掉的開頭只佔一小部分 |

### ⚠️ 對長照場景的意義

台語那句最值得注意的不是「字不對」，是**語意被反轉**：

```
會記得食藥仔喔   →   忘記吃藥知道嗎
```

用藥提醒被合成成相反的意思。在長照場景，這已經不是音質問題的層級。

⚠️ **這一節不能推論到微調後的模型**。兩個受測的都是**未微調台語的底模**，
VoxCPM2 的 smoke 腳本自己就寫明「base 未微調台語，輸出會是華語／廈門腔」。
本專案先前（2026-07-30）以微調路線驗證過**台語克隆走 VoxCPM2 可行、CosyVoice3 不行**，
那個結論與本次測試不衝突——**它們測的是不同的東西**：本次測底模，先前測微調後。

## 六、對金孫的建議

1. **正式服務維持 CosyVoice3**：速度快近一倍、輸出穩定、載入快 3 倍，且現有的
   `voice_profiles` 全套（朗讀稿、四條準則、測試）都是圍繞它建立的。
2. **VoxCPM2 保留為台語路線的候選，但必須微調，且微調後必須驗證「輸出＝輸入」**：
   本次測到的底模在台語上比 CosyVoice3 更差——不只腔調錯，而是合成出別的句子，
   甚至把「會記得食藥仔」變成「忘記吃藥」。所以「直接拿來用」不成立。
   若日後走微調路線，建議把本文的 ASR 回送實驗納入驗收：**用藥提醒類的句子
   一旦語意反轉，後果不是音質問題**。
   它的價值在於先前（2026-07-30）已驗證**微調後的台語克隆走 VoxCPM2 可行、
   CosyVoice3 不行**。兩者互補而非二選一：國語用 CosyVoice3、台語走 VoxCPM2 微調。
3. **fish-speech 不投入**：授權與 aarch64 兩項風險，在現階段不划算。

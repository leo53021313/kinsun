## 3. 🔴 嚴重問題

### S1（已修）每晚反思一跑就 400，反思功能等於不存在

**現象**：夜間批次對 4 位長輩全部丟出「每晚反思失敗」，`strategies` 表零新增。正式庫最後一條守則停在 **2026-07-20 14:09**（該筆為手動觸發，當時主模型還是 3.1）。生成模型於 **2026-07-25**（`fa25cb3`）升為 `gemini-3.5-flash-lite`——**此後只要反思真的被執行，就必定失敗**。它沒有被更早發現，是因為 S5：這支批次根本沒在跑。

**根因**：`reflect_days` 把對話歷史直接當 messages 餵給 Gemini，而對話**必然以金孫的回覆（模型回合）結尾**；gemini-3.5 拒收這種請求：

```
400 INVALID_ARGUMENT — Requests ending with a model turn are not supported.
```

A/B 實測確認與 `response_schema` 無關，純粹是「結尾是模型回合」：

| 送出的訊息 | 結果 |
| :--- | :--- |
| 結尾是 assistant＋schema | ❌ 400 |
| 結尾是 assistant、無 schema | ❌ 400 |
| 結尾是 user＋schema | ✅ 正常回傳 |

同一家族的問題在 7/26 已修過一次（`cdc9f35` 工具結果回帶改用 `role="user"`），反思這條路徑漏了。

**為什麼沒人發現**：失敗被 `except Exception: logger.warning("每晚反思失敗 elder=%s")` 吞掉，**沒有例外內容**，看不出是 400 還是逾時；離線測試用假 LLM，永遠不會踩到真 API 的這條規則。

**修法**：改送單一「文字稿」user 訊息——與同專案 `reports/summaries.py::_transcript_message` 完全相同的做法（該檔已載明理由：直接餵歷史會讓模型「接話」而非旁觀分析）。

**驗證**：新增回歸測試 `test_the_request_never_ends_with_a_model_turn`（拿掉修復即紅）；重啟後端以真 Gemini 跑夜間批次，產出 2 條守則：

```
[address/3天] 長輩習慣叫金孫，對話時請直接接受並延續這個稱呼。
[topic/3天]   長輩經常提及她在台北念大學的孫女小婷，聊到孫女時可以多加關注與互動。
```

**順帶**：`worker.py` 兩處 `logger.warning` 補上 `exc_info=True`——讓這個 bug 隱形六天的正是「沒有原因的一行警告」。

### S2（已修）對講機端點佔住事件迴圈：整台後端一次只服務得了一位長輩

**現象**：`POST /api/v1/turns` 宣告為 `async def`，但底下整段（進站音檔上傳、ASR、Gemini、TTS、落庫）都是同步阻塞呼叫，直接跑在事件迴圈上。

**實測（修復前）**：一輪對話進行中（3.08 秒），同時打最簡單的 `GET /healthz`——

```
對話回合耗時 3082 ms（HTTP 201）
同時間 healthz：3 秒內只完成 2 次探測、中位數 1447 ms、最大 2891 ms
```

**影響**：第二位長輩開口要排隊等第一位講完；家屬 App 拉通知、觀測後台、LINE webhook 全部一起卡住。長輩越多越明顯——這是**線性劣化**，不是尖峰問題。

**修法**：把同步本體抽成 `_run_turn`，以 `starlette.concurrency.run_in_threadpool` 執行（順序一字未動）。FastAPI 對所有同步 handler 本來就是這樣跑的，這裡只是把這支端點放回同一條路上。

**驗證（修復後）**：

```
對話 2941 ms；同時間 healthz 取樣 28 次、中位數 2 ms、最大 80 ms
```

Opik trace 樹完整保留（`care_conversation → care_turn_voice → asr／risk_assess／abuse_moderate／memory_assemble／agent_generate／tts／deliver`），確認 contextvars 有跨執行緒傳遞。新增回歸測試 `test_the_blocking_work_never_runs_on_the_event_loop`（以 `asyncio.get_running_loop()` 判定，不靠計時，拿掉修復即紅）。

> ⚠️ 併發打開後，下一個瓶頸會是 `DATABASE_POOL_MAX_SIZE=5` 與 Gemini 每分鐘配額（見 M7），上線前要一起看。

### S3（已修）危急誤報真的送到家屬手機，且理由欄自己就寫著「並非危急」

> **修復（2026-07-26，Leo 指示）**：症狀詞撐住的 L2，在「分級器**沒故障**、判定為 **L0（完全沒事）**、且**信心 ≥ 0.7**」時降為 **L1**（落庫留痕、不通知家屬）。降到 L1 而不是 L0，是因為長輩確實講了症狀詞，這件事該讓家人在每日摘要看到（✅ D-10 己-5），只是不該響警報。
> **三條紅線一步沒動**：絕對詞（想不開、喘不過氣、叫救護車…）仍無條件 L2；分級器故障時症狀詞照舊撐 L2（fail-safe，另補測試守住——原本沒有任何測試守它）；分級器只要判 L1（它自己也覺得有小訊號）就照舊通報。
> 翻案門檻 0.7 **刻意高於** `SAFETY_CONFIDENCE_MID`(0.4)，理由與 `safety_moderation_min_confidence` 同源：關掉一道安全機制，要比啟動它更難。

12 筆風險事件中，**至少 4 筆為明確誤報**，而且家屬 App 通知中心真的收到警報：

| 長輩說的話 | 系統判定 | 分級器自己寫的理由 |
| :--- | :--- | :--- |
| 你放心啦，**我沒有跌倒**，好好的 | L2 → 通報家屬 | 「使用者明確表示沒有跌倒且身體狀況良好，屬於一般日常對話」 |
| 我**十年前**跌倒過一次…現在都好了 | L2 → 通報家屬 | 「使用者描述的是十年前的舊傷且已經痊癒…並無現階段的危急情況」 |
| **隔壁的陳太太**昨天跌倒送醫院了 | L2 → 通報家屬 | 「使用者在描述鄰居的狀況，並非自身發生跌倒」 |
| 老人家要**怎麼預防**跌倒？ | L2 → 通報家屬 | 「使用者詢問預防跌倒的方法，屬於一般健康衛教諮詢，無立即危險」 |

LLM 分級器判斷全部正確，是**關鍵詞地板／絕對詞 override** 把它們一律拉到 L2。

12 筆風險事件分佈：**正確 4 筆**（浴室跌倒爬不起來、胸悶喘不過氣、輕生念頭、頭暈想吐）、**可辯護 4 筆**（自行加藥、漏藥、要求立刻叫兒子回來——保守通報可接受）、**明確誤報 4 筆**（上表）。

這與 07-17／07-18 兩份報告記錄的 D-72 追蹤項同源，本輪的新證據是：**誤報已經實際送達家屬手機**（`app_notifications` 有對應紀錄、`risk_notification_logs` 標記 `delivered=True`），且真假警報的文案一模一樣（「⚠️【金孫關懷提醒】…請盡快主動關心一下」），家屬無從分辨。三分之一的警報是誤報，狼來了效應會讓真警報被忽略。

**仍待 D-72 拍板的部分**：通知文案沒有帶上判定依據，家屬看到的真假警報長得一模一樣。本次只改了「哪些該通報」，沒改「通報長什麼樣」——若要讓家屬自己分辨，文案要加上觸發原因（「他說他跌倒了」vs「他問到跌倒相關的事」）。

**真 LLM 驗證（2026-07-26，`GEMINI_API_KEY4`）**：拿**專案自己的標注集**（`data/safety_eval/labeled_utterances.jsonl`，60 句、其中 27 句標注為應通報），每句只呼叫一次分級器、把同一份判定餵給新舊兩套規則——差異只可能來自規則本身，不會被模型的隨機性污染。

| 標注集 60 句 | 舊規則 | 新規則 |
| :--- | :---: | :---: |
| 應通報 27 句，**漏掉** | 0 | **0**（一句都沒掉） |
| 不該通報 33 句，**誤報** | 7 | **3** |

剩下的 3 筆誤報全是**絕對詞**造成的（「新聞說有人想不開跳樓」「連續劇裡的媽媽昏倒了」「年輕時差點昏倒在工廠」），那是刻意保留的紅線，不在本次改動範圍。

> ⚠️ **這裡差點做錯**：一開始的規則是「分級器判定低於 L2 就准翻案」，標注集實測顯示它會**新漏掉 2 句**（「我好幾天沒睡，眼睛都花了」「最近都沒力氣，連菜都提不動」——分級器判 L1／信心 0.90–0.95）。收緊成**只准 L0（完全沒事）翻案、L1 一律照舊通報**之後，漏報歸零而誤報的修復量不變。這個分別是量出來的，不是想出來的。

### S4（已修）沒查任何來源，卻對長輩說「國健署網站說」

Opik 逐輪比對（工具 span 是唯一真相）：

| 長輩問 | 該輪用到的工具 | 金孫回答 |
| :--- | :--- | :--- |
| 老人家要怎麼預防跌倒？ | **（無）** | 「**國健署網站說**，在家裡要穿防滑鞋子、走道保持亮光…」 |
| 鄰居說吃苦瓜可以治好糖尿病…？ | **（無）** | 「**查核中心說這是假的喔**！千萬不要停藥。」 |
| 跟我說說怎麼保養身體才會健康 | **（無）** | 直接給健康建議（均衡飲食、多運動…） |
| 血糖高的人可以吃水果嗎 | web_search＋RAG | 「衛福部網站說水果可以吃…」（有依據） |

兩個問題疊在一起：

1. **模型常常跳過 `health_education_rag` 就回答衛教問題**，違反系統提示詞「衛教問題一律先用 health_education_rag」。
2. **來源名稱是編的**。系統提示詞裡寫著「引用查到的內容要口語帶一句來源，例如『衛福部網站說』『查核中心說這是假的』」——這兩句例句原封不動出現在沒查任何東西的回覆裡，模型把它當成句型模板照抄。

對一個給長輩用的健康陪伴產品，冒用政府機關名義背書健康建議是**信任與法律雙重風險**（即使這次的內容剛好正確）。

**修復（2026-07-26，Leo 指示）**，三層：

1. **提示詞不再遞刀子**：可照抄的例句換成條件式描述（「工具真的回傳來源時，口語帶一句來源，而且要照工具給的名字講；沒有查、或工具查不到，就不可以講出任何機關、網站或查核單位的名字」）。
2. **本輪來源登記簿**（新的跨層 seam `turn_context.turn_sources()`，contextvar，方向與既有的 `elder_utterance` 相反：工具→agent）。只有真的握有外部來源的工具登記：web_search 的網域、health_rag 的 citation publisher、news 的媒體名；天氣、路線、TDX、排程刻意不登記——它們沒有可以講給長輩聽的出處。
   > ⚠️ 閘門是「**有沒有拿到來源**」而不是「有沒有呼叫工具」。這個分別是關鍵：目前沒有 active RAG release，衛教檢索每次都回「查不到」，若寫成「呼叫過就放行」，模型只要呼叫一次、拿到查不到、再照樣冒名就能穿過去——而上表第 4 列證明模型**會**呼叫工具。
3. **出站防線** `_no_fake_source()`（與既有的 `_speakable` 同層同形）：**逐個機關名比對**它有沒有對應的來源（「國健署」要對上 `hpa.gov.tw`），對不上就移除那段引述。**只認封閉的機構清單**，不做通用的「X 說」偵測——後者需要無窮無盡的豁免（電視說、醫生說、我女兒說…），封閉清單讓這些情形自動免疫。
   > ⚠️ 對抗審查抓到的重點：一開始寫成「這輪有沒有**任何**來源」的布林閘，那會被主動問候直接穿過——早安問候本來就會呼叫 `get_news`，登記了「中央社」就把整輪防線關掉，「疾管署提醒流感疫苗要打喔」照樣送出去。改成逐機關比對之後，查了新聞不能冒衛福部的名。

實測行為（離線、確定性）：

| 輸入回覆 | 沒有來源時 |
| :--- | :--- |
| 國健署網站說，在家裡要穿防滑鞋子、走道保持亮光。 | 在家裡要穿防滑鞋子、走道保持亮光。 |
| 查核中心說這是假的喔！千萬不要停藥。 | 這是假的喔！千萬不要停藥。 |
| 醫生說要按時吃藥／電視說最近很冷／您女兒說她週末會回來 | **原樣通過** |
| 我兒子在衛福部上班／健保署的卡片您有帶著嗎 | **原樣通過**（機關當地點講，不是引述） |

⚠️ **這是絆索，不是解藥**：機關名不是封閉集合（「衛生局」「長照中心」都不在清單上），模型換個名字仍會穿過。它擋掉的是實測中真正發生的那幾種，不可對外宣稱「冒名問題已解決」。

**刻意沒做**：衛教問題強制先查 RAG。今天沒有 active release，強制的結果是每個衛教問題都變成罐頭拒答——等 RAG 建版完成後再評估。

### S5（已修）排程器「活著但停止運作」：夜間批次 13 天沒跑，而且**此刻連用藥提醒都沒在派送**

> ⚠️ 這一項在深入追查後，根因與初判不同。原本以為是「排程程序沒常駐」，
> 實際是**程序活著卻卡死**——後果更嚴重，因為 `kinsun.sh status` 顯示它是 RUNNING。

**現場證據（2026-07-26 21:22 採集，刻意沒有重啟以免現場消失）**：

| 觀察 | 數值 |
| :--- | :--- |
| 程序狀態 | PID 3049012 存活，已跑 1 小時 50 分，CPU 只用了 **4 秒** |
| `schedule-dispatch`（cron **每分鐘**）last_run | **14:05:32**（採樣時 21:22，停了 7 小時） |
| `daily-consolidation` last_run | **2026-07-13 03:00** |
| DB 連線 | `ESTAB Recv-Q=11988` → **收到 11988 bytes 沒被程式讀走** |
| 日誌 | 自 19:31 起零成長，**沒有任何例外** |

#### ⚠️ 根因更正（2026-07-26 23:20，取代以下兩段初判）

**它從來沒有假死。它一直在跑，只是每一輪都認領失敗。**

當晚重啟到新版程式碼後量到的現場：心跳每 65 秒推進一次、日誌持續輸出、CPU 幾乎零——
但 `schedule-dispatch` 仍卡在 14:05 不動。迴圈是活的，`run_due` 每輪都回來了，
卻**一個 job 都認領不到**。

真正的根因是 `scheduler/state.py::try_claim` 拿**浮點數做等值比對**：

```sql
UPDATE scheduler_state SET last_run_at = %s
 WHERE job_name = %s AND last_run_at = %s   -- ← 這個 `=`
```

Supabase 這條連線的 `extra_float_digits = 0`，PostgreSQL 因此只用 **15 位有效數字**
輸出 `double precision`。實測正式庫：

| | 值 |
| :--- | :--- |
| 資料庫實際儲存 | `1785045932.084225` |
| 程式讀回來的 | `1785045932.08422`（**是另一個 double**） |
| `WHERE last_run_at = 讀回值` | **命中 0 列** |
| `WHERE last_run_at <= 讀回值 + 1ms` | 命中 1 列 |

於是該 job **從此再也認領不到，直到有人手動改資料庫**。這解釋了所有原本說不通的現象：

- **重啟六次完全無效**——壞掉的值在資料庫裡，不在記憶體裡
- **各 job 停擺時間點全都不一樣**——每個 job 各自死在「它的時間戳剛好需要 16 位以上有效數字」的那一刻，隨機、逐一、無聲
- **`status` 顯示 RUNNING 是真的**——它真的在跑

**我當時錯在哪**：上一段寫著「epoch 往返精度我也實測過沒有損失（`1783882859.33351`
轉回完全相等）」。那個實測是對的，但**測錯了一半**——我驗證的是 Python 端
`datetime.fromtimestamp(x).timestamp() == x`，而失效的是 **SQL 端的 `WHERE` 比對**，
那一半我從頭到尾沒測。`Recv-Q=11988` 也一樣：它證明「資料到了沒人讀」，
我卻拿它推論成「對端消失」，而那個推論從來沒有被驗證過就寫進了修復理由。

**修法**：改成範圍比對 `last_run_at <= expected + 1ms`（`CLAIM_TOLERANCE_SECONDS`）。
雙 worker 防重語意不變：贏家把值推到 `now`，輸家的條件因此不成立。容差取 1 毫秒——
遠大於浮點文字往返誤差（微秒級），遠小於最密的 cron 間隔（1 分鐘），兩端各留三個數量級。
合約測試新增「讀回值略小於實際值」情境，Fake 與 Pg 兩個 adapter 同跑。
全庫其他浮點比對本來就都是 `>=`／`<=` 範圍式，這是唯一的受害點。

**修復後實測（23:24 重啟）**：`daily-consolidation`、`schedule-dispatch`、`daily-greeting`、
`inactivity-care`、`audio-cleanup`×2、`observability-cleanup` **全數恢復認領並執行**，
`schedule-dispatch` 恢復每分鐘派送。夜間護欄同時受到真實檢驗：13 天份的問候補跑在
23:26 觸發，全部 39 位長輩都印出「已超過補問候時限，今天不問候」，
`reminder_logs` 新增 **0 筆**、assistant turns **0 筆**——**沒有任何一位長輩在半夜被吵醒**。

> 以下兩段為當時的初判，保留以存真，但**結論是錯的**。

**補跑邏輯本身是好的**：`scheduler.py::_claim_if_due` 會把「上次執行時間的下一個 cron 時刻早於現在」判為到期並原子搶占，epoch 往返精度我也實測過沒有損失（`1783882859.33351` 轉回完全相等）。問題不在判斷式——是整個 tick 迴圈沒有在動。

# 同意條款修訂草稿

**為什麼要改**：危急事件開逐字例外之後，家屬會看到長輩的原始對話與錄音。現行條款沒有寫這件事，這是**實質變更**，需要重新取得同意。

⚠ 這是設計端的草稿，**要法務審過才能上線**。

---

## 現行條款（`strings.ts` → `guardianHome.consent`）

> 建立後，金孫會記錄長輩與它的對話內容（文字與語音），用來陪伴關懷、產生每日摘要、偵測到危急狀況時通知家人；資料會一直保留，開發團隊為了改善服務可檢視內容。按下「建立長輩檔案」即代表您替長輩同意以上事項。

**缺什麼**：只說「通知家人」，沒說通知裡會**包含什麼**。家屬會看到逐字與錄音這件事，長輩與代為同意的家屬都不知道。

## 修訂版

```ts
consent:
  "建立後，金孫會記錄長輩與它的對話內容（文字與語音），用來陪伴關懷、" +
  " 產生每日摘要、偵測到危急狀況時通知家人。" +
  " 平常家屬只看得到每日摘要，看不到逐字對話；" +
  " 但偵測到危急狀況時，家屬會看到觸發當下那一段的原始對話與錄音，" +
  " 以便判斷該不該立刻聯絡或送醫。這段內容保留 30 天，之後只留事件時間與原因。" +
  " 對話資料會一直保留，開發團隊為了改善服務可檢視內容。" +
  " 按下「建立長輩檔案」即代表您替長輩同意以上事項。",
```

### 三個刻意的用字

**「平常⋯但⋯」** 先講常態、再講例外。倒過來寫會讓人以為家屬隨時都看得到。

**「觸發當下那一段」** 不是「對話紀錄」。範圍必須寫死在條款裡，否則日後擴大範圍不需要重新同意。

**「30 天」** 錄音是最敏感的一類，另訂較短期限。這與「對話資料會一直保留」不衝突——保留的是文字，錄音有期限。

## 三件配套

### 1. 既有使用者要重新同意
條款變更前建立的長輩檔案，家屬下次開 App 要出一次同意畫面。**沒有重新同意的帳號，危急詳情頁不給看逐字**——降級成只顯示 `reason` 與時間。

工程上要在 guardian 資料表加 `consent_version`，比對目前版本號。

### 2. 長輩端要知道
長輩沒有簽任何東西，是家屬代簽的。至少要讓長輩問得到：

```ts
elderPrivacy: {
  question: "我說的話誰會聽到？",
  answer:
    "平常只有我聽。您說的話我會整理成摘要給家人看，" +
    "不會把您說的每一句話都給他們。" +
    "但如果聽到您不舒服、跌倒這類事情，我會把那一段講給家人聽，" +
    "讓他們趕快來看您。",
},
```

長輩問「我說的話誰會聽到」時由阿白回答。這不是 UI 元件，是 LLM 的知識——寫進 system prompt。

### 3. 稽核紀錄
家屬每次開危急詳情頁都要留紀錄（誰、何時、哪一筆）。理由不是合規，是**長輩有權知道自己的話被誰聽過**。

未來若做長輩端的「誰看過我的話」畫面，資料源就是這個。

## 已定案（2026-08）

### 錄音保留 30 天
採設計端提的期限。這不是法規要求，是「家屬判斷得完」與「不留過多敏感資料」之間的取捨——危急事件的處理通常在當天結束，30 天足夠回溯與爭議釐清。

實作要一致：
- 錄音檔與逐字在 `created_at + 30 天` 後刪除，只留 `tier`／`reason`／`created_at`
- 前端 `audio_url` 與 `transcript` 拿到 `null` 時顯示 `criticalAlert.expired`，**不要顯示錯誤**——那是正常的過期，不是故障
- 刪除要有排程與稽核，不能只靠讀取時判斷

```ts
criticalAlert: {
  expired: "這件事超過 30 天了，錄音與對話已經刪除，只留下時間與原因。",
}
```

### 長輩本人不看危急事件紀錄
長輩端不做「我的危急事件」畫面。理由是看到「系統認為我有危險」會造成焦慮，而且長輩對這件事**無法採取任何行動**——處理的人是家屬。

但兩件事仍然要做到：
- 長輩問「我說的話誰會聽到」時，阿白要照上面 §2 的答案回答。**不主動說，問了要答。**
- 危急事件發生當下，阿白對長輩的回應維持沉穩（「先坐下休息」），**不提「我通知了家人」**——那會讓長輩覺得被監視。家屬那端自己會知道。

這個決定日後可以改。若要開放，資料源是稽核紀錄（§3），不是危急事件本身。

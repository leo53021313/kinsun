# 危急通知詳情 · 後端規格

**決議（2026-08）：危急事件開逐字例外。**

現行政策「家屬可看摘要、不開放逐字對話」（`api.ts` §243）維持，但**危急事件是例外**——家屬要判斷該不該打電話、該不該叫救護車，只給一句摘要不夠。

---

## 現況：三樣東西都不存在

型別核對結果（`shared/types.ts`）：

```ts
AppNotification = { content: string; created_at: number; severity?: NotificationSeverity }
RiskEventItem   = { tier: number; reason: string; created_at: number }
```

通知**沒有 id**，無法從清單導到詳情；沒有錄音、沒有逐字、沒有送達狀態。這頁在後端補完之前只能做靜態版。

---

## 要新增的端點

### `GET /api/v1/elders/{elder_id}/risk-events/{event_id}`

```ts
export type RiskEventDetail = {
  event_id: string;
  tier: number;                    // 沿用現行分級
  reason: string;                  // 沿用現行欄位
  created_at: number;
  /** 觸發當下那一輪的逐字。危急例外的核心。 */
  transcript: RiskTranscriptTurn[];
  /** 當時的錄音。null = 已過保存期或當時沒錄到。 */
  audio_url: string | null;
  audio_duration_ms: number | null;
  /** 通知送給了誰、什麼時候。 */
  deliveries: RiskDelivery[];
  /** 家屬處理狀態。 */
  handled_at: number | null;
  handled_by: string | null;
  /** 家屬回報這不算危急——誤判要能被修正，否則家屬會學會忽略通知。 */
  dismissed_at: number | null;
};

export type RiskTranscriptTurn = {
  speaker: "elder" | "bear";
  text: string;
  at: number;
};

export type RiskDelivery = {
  guardian_id: string;
  name: string;
  /** 送達 = 推播已投遞；已讀 = 家屬開過詳情頁 */
  delivered_at: number | null;
  read_at: number | null;
  /** 第二順位家屬的延遲送達時間（10 分鐘內沒人處理才送） */
  scheduled_at: number | null;
};
```

### `POST /api/v1/elders/{elder_id}/risk-events/{event_id}/handle`
家屬按「我處理好了」。寫 `handled_at` / `handled_by`，並**取消尚未送出的第二順位通知**。

### `POST /api/v1/elders/{elder_id}/risk-events/{event_id}/dismiss`
家屬按「這不算危急」。寫 `dismissed_at`，同樣取消後續通知。

這個回饋要進評估資料——誤判率是安全雷達唯一可信的品質指標。

AppNotification = {

## 逐字例外的四條界線

開例外不是全面開放。**只有危急事件那一輪**可以看逐字，不是整天的對話。

1. **範圍**：觸發危急判定的那一輪（長輩說的那句＋阿白的回應），前後各多帶一輪當上下文。不給整段 session。
2. **保存期**：逐字與錄音保留 30 天（**已定案**），之後只留 `tier`／`reason`／`created_at`。刪除要有排程與稽核，不能只靠讀取時判斷。過期後 `audio_url` 與 `transcript` 回 `null`，前端顯示「已刪除」而非錯誤。
3. **稽核**：家屬每次開啟詳情頁都要留紀錄（誰、何時、看了哪一筆）。長輩有權知道自己的話被誰聽過。
4. **同意條款要改**：現行條款沒有提到「家屬可在危急事件時看到逐字與錄音」。這是**實質變更**，不是補充說明——需要重新取得同意，不能靜默上線。草稿見 `handoff/同意條款修訂草稿.md`。

**長輩端不做危急事件紀錄畫面（已定案）**——長輩對這件事無法採取任何行動，處理的人是家屬。但長輩問「我說的話誰會聽到」時阿白要照實回答（見條款草稿 §2）。

## 前端在等什麼

`guardian-detail/alert/[eventId].tsx` 還沒寫。設計稿（`長輩端×家屬端 新視覺 UI` 家屬端 08）已定案，四個區塊：

1. 危急標籤＋標題（發生什麼）
2. 當時的錄音（播放器＋波形，波形可用 `audio_duration_ms` 畫假的）
3. 當時的對話（`transcript`，長輩靠左、阿白靠右）
4. 通知送給了誰（`deliveries`，含第二順位的 `scheduled_at`）

底部三顆鍵：打電話給長輩（主）、我處理好了、這不算危急。

**後端給了型別就能做，前端沒有阻塞。**

## 一個順帶發現

`TurnReply.duration_ms` 的註解寫著「保留給虛擬形象動畫對嘴（階段 5 後）」——這個欄位早就為了對嘴留好了。Otto 版的注音 viseme 可以直接用它，不用另外要後端加欄位。
